# Atelier

Coding-agent orchestrator with two first-class clients, a CLI and a desktop app, on top of one headless core.

| Package            | Directory          | Status                                                                                                           |
| ------------------ | ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `@atelier/core`    | `atelier-core/`    | Event contract, session, tools, subagents, protocol server; backends `claude-code` (M1) and `anthropic-api` (M3) |
| `@atelier/cli`     | `atelier-cli/`     | `atelier` command                                                                                                |
| `@atelier/desktop` | `atelier-desktop/` | Desktop chat app (M2)                                                                                            |

## Requirements

- Node 22.18+ (TypeScript runs natively; there is no build step) and pnpm.
- For the default `claude-code` backend: Claude Code logged in with your Claude subscription (run `claude` and use `/login`).
- For the `anthropic-api` backend: an Anthropic API key with credit, stored once in the macOS Keychain. The command asks for the key, so it stays out of your shell history:

  ```bash
  security add-generic-password -U -s atelier-anthropic -a "$USER" -w
  ```

  `ANTHROPIC_API_KEY` set for a single command takes priority. Do not export it in your shell profile: Claude Code would then bill the API instead of your subscription.

## Usage

```bash
pnpm install
pnpm atelier "add email validation to src/user.ts and run the tests"   # one turn
pnpm atelier                                                          # interactive; /exit or Ctrl+D to quit
```

| Option                             | Effect                                                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `-y`, `--yes`                      | Run `bash` commands that run sandboxed without asking (not the others, see below).                           |
| `--backend <name>`                 | `claude-code` (default, Claude subscription) or `anthropic-api` (Atelier's own loop, billed to the API key). |
| `--model <name>`                   | Model to use (default: `opus` on `claude-code`, `claude-sonnet-5-5` on `anthropic-api`).                     |
| `--cwd <dir>`                      | Working directory (default: current directory).                                                              |
| `--no-review`                      | Do not review changes or verify them (same as `ATELIER_REVIEW=off`).                                         |
| `--no-sandbox`                     | Run `bash` without the macOS sandbox (same as `ATELIER_SANDBOX=off`).                                        |
| `-h`, `--help` / `-v`, `--version` | Help and version.                                                                                            |

Output shows streamed text, one line per tool call (`▸ edit src/user.ts (1 edit) ✓`) and the turn's tokens: input, output, cache reads and writes, the share of the prompt served from the cache (`cacheRead / (input + cacheRead + cacheWrite)`), the number of model requests and the cost. A `cache miss` line says why the prompt cache could not be reused. When the backend reports it, the tokens line also says how full the context is (`context 45,000 / 200,000 (23%)`). A turn with more than one part (the main agent plus the risk declaration, the verifier or a review) gets a compact line under it with each part's cost and requests, or its tokens when neither is known: `phases: main $0.0400 (1 req) · verify $0.0021 · lenses 2 req`. In the interactive session, `/compact [instructions]` summarizes the older history now. On `claude-code`, a warning appears when the session is not using a Claude subscription.

Exit codes: `0` ok, `1` failed turn, `2` usage error, `130` interrupted.

When stdin and stdout are both terminals, the CLI reads the terminal in raw mode and turns on bracketed paste (`\e[?2004h`), and turns both off when it exits, Ctrl+C, SIGTERM and SIGHUP included (`\e[?2004l`; the last two exit 143 and 129). It takes the terminal over before the session starts, so anything typed while it starts counts as typed before a question. A pasted block, line breaks included, becomes one prompt that Enter sends. Line editing is Backspace, Ctrl+U (erase the line), Ctrl+W (erase a word) and Ctrl+D on an empty line (end the session); other keys are ignored.

A yes/no question (a `bash` approval or a review consent) only takes an answer typed after it appears: lines typed or pasted before it are dropped (a pasted block counts as one line), and the CLI says how many. An answer line that had pasted text in it, even a pasted `y` or a paste erased before typing `y`, is never a yes: the CLI prints `pasted text does not answer this question` and takes it as no. Ctrl+C interrupts the running turn (and answers no to a pending approval); with no turn running, or pressed twice, it closes the session.

## Desktop app

```bash
pnpm desktop            # dev mode with hot reload
pnpm -C atelier-desktop smoke   # build + Playwright smoke test (echo backend, no network)
```

Open a folder, pick a backend and a model, and chat. Each tool call shows as a row with its status; `bash` commands ask for approval in a card that shows invisible and control characters as visible markers. Every turn ends with a one-line summary of its tokens and cost that unfolds into the token breakdown and, when the turn had more than one part, one line per part (`main`, `declare`, `verify`, `lenses`, `refuter`, `correction`, `validator`) with its tokens, requests and cost; the status bar shows the core status, whether `bash` is sandboxed, warnings and the latest error; a command the sandbox stopped lists why under its row (see "Sandbox (macOS)"). If the core process dies, the app says so and offers a restart.

The desktop starts the core with Electron's own Node (no system Node needed) and talks to it over the Atelier protocol (version 5): one JSON message per line on stdin/stdout, a `hello` with the protocol version, an `id` on every command and exactly one response per command, and events tagged with their session. See `../docs/m2-diseno.md`.

## How it works

- The core emits plain-JSON `AtelierEvent`s; clients only render them. Every turn ends with exactly one `turn_finished`.
- `turn_finished` carries `phases`, the turn's cost by part: `main` (the main agent), `declare` (the request to declare the risk), `verify` (the verifier and its correction), `lenses`, `refuter`, `correction` and `validator`, each with `usage` and, when its backends report them, `requests` and `costUsd`. A part that did not run is absent (an on-demand `/review` has no `main`), and the parts add up to the turn's `usage`, `requests` and `costUsd`.
- The agent only has Atelier's tools: `read`, `edit`, `bash`, `grep`. The core executes them and owns approval. File tools are confined to the working directory; `bash` is not confined and is gated by approval instead.
- `ClaudeCodeBackend` drives Claude Code through the Claude Agent SDK, isolated from your `~/.claude` setup (no settings, hooks, plugins, skills, CLAUDE.md or other MCP servers) and without `ANTHROPIC_API_KEY`, so it uses your subscription.
- `AnthropicApiBackend` runs Atelier's own loop on the Messages API. It owns the prompt: tools and system prompt are fixed for the session, and three cache breakpoints (last tool, system, last message) keep the prefix cached. Each request asks the API to compare its prefix with the previous response, which is how cache misses are reported. See `../docs/m3-diseno.md`; a measured session is in `../docs/m3-medicion.md`.
- Subagents: the agent can delegate with a `task` tool to `explorer` (read and grep only, on the cheapest model: `haiku` / `claude-haiku-5-5`) or `worker` (read, edit, grep, bash, on the session's model). A subagent runs in its own session with only the task prompt and its role's instructions, on a fresh backend of the same kind. Only its final report, cut in code at 8,000 characters, returns to the parent. Its work shows nested under the task call: indented under `↳ agent · model` in the CLI, in a foldable block in the desktop, each with its own token line. Its bash commands ask for approval like any other. See `../docs/m4-diseno.md` and `../docs/m4-medicion.md`.
- ODD (Organic Driven Development) is core state, not prompt prose. For large work the agent keeps a feature document in `odd/tasks/<name>.md` (`## Specs`, `## Tasks`, `## Log`) through the `feature` tool, the only way to change it: `edit` refuses that directory. Atelier writes the log's user entries itself, verbatim (L1 is the original request), so the model never paraphrases you. Each change is validated and written as one transaction, so the document stays well formed. A later session resumes with `open`. The current phase (exploring, implementing, checking…) is inferred from the tools, or declared with the `phase` tool. The CLI prints `· <phase>` and `◆ <feature>: n/m done`; the desktop shows the phase in the status bar and the feature's tasks in a side panel. See `../docs/m5-diseno.md`, `../docs/m6-diseno.md`.
- Long-term memory (M6): with Engram 3.4.0 or newer installed, each session gets the project's memory (Engram resolves the project from the working directory). The agent searches and saves through the `memory` tool; a compact context of recent memory comes with the first message, outside the system prompt. Rules enforced in code: the user's prompts are never captured, anything shaped like a credential is refused, subagents get no memory, and a finished ODD feature is saved under `odd/<name>/tasks` without the user's verbatim messages. A save that Engram keeps but could not check for conflicting memories (`candidate_detection_status: "incomplete"`) is not retried: the tool's answer says `Saved memory #<id>. Warning: ...`, and a feature mirror sends a recoverable `memory_mirror_warning` error. Without Engram, sessions work and say why there is no memory (`memory: <project>` / `no memory: <reason>`); `ATELIER_MEMORY=off` turns it off. Only `atelier-core/src/memory/engram.ts` knows Engram, and a test enforces it. See `../docs/m6-diseno.md`.
- Review with receipts (M7, Receipt-Driven Development): at the end of a turn that changed a git repo, the core freezes the candidate: the worktree (tracked and untracked but not ignored) against the tree of the `HEAD` the turn started at, as two git trees built with a temporary index, so your index and worktree are never touched and commits made during the turn are part of the candidate. If `HEAD` no longer descends from the commit the turn started at (a reset or rebase), the base is the current `HEAD`; without a commit at the start of the turn (an empty repo) it is `HEAD` and derives its risk from the diff, with no model and no cost: `passive` (documentation only, 0 lenses), `medium` (1 lens, `reliability` unless the agent picks another with the `risk` tool) or `high` (4 lenses: `risk`, `resilience`, `readability`, `reliability`). High risk comes from paths (`auth`, `security`, `permission`, `payment`, `webhook`, `migration`, `secret`, `credential`), dependencies and environment files, and from the content of the added lines, following gentle-ai's method; the size of the change, the number of files and the model never count. Each signal is a named reason with its place: `shell_process: <path>:<line>` for a real process spawn (`spawn`, `exec`, `execFile`, `execSync`, `child_process`, `subprocess`, `popen`, `ProcessBuilder`, `os.system`, `proc_open`, `Process.Start`...; a member call such as `cp.exec(` or `childProcess.spawn(` counts only in a file that imports `child_process`, so `db.exec(` and `/re/.exec(` elsewhere are not spawns, and neither is `process.stdin.setRawMode`; spaces before the parenthesis do not hide a call) and `dangerous_sink: <path>:<line> (<sink>)` for a concrete sink: `eval`, `new Function`, disabled TLS validation, unsafe deserialization, shell commands composed from variables, `rm -rf`, `DROP TABLE`, `DELETE FROM`, world-writable modes, CSRF or JWT bypasses (the catalog is gentle-ai's, gated by language). A line that is only a comment in its file's language (`//`, `/* */`, `#`, `--`) is skipped, and so are the lines inside a block comment that an added line opens (code after its `*/` is scanned); a language Atelier does not know is never skipped. Only source, configuration and `.txt` files are scanned, never test files (`*.test.*`, `*.spec.*`, `__tests__`, `testdata`) or `docs/` and fixture folders, and only the first line of each kind per file is named. The scan fails closed: if the added bytes of scanned files pass 8 MiB the level is high with `process_scan_limit: <path>`. A change is `passive` only when every changed file is documentation proven by its content: an extension only nominates it, and a code fence, an interpreter line (`#!`), a `<script>` tag, MDX with imports, expressions or tags, binary content or text that is not UTF-8 make it not passive. Finally the level must be explained by its reasons (high needs a high reason, passive only `documentation only` over documentation files, medium none); if it is not, the level is high with a `tier_not_explained` reason. The agent's declaration can raise the level, never lower it. Following gentle-shell, the main agent closes every code change by declaring its risk with the `risk` tool: the high-risk items that apply (1 data that cannot be rebuilt or irreversible effects, 2 security, 3 contracts others consume, 4 concurrency, which includes asynchronous events or callbacks that can arrive in another order, turn or request than expected, interrupts and timeouts, races, shared mutable state and locks, 5 delivery or environment, 6 no test would catch a regression), each with a reason, or `none` with a reason (`{ "none": true, "reason": "..." }`). A declaration can only raise the level, never lower what the diff shows. If a code change reaches the end of the turn without a declaration, the core asks the agent once, inside the same turn, to declare it; if it still does not, the risk is not lowered (it stays at least `medium`) and the risk line says `no risk declaration`. A declaration covers only the turn it was made in: it is cleared when the next turn starts. If the agent edits, commits or resets while answering the request to declare, the candidate is frozen again (tree, base and base note are compared) and the new one is assessed. The `review_assessed` event carries the declaration (`declaration`: `items`, `none` or `missing`; absent for documentation) and the base when it is not the current `HEAD` (`since`: the short id of the commit the change is measured from, so the turn's commits are included; `baseNote`: why the base fell back to the current `HEAD`), and both clients show them: the CLI as `◇ review medium · 1 lens (...) · declared none: <reason> · since 1a2b3c4`, the desktop in the review block. A high-risk candidate is offered for review with a consent question (review / do not review this candidate; the CLI asks on a terminal, the desktop shows a card); `/review` in the CLI and the Review button in the desktop review any risk, without asking, against `HEAD`; `/review <ref>` in the CLI (`Session.review(turnId, base)` in the core) reviews the worktree against that git ref instead, and refuses an unknown one with `Unknown git ref "<ref>": there is nothing to review against.` (the desktop button takes no ref). A receipt is keyed by the candidate tree, so the same worktree state is not offered twice whatever its base. The lenses are read-only subagents on the session's model that read the frozen tree, never the live worktree, and a context over 200 KiB is refused, not truncated. Only `blocker` or `critical` findings caused by the candidate block; a refuter confirms or discards them once, the main agent makes one correction within `min(200, ⌈n/2⌉)` changed lines (at least 2, measured by the core), and a validator checks it. The verdict is `approved`, `escalated` (out of budget or unresolved: the correction stays in the worktree and nothing else is attempted), `declined` or `unavailable`. Every review leaves a JSON receipt in `<git-dir>/atelier/reviews/`, never in the worktree, and the same candidate is not offered twice. Approving never commits, pushes or opens a PR. Review is on by default; `--no-review` or `ATELIER_REVIEW=off` turns it off, and without git (or without a commit) it says why there is no review. See `../docs/m7-diseno.md`; measured runs are in `../docs/m7-medicion.md`.
- Independent verification (M9, following gentle-shell's `gentle-ai-verify`): when the agent's risk declaration for a turn names at least one high-risk item (1 to 6; `none`, no declaration, and a high risk that only the diff showed do not count), the core, not the model, runs a `verifier` role on the turn's frozen candidate at the end of the turn, before the review is assessed or offered. It is not asked for consent (the review keeps its consent), and `--no-review` / `ATELIER_REVIEW=off` turns verification off with the review. The verifier works in a temporary directory (`atelier-verify-*` in the system temp folder) that holds `candidate/` and `base/`, both written from the frozen git trees with `git cat-file`, so your worktree, index and refs are never touched and no attribute or filter of the repository runs. Installed dependencies are made usable without installing and without sharing them with your project: every `node_modules` of the worktree (the root's and each workspace package's) is copied into both copies (a copy-on-write clone with `cp -c` on macOS, `cp --reflink=auto` on Linux, a plain recursive copy otherwise; links stay links, files are new ones, so a hard link to the pnpm store is broken). A symbolic link in the copies that points into your project is re-pointed at the same place of the copy, so the candidate's tests run the candidate's code, and one that points anywhere else is removed (the verifier is told how many). More than 4 GiB of dependencies, more than 120 seconds of copying, or a failed copy leaves the copies with no dependencies, and the verifier is told and marks those requirements unverified; so does a project without any. What the verifier's `bash` writes in `node_modules` stays in the copy. Its `bash` is confined by the sandbox (see "Sandbox (macOS)"): it writes only this directory and has no network; without a sandbox it gets no `bash`. The copy is removed when the verification ends, also on error or interrupt. The verifier has `read`, `grep` and `bash` with that directory as working directory; its `bash` runs without asking (only there) with the same filtered environment as the agent's `bash`, plus variables that make package managers refuse to install or fetch (`npm_config_offline`, `pnpm_config_offline`, an unreachable `npm_config_registry`, `npm_config_manage_package_manager_versions=false`, `NO_UPDATE_NOTIFIER`, `COREPACK_ENABLE_NETWORK=0`, `YARN_ENABLE_NETWORK=0`, `PIP_NO_INDEX`, `CARGO_NET_OFFLINE`, `GOPROXY=off`); its mandate also forbids installing and using the network, and caps it at 80 model requests per run. It receives the user's request for the turn verbatim, a copy of the active ODD feature document (`feature/<name>.md`), the agent's declaration and a summary of base vs candidate, and must derive the requirements, run probes (including hostile input aimed at what the declared item protects), reproduce every defect on `candidate/` and on `base/` (a defect that also happens on the base is advisory), and answer one JSON report: a verdict per requirement (`met`, `unmet`, `unverified`, with evidence) and the defects (`blocker`, `major` or `minor`, with reproduction, behavior on the candidate and on the base, `onBase`). A reply that is not a complete report (including one with no requirements) is a failed verifier, never a pass. A requirement judged `unmet` counts as a blocker even without a defect. Blocker or major defects that are not on the base, and unmet requirements (as `R1 [blocker] Requirement not met: ...`, with the verifier's evidence), go to the main agent once, inside the same turn, as a correction request; the candidate is frozen again and the verifier runs a second time. There are at most two rounds. It passes only when every requirement is `met` and no blocking defect is left; a requirement still `unverified` ends it with "needs your decision" and the list of them, never as a pass. If blocking defects remain after round 2, or the verifier failed, the turn ends with a visible "needs your decision" and the open defects; it does not loop. The review then continues on the final candidate as usual. Events: `verification_started` (`verifyId`, `items`, `declaration`), `verification_round` (`round`, `ok`/`error`, `requirements`, `defects`, `blocking`, `correcting`, `usage`, `costUsd`) and `verification_finished` (`outcome`: `passed`, `corrected`, `needs_decision` or `failed`; `reason`, `rounds`, `openDefects`, `usage`, `costUsd`); the verifier's own events are tagged `agent: "verify:verifier"` under `verifyId`, and its cost (and the correction's) is added to the turn's `turn_finished`. The CLI prints `◇ verifying · item 2`, `◇ verify · round 1 · 2 defects (blocker, major) · asking the agent to fix them`, `✓ verify passed`, `✓ verify passed after a correction · 2 rounds`, `✗ verify: needs your decision · 1 open defect` (followed by each defect and its reproduction), `✗ verify: needs your decision · 1 unverified requirement: R1 ...` and `✗ verify failed: <reason> · needs your decision`; the desktop shows a verification block with the declared items, each round's verdicts and defects, and the outcome. See `../docs/m9-diseno.md`.
- Project instructions: at session start the core walks up from the working directory (`--cwd`) through every parent folder, stopping before the user's home folder (or at the disk root if the folder is not under it), and takes `AGENTS.md` from each folder, or `CLAUDE.md` when there is no `AGENTS.md`. Before them comes the user's own `~/.agents/AGENTS.md`, if there is one, as `User instructions from <path>:`. The files are appended to the main session's system prompt from the outermost folder to the closest, each preceded by `Project instructions from <path>:`, so the closest comes last and wins a contradiction. It works the same on `anthropic-api` and `claude-code`, and the files are read once, at start (editing them later does not change the running session, which keeps the prompt prefix cache intact). The total is capped at 32 KiB: over it, the outermost files are dropped first, the user's file before any project file. The first turn reports `instructions: <paths>` and, if the cap left files out, the warning `instructions over 32 KiB, left out: <paths>`; the desktop shows both in the status bar. Subagents do not get them: they keep only their task and role instructions. There is no stop at the git root, so running in `atelier/` also reads `../AGENTS.md`.
- Context compaction (M8): a long session no longer ends in a context error. On `anthropic-api`, before each model request the core compares the context (the last response's real usage plus an estimate of what was appended since) with `min(window − (max output + 16,384), 200,000)` tokens, the window coming from the models API (200,000 when it does not answer); `ATELIER_COMPACT_AT=<n>` replaces the 200,000 cap, but never goes past the window minus the reserve. Crossing it, the core asks the session's model for a summary in a fixed format (Goal, Constraints & Preferences, Progress, Key Decisions, Next Steps, Critical Context), with the session's own prefix so it reads from the prompt cache, and replaces the older history with one message: the summary, the files read and edited (from the tool calls, not from the model), the current turn's request verbatim when it was summarized, and once the core's state (active ODD feature and task, phase, the memory of the first turn). The last ~20,000 tokens stay verbatim and a tool result never loses its call. A summary that is empty, cut short or missing a section is refused and the history stays as it was; a context overflow compacts once and retries the request. Claude Code compacts on its own: Atelier shows its compactions, forwards `/compact`, and gives the core's state with the next prompt. Both clients show the compaction (before → after, messages kept, cost), mark the cache miss that follows it as expected, show how full the context is, and accept `/compact [instructions]`. Subagents are not compacted. See `../docs/m8-diseno.md`; measured runs are in `../docs/m8-medicion.md`.
- `bash` runs without `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`. That only filters its environment; the isolation is the macOS sandbox described in "Sandbox (macOS)" below. Keep approvals on (no `--yes`) for work you do not trust.

Design and decisions: `../docs/m1-diseno.md`, `../docs/m2-diseno.md`, `../docs/m3-diseno.md`, `../docs/m4-diseno.md`, `../docs/m5-diseno.md`, `../docs/m6-diseno.md`, `../docs/m7-diseno.md`, `../docs/m8-diseno.md`, `../docs/m10-diseno.md`.

## Sandbox (macOS)

On macOS every `bash` command of the agent, its workers and the verifier runs under the operating system's sandbox (Seatbelt, through `@anthropic-ai/sandbox-runtime` 0.0.81). It is built for macOS only: elsewhere, or if `sandbox-exec` does not answer, there is no sandbox and the commands fall back to approvals (see below). Design: `../docs/m10-diseno.md`.

### What is isolated and what is not

|         | Agent and workers                                                                                                                                                                                                                                                                                     | Verifier                                                                                                                                                                                                                                                |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writes  | the working directory, the system temporary directory, the session scratch directory and the package managers' caches under your home (`~/.npm`, `~/Library/pnpm`, `~/.local/share/pnpm`, `~/.pnpm-store`, `~/.yarn`, `~/.node-gyp`, `~/.cache`, `~/Library/Caches`), never the home directory itself | only its own temporary directory                                                                                                                                                                                                                        |
| Reads   | everything except `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` and `~/.claude`                                                                                                                                                                                               | only its directory, the Node installation and the system toolchain (`/usr`, `/bin`, `/sbin`, `/System`, `/etc`, `/dev`, `/opt/homebrew`, `/Library/Apple/usr`, `/Library/Frameworks`); `/Library/Keychains` and the rest of `/Library` are not readable |
| Network | free, as in gentle-shell                                                                                                                                                                                                                                                                              | none                                                                                                                                                                                                                                                    |

In the working directory the agent never writes `.env`, `.env.*`, `*.pem`, `*.key`, the git hooks and configuration, shell start-up files and editor or tool configuration (`.git/hooks`, `.git/config`, `.gitconfig`, `.gitmodules`, `.bashrc`, `.bash_profile`, `.zshrc`, `.zprofile`, `.profile`, `.ripgreprc`, `.mcp.json`, `.vscode`, `.idea`, `.claude/commands`, `.claude/agents`), nor `.atelier`.

Not covered:
- The agent's network is not restricted: a command can reach the network and anything it can read.
- Other platforms: no Linux or Windows code exists.
- The `read`, `edit` and `grep` tools are not run by the sandbox; they are confined to `--cwd` by code, which is a separate mechanism.
- `bash` also runs without `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`; that filters its environment and is not isolation.

### What you see

At the start of a session (in its first turn) the core emits `{ type: "sandbox_status", sandboxed: boolean, mechanism?: string, reason?: string }`, computed without running a command. The CLI prints `bash: sandboxed (macOS seatbelt)` on stdout, or `bash: not sandboxed (<reason>): every command asks for approval and --yes does not apply` on stderr. The desktop shows `bash: sandboxed (macOS seatbelt)` in the status bar, or `bash: not sandboxed` in the warning style with the reason as its tooltip. Subagents do not repeat it.

When a command that failed was blocked by the sandbox, its result says what it tried and why it was stopped, after the exit code:

```
[exit code 1]
[sandbox blocked: write to /Users/ana/notes.txt (not an allowed write path)]
[sandbox blocked: read of /Users/ana/.ssh/id_rsa (denied by the sandbox policy)]
[sandbox blocked: network connect to 127.0.0.1:8080 (no network for the verifier)]
```

The causes come from the sandbox library's own violation report, nothing is guessed: if it reports nothing, nothing is added. At most five causes are listed (then `[sandbox blocked: and N more]`), network first, then writes, then reads; the system's own preference reads are left out. The output truncation rules are unchanged. `tool_call_finished` carries the same causes as `blocked: string[]`; the CLI prints them under the tool line as `  sandbox blocked: <cause>`, and the desktop shows them in the tool row. Limits: only a command that failed is asked; each run is given its own id and the library records its denials under it, so a cause is shown only for the run that produced it, never for an overlapping run of the same text, and a denial the library could not attribute to a run is not shown; and the file denials come from the system log, which can lag, so a block in the first seconds of a session may go unreported.

### Approvals and `--yes`

A command that runs in the sandbox asks for approval as always, and `--yes` approves it. `--yes` approves only what runs sandboxed.

The `bash` tool has two optional inputs, `unsandboxed: true` and a required `reason`, with which the agent asks to leave the sandbox for one command (for example to install dependencies with network access). The user is always asked, even with `--yes`, and sees the reason (CLI: `Run this command OUTSIDE the sandbox?`, then the command and `reason: ...`; desktop: a card titled `Run this command outside the sandbox?` that shows the reason; the `approval_requested` event carries `reason`). Without a terminal the CLI refuses it (`bash command asks to run outside the sandbox and needs your approval, but there is no terminal to ask (--yes does not allow this): <command>`, then `reason: <reason>`). A missing or blank `reason` is `Invalid input: reason is required with unsandboxed: ...`, and the verifier's `bash` refuses it (`Refused: the verifier's bash cannot run outside the sandbox — <command>`).

Without a sandbox (another platform, a sandbox that fails to start, `--no-sandbox` or `ATELIER_SANDBOX=off`; `SessionOptions.noSandbox` for other clients) every command asks even with `--yes`, and the verifier gets no `bash`. The core emits `{ type: "sandbox_warning", reason }` once per turn, before the first question of the turn that runs `bash`. The CLI prints `warning: bash runs without a sandbox (<reason>): every command asks for approval and --yes does not apply` on stderr, except in the turn whose start already printed the `bash: not sandboxed` line (one line, not two); the desktop shows it in the turn, as `bash runs without a sandbox (<reason>): every command asks for approval and --yes does not apply`. Without a terminal the CLI denies such a command and says `--yes does not apply because the sandbox is off or unavailable`.

### Turning it off

`--no-sandbox` or `ATELIER_SANDBOX=off` runs `bash` without the sandbox, with the behavior above. `atelier-core serve` honors `ATELIER_SANDBOX=off` for every session, and `session.start` accepts `noSandbox: true` for one session (that is how a client such as the desktop starts one without it). With the sandbox off the configuration files below are not read or validated.

### Commands that are always refused

Before the sandbox and before any approval question, even with `--yes`, for every caller (the agent, its workers and the verifier), following gentle-shell's destructive command guard: recursive removal (`rm -r`) of `/`, of `~` or `$HOME`, or of the project directory (or a directory that contains it, `.` and `./*` included), and a `find` from one of those places that removes everything it finds (`-delete` or `-exec rm ... {}` with no test that narrows the selection, so `find . -name '*.log' -delete` still runs); `mkfs*`; `dd` with `of=/dev/...` (not `/dev/null`, `/dev/stdout`, `/dev/stderr`, `/dev/tty`); fork bombs (`:(){ :|:& };:` and any function that pipes itself into itself in the background); recursive `chmod`/`chown` on `/`; and `sudo` and `su` as a command of any segment (also behind `env` and `env -S "..."`, `nohup`, `timeout`, `xargs`, `sh -c`, `eval`, `find -exec`, `$(...)`, backticks and redirections written before the command). The tool result is `Refused: <rule> — <command>` (the rules are `recursive removal of /`, `recursive removal of the home directory`, `recursive removal of the project directory`, `mkfs`, `dd to a device`, `fork bomb`, `recursive chmod/chown on /`, `sudo`, `su`) and nobody is asked.

It only knows recognizable forms: text in quotes or in a heredoc is data, and it does not read pipes (`echo / | xargs rm -rf`), heredocs passed to a shell, redirections to a device, a bare `*`, or scripts. What it does not recognize is not refused by it; the sandbox is the next layer.

### Configuration files

Two optional files add to the agent's policy and never to the verifier's: `~/.atelier/sandbox.json` (yours) and `<cwd>/.atelier/sandbox.json` (the project's), each `{ "allowWrite"?: string[], "denyRead"?: string[] }`. A path is absolute, `~/...`, or relative to the file's base (your home for yours, the working directory for the project's). The files only add, and never remove a fixed protection. An `allowWrite` entry that is, contains or lies inside a protected place (your home itself, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains`, `~/.claude`, `~/.atelier`; so `~`, `/` and any parent of home too, also through a symbolic link) is refused, and the secret file patterns and the git and shell files above also hold inside every added directory.

A file that is invalid (not JSON, not an object, an unknown key, a value that is not an array of non-empty strings, a refused entry) stops the CLI before anything runs (exit 1, `error: Invalid sandbox configuration <file>: <problem>`) and fails `session.start` of `atelier-core serve` (`session_start_failed`, same message). A file that becomes invalid later makes each `bash` command fail with `[sandbox error: Invalid sandbox configuration <file>: <problem>]` and run nothing. It is never ignored, because that would silently widen or narrow what commands can do.

**Caveat:** the project file lives in the repository, so a repository you do not control can ship one that makes more places writable for the agent, everywhere except your home directory itself, the protected places above and `~/.atelier`. Read it before you trust the project.

### Running as root

As root (uid 0), the CLI and `atelier-core serve` refuse to start (exit 1) unless `ATELIER_ALLOW_ROOT` is exactly `I accept the risk`: `error: Atelier will not run as root (uid 0): a mistaken command could damage the whole system. To run as root anyway, set ATELIER_ALLOW_ROOT="I accept the risk" (exactly that text).`, plus `ATELIER_ALLOW_ROOT is set to "<value>", which is not that exact text.` when it is set to something else. With the exact text they start and print `warning: running as root (uid 0) because ATELIER_ALLOW_ROOT is set: every command has full control of this system.` on every start (the server prefixes both with `atelier-core: ` on stderr). `--help` and `--version` still work as root.

### Known limits

- `git config` and `git branch -u` fail inside `bash` (the library protects `.git/config`).
- Git state that git acts on later stays writable in the project's `.git` (and in a linked worktree's own git directory): for example the `exec` lines of a rebase in progress (`rebase-merge/git-rebase-todo`), which a `git rebase --continue` you run outside Atelier would execute. Check a rebase you did not start yourself before continuing it.
- In a linked git worktree (`git worktree add`), whose git data lives in the main checkout's `.git`, the agent may also write that worktree's own directory there (`.git/worktrees/<name>`) and the repository's `objects`, `refs`, `logs`, `packed-refs`, `packed-refs.lock` and `packed-refs.new`, so branches, commits and packing refs work without leaving the sandbox. What would make git run code or work on another repository stays protected: the shared `hooks` (and the hooks directory git actually runs, `core.hooksPath` included, as `git rev-parse --git-path hooks` reports it), `config` and `config.worktree`, `objects/info` (alternates), and the worktree's own `config.worktree` (a `core.hooksPath` there would run a hook the next time you commit, outside the sandbox), `commondir`, `gitdir` and `hooks`; the secret file patterns hold in those directories too, and nothing else of the main checkout becomes writable. `git gc` and `git repack`, which update `objects/info`, need to leave the sandbox. The worktree's git directories are asked from `git rev-parse` once per working directory and checked against the files git keeps for a worktree (its directory must be `<common>/worktrees/<name>`, and its `gitdir` file must point back at the worktree), so a tampered `commondir` grants nothing.
- The verifier's `git` is the real one of the active developer directory (found once with `xcrun --find git`), first on its `PATH`, with that directory's `usr/` readable and no system or global git configuration (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`): the `/usr/bin/git` shim cannot run there, because it writes a cache in your per-user temporary folder. Its commands also get `TMPDIR` inside its own directory (`<dir>/.tmp`), set in the command, so tests that create temporary directories work, and a `HOME` of their own (`<dir>/.home`, with `XDG_CONFIG_HOME` under it), because your home is not readable and tools such as git read their configuration from home even when a caller clears the `GIT_*` variables; the library's own `/tmp/claude` stays writable but the verifier cannot read `/tmp`. It also reads `/private/var/select`, where macOS records the shell `/bin/sh` runs and the developer directory. Without a developer directory the verifier has no `git`. Atelier's own suite passes inside the verifier's sandbox, apart from the tests that need a real sandbox, which are skipped there.
- Each command costs about 16 ms more (about 63 ms the first one).
- macOS cannot nest sandboxes. An Atelier that already runs inside one (Atelier running its own tests from a sandboxed command) finds out by trying the smallest sandbox there is and reads macOS's refusal; it then reports `already inside a sandbox, and macOS cannot nest them: commands stay confined by the outer one` and takes the unavailable path (every command asks, the verifier gets no `bash`). Nothing in the environment can claim this. The tests that need a real sandbox are skipped there and run in a normal `pnpm check`.
- The library is "Beta Research Preview" and global to the process; the sandbox is not reset until the process exits.

## Working on Atelier with Atelier

Changing Atelier with the Atelier you are changing breaks the tool in the middle of the work. Keep a stable copy as the tool and the repository as the workpiece:

```
atelier/          the workpiece: feat/* branches, where the agent edits
atelier-stable/   the tool: a worktree pinned to a stable-* tag, never edited
```

```bash
# once: pin the copy that works today
git tag -a stable-m8 -m "Stable Atelier"
git worktree add --detach ../atelier-stable stable-m8
pnpm -C ../atelier-stable install

# use it on the workpiece (or on any other project)
alias atelier-stable='node /path/to/atelier-stable/atelier-cli/src/main.ts'
atelier-stable --cwd /path/to/atelier
pnpm -C ../atelier-stable desktop   # the desktop starts the stable copy's own core
```

- `read` and `edit` cannot leave `--cwd`, so they never touch the stable copy. `bash` is not isolated: keep approvals on (no `--yes`) when the workpiece is Atelier itself.
- To try a change for real, run the workpiece's CLI (`pnpm atelier` inside `atelier/`) in another terminal; the stable copy stays in charge of the work.
- Memory (Engram resolves the project from the working directory), review receipts (in the workpiece's `.git`) and the API key are shared on purpose.

Promote only what is verified: once a branch is merged into `main` with `pnpm check`, the desktop smoke and a real run green, tag it and move the copy. To go back, check out the previous tag.

```bash
git tag -a stable-m9 -m "Stable Atelier"
git -C ../atelier-stable checkout --detach stable-m9 && pnpm -C ../atelier-stable install
```
