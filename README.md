# Atelier

Coding-agent orchestrator with two first-class clients, a CLI and a desktop app, on top of one headless core.

| Package            | Directory          | Status                                                                                                           |
| ------------------ | ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `@atelier/core`    | `atelier-core/`    | Event contract, session, tools, subagents, protocol server; backends `claude-code` (M1) and `anthropic-api` (M3) |
| `@atelier/cli`     | `atelier-cli/`     | `atelier` command                                                                                                |
| `@atelier/desktop` | `atelier-desktop/` | Desktop chat app (M2)                                                                                            |

## Requirements

- Node 22.18+ (TypeScript runs natively; there is no build step) and pnpm.
- For the default `claude-code` backend: Claude Code logged in with your Claude subscription (run `claude` and use `/login`).
- For the `anthropic-api` backend: an Anthropic API key with credit, stored once in the macOS Keychain. The command asks for the key, so it stays out of your shell history:

  ```bash
  security add-generic-password -U -s atelier-anthropic -a "$USER" -w
  ```

  `ANTHROPIC_API_KEY` set for a single command takes priority. Do not export it in your shell profile: Claude Code would then bill the API instead of your subscription.

## Usage

```bash
pnpm install
pnpm atelier "add email validation to src/user.ts and run the tests"   # one turn
pnpm atelier                                                          # interactive; /exit or Ctrl+D to quit
```

| Option                             | Effect                                                                                                           |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `-y`, `--yes`                      | Run `bash` commands that run sandboxed without asking (not the others, see below).                               |
| `--backend <name>`                 | `claude-code` (default, Claude subscription) or `anthropic-api` (Atelier's own loop, billed to the API key).     |
| `--model <name>`                   | Model to use (default: `opus` on `claude-code`, `claude-sonnet-5-5` on `anthropic-api`).                         |
| `--profile <name>`                 | Agent profile for this session (see "Agent profiles"); `--model` and `--backend` still replace the main agent's. |
| `--cwd <dir>`                      | Working directory (default: current directory).                                                                  |
| `--no-review`                      | Do not review changes or verify them (same as `ATELIER_REVIEW=off`).                                             |
| `--no-sandbox`                     | Run `bash` without the macOS sandbox (same as `ATELIER_SANDBOX=off`).                                            |
| `-h`, `--help` / `-v`, `--version` | Help and version.                                                                                                |

Output starts with the main agent's header, `atelier · <backend> · <model> · <auth>`, plus `· effort <level>` when a thinking level was asked, and a line with the session's profile (repeated with every header): `profile cheap (local-pin) · verifier claude-code/claude-sonnet-5-5 thinking medium`, its name, the layer it came from and what it sets for each role but the main agent, or `profile default` when none applies. Then streamed text, one line per tool call (`▸ edit src/user.ts (1 edit) ✓`) and the turn's tokens: input, output, cache reads and writes, the share of the prompt served from the cache (`cacheRead / (input + cacheRead + cacheWrite)`), the number of model requests and the cost. A `cache miss` line says why the prompt cache could not be reused. When the backend reports it, the tokens line also says how full the context is (`context 45,000 / 200,000 (23%)`). A turn with more than one part (the main agent plus the risk declaration, the verifier or a review) gets a compact line under it with each part's cost and requests, or its tokens when neither is known: `phases: main $0.0400 (1 req) · verify $0.0021 · lenses 2 req`. In the interactive session, `/compact [instructions]` summarizes the older history now. On `claude-code`, a warning appears when the session is not using a Claude subscription.

Exit codes: `0` ok, `1` failed turn, `2` usage error, `130` interrupted.

When stdin and stdout are both terminals, the CLI reads the terminal in raw mode and turns on bracketed paste (`\e[?2004h`), and turns both off when it exits, Ctrl+C, SIGTERM and SIGHUP included (`\e[?2004l`; the last two exit 143 and 129). It takes the terminal over before the session starts, so anything typed while it starts counts as typed before a question. A pasted block, line breaks included, becomes one prompt that Enter sends. Line editing is Backspace, Ctrl+U (erase the line), Ctrl+W (erase a word) and Ctrl+D on an empty line (end the session); other keys are ignored.

A `write` outside `--cwd` asks `Write a file outside the working directory?` the same way (row: `▸ write src/new.ts (120 bytes) ✓`), and without a terminal the CLI refuses it (`write asks to create or replace a file outside the working directory and needs your approval, but there is no terminal to ask (--yes does not allow this): <path>`) and writes nothing. An `edit` of a file outside `--cwd` asks `Edit a file outside the working directory?` and shows the real absolute path; `--yes` does not answer it, and without a terminal the CLI refuses it (`edit asks to change a file outside the working directory and needs your approval, but there is no terminal to ask (--yes does not allow this): <path>`) and leaves the file alone. A yes/no question (a `bash`, `edit` or `write` approval or a review consent) only takes an answer typed after it appears: lines typed or pasted before it are dropped (a pasted block counts as one line), and the CLI says how many. An answer line that had pasted text in it, even a pasted `y` or a paste erased before typing `y`, is never a yes: the CLI prints `pasted text does not answer this question` and takes it as no. Ctrl+C interrupts the running turn (and answers no to a pending approval); with no turn running, or pressed twice, it closes the session.

## Desktop app

```bash
pnpm desktop            # dev mode with hot reload
pnpm -C atelier-desktop smoke   # build + Playwright smoke test (echo backend, no network)
```

Open a folder, pick a backend and a model, and chat. When `~/.atelier/profiles.json` has profiles, a `profile` selector lists them (asked with `profiles.list` each time the core is ready): `by layers (active: <name>)` lets the core resolve it, and a name is sent as `session.start.profile` for the next session; a chosen name the core no longer lists (after a restart, or when the list fails) goes back to `by layers`, so what the selector shows is what is sent; the backend and model pickers are still sent, so they replace the orchestrator's. The status bar shows the model with its effort (`opus · effort high`) and the session's profile (`profile: cheap (repo)`, or `profile: default`; kept when a later `session_started` carries none), with what it sets for each role in its tooltip. Each tool call shows as a row with its status; `bash` commands ask for approval in a card that shows invisible and control characters as visible markers; an `edit` of a file outside the working directory asks in the same card (`Edit a file outside the working directory?`, with `edit <absolute path>`; a `write` asks as `Write a file outside the working directory?`, with `write <absolute path>`). Every turn ends with a one-line summary of its tokens and cost that unfolds into the token breakdown and, when the turn had more than one part, one line per part (`main`, `declare`, `verify`, `lenses`, `refuter`, `correction`, `validator`) with its tokens, requests and cost; the status bar shows the core status, whether `bash` is sandboxed, warnings and the latest error; a command the sandbox stopped lists why under its row (see "Sandbox (macOS)"). If the core process dies, the app says so and offers a restart.

The desktop starts the core with Electron's own Node (no system Node needed) and talks to it over the Atelier protocol (version 5): one JSON message per line on stdin/stdout, a `hello` with the protocol version, an `id` on every command and exactly one response per command, and events tagged with their session. See `../docs/m2-diseno.md`.

## How it works

- The core emits plain-JSON `AtelierEvent`s; clients only render them. Every turn ends with exactly one `turn_finished`.
- `turn_finished` carries `phases`, the turn's cost by part: `main` (the main agent), `declare` (the request to declare the risk), `verify` (the verifier and its correction), `lenses`, `refuter`, `correction` and `validator`, each with `usage` and, when its backends report them, `requests` and `costUsd`. Each part also lists in `agents` who ran in it, once each in the order they first ran: the profile role (`orchestrator` for the main agent in `main`, `declare`, `correction` and the correction inside `verify`; `verifier`; `review-risk`, `review-resilience`, `review-readability`, `review-reliability`, `review-refuter`, `review-validator`), and the `backend`, `model` and `effort` that agent's `session_started` said (`effort` absent when no level was asked); `agents` is absent when no agent of the part said `session_started`. A part that did not run is absent (an on-demand `/review` has no `main`), and the parts add up to the turn's `usage`, `requests` and `costUsd`.
- The agent only has Atelier's tools: `read`, `edit`, `write`, `bash`, `grep`. The core executes them and owns approval. `read` and `grep` of the main agent and its workers open any path, absolute or `../`, except the protected secret locations (the home's secret directories and the `denyRead` entries of the sandbox configuration, the same list the sandbox hides from `bash`; a symbolic link into one is refused too, with `Path is a protected secret location: <path>`; `grep` skips them while walking, and drops any match whose real path is one, whatever the glob or the file name). This holds with the sandbox off or unavailable. `edit` writes without asking in the working directory, the session's scratch directory and the `allowWrite` directories of the sandbox configuration. `write` (`path`, `content`) creates a file, or replaces an existing one whole keeping its mode (a new file is `0644`), and creates the missing folders only after the gate; use `edit` to change part of a file that exists and `write` to create one or replace it entirely. It follows `edit`'s policy: the same places without asking, and anywhere else the same approval, with `{ command: "write <path>", reason: "outside the working directory", tool: "write" }` (`always: true`), shared with `edit` (a file approved for one is allowed for the other, for the rest of the session). The content is capped at 1 MiB (1,048,576 bytes of UTF-8): over it the answer is `Not written: the content is <n> bytes and write takes at most 1048576 (1 MiB); write the file in parts or generate it with bash.` and nothing is written. `edit` and `write` share one path policy, compared by real path as well as by name (a link or a move gives a file no other name): a symbolic link to a missing file, or a folder on the way that is one, is refused without asking (`Not written: <path> is a symbolic link to a missing file.`, `Not edited: ...` for `edit`), and the protected places (secret directories and files, `.atelier/`, `odd/tasks/`, git state) are compared folding letter case and Unicode form, on any filesystem; the approval covers that one real path, and if the path leads elsewhere when the write happens the call is refused (`Not written: <path> led to <approved> when the user was asked, but now leads to <now>.`, `Not edited: ...` for `edit`). Both also refuse, without asking, the files the sandbox denies `bash` because git runs code from them (`.git/hooks`, `.git/config`, `.gitconfig`, `.gitmodules`, the pending steps of a rebase or cherry-pick, and what git reports for the repository of the working directory, wherever its git directory is: the hooks directory git runs, `core.hooksPath` included, in a main checkout too, the `config` and `config.worktree` of the git directory and of the shared one, the files they include, `info/attributes`, `modules/` and the `.git` file of a linked worktree; a subdirectory of a repository protects the repository's `.git` too): `<path> is git state that runs code: the agent does not write it.` `edit` also refuses the project's `.atelier/` (`<path> is project configuration: the agent does not write .atelier/.`) and the feature documents, whatever name or link reaches them. `write` also refuses, without asking, the feature documents (`<path> is a feature document: change it with the feature tool, not write.`) and the project's `.atelier/` (`<path> is project configuration: the agent does not write .atelier/.`); a denial answers `Not written: <path> is outside the working directory and the user did not approve writing it.` The main agent and the `worker` have it; the explorer, the review roles and the verifier do not. For `edit`, anywhere else it asks for approval showing the real absolute path (symbolic links resolved): the `approval_requested` event is `{ command: "edit <path>", reason: "outside the working directory", tool: "edit" }` (`tool` is optional and absent for `bash`; `ApprovalRequest` carries it too, with `always: true`). `--yes` does not answer it. Once approved, that exact file stays allowed for the rest of the session (not its directory, and not in another session; a worker subagent asks the same user through the same channel, and its approvals last as long as that worker). If the user denies, or nobody can be asked, the file is left untouched and the tool answers `Not edited: <path> is outside the working directory and the user did not approve editing it.` The file written is the approved real path: if a link changed since the question, the edit is refused. `edit` never writes the home's secret directories or `~/.atelier` (`Path is a protected secret location: <path>`), nor outside the working directory a `.env`, `.env.*`, `*.pem` or `*.key` file, approved or not, and nobody is asked. `bash` is not confined and is gated by approval instead. The review roles and the verifier keep `read` and `grep` inside the frozen tree or their own directory. The shared system prompt says so too: `Paths are relative to the working directory; read and grep also take absolute and ../ paths outside it (except the user's secrets), and edit and write outside it ask for approval. Use edit to change a file that exists and write to create one or replace it whole.`, so the agent reads another folder with `read` instead of `bash`.
- `ClaudeCodeBackend` drives Claude Code through the Claude Agent SDK, isolated from your `~/.claude` setup (no settings, hooks, plugins, skills, CLAUDE.md or other MCP servers) and without `ANTHROPIC_API_KEY`, so it uses your subscription.
- `AnthropicApiBackend` runs Atelier's own loop on the Messages API. It owns the prompt: tools and system prompt are fixed for the session, and three cache breakpoints (last tool, system, last message) keep the prefix cached. Each request asks the API to compare its prefix with the previous response, which is how cache misses are reported. See `../docs/m3-diseno.md`; a measured session is in `../docs/m3-medicion.md`.
- Subagents: the agent can delegate with a `task` tool to `explorer` (read and grep only, on the cheapest model: `haiku` / `claude-haiku-5-5`) or `worker` (read, edit, write, grep, bash, on the session's model). A subagent runs in its own session with only the task prompt and its role's instructions, on a fresh backend of the same kind. Only its final report, cut in code at 8,000 characters, returns to the parent. Its work shows nested under the task call: indented under `↳ agent · model` in the CLI, in a foldable block in the desktop, each with its own token line. Its bash commands ask for approval like any other. See `../docs/m4-diseno.md` and `../docs/m4-medicion.md`.
- ODD (Organic Driven Development) is core state, not prompt prose. A small task takes the small path from gentle-shell: the agent reads only what it changes and its helpers, in one batch, and runs the focused test and the suite in one command. For large work the agent keeps a feature document in `odd/tasks/<name>.md` (`## Specs`, `## Tasks`, `## Log`) through the `feature` tool, the only way to change it: `edit` and `write` refuse that directory. Atelier writes the log's user entries itself, verbatim (L1 is the original request), so the model never paraphrases you. Each change is validated and written as one transaction, so the document stays well formed. A later session resumes with `open`. The current phase (exploring, implementing, checking…) is inferred from the tools (`edit` and `write` mean implementing), or declared with the `phase` tool. The CLI prints `· <phase>` and `◆ <feature>: n/m done`; the desktop shows the phase in the status bar and the feature's tasks in a side panel. See `../docs/m5-diseno.md`, `../docs/m6-diseno.md`.
- Long-term memory (M6): with Engram 3.4.0 or newer installed, each session gets the project's memory (Engram resolves the project from the working directory). The agent searches and saves through the `memory` tool; a compact context of recent memory comes with the first message, outside the system prompt. Rules enforced in code: the user's prompts are never captured, anything shaped like a credential is refused, subagents get no memory, and a finished ODD feature is saved under `odd/<name>/tasks` without the user's verbatim messages. A save that Engram keeps but could not check for conflicting memories (`candidate_detection_status: "incomplete"`) is not retried: the tool's answer says `Saved memory #<id>. Warning: ...`, and a feature mirror sends a recoverable `memory_mirror_warning` error. Each compaction that succeeds, on either backend (threshold, overflow or `/compact`), saves its summary as a `session_summary` titled `Session summary: <project>, <YYYY-MM-DD>` under the key `session/<id>/summary`, one per session, so later compactions of the same session update it; the turn waits for the save, and a summary shaped like a credential (`memory_summary_skipped`), a failed save (`memory_summary_failed`) or a save with a warning (`memory_summary_warning`) is a recoverable error, never retried. Without Engram, sessions work and say why there is no memory (`memory: <project>` / `no memory: <reason>`); `ATELIER_MEMORY=off` turns it off. Only `atelier-core/src/memory/engram.ts` knows Engram, and a test enforces it. See `../docs/m6-diseno.md`.
- Review with receipts (M7, Receipt-Driven Development): at the end of a turn that changed a git repo, the core freezes the candidate: the worktree (tracked and untracked but not ignored) against the tree of the `HEAD` the turn started at, as two git trees built with a temporary index, so your index and worktree are never touched and commits made during the turn are part of the candidate. If `HEAD` no longer descends from the commit the turn started at (a reset or rebase), the base is the current `HEAD`; without a commit at the start of the turn (an empty repo) it is the empty tree, so the turn's first commit and everything after it are the candidate; if the turn brought in history it did not write (a `git pull`, a checkout of an existing branch), HEAD's reflog shows it and the base is where HEAD landed after that, or the current `HEAD` without a reflog, so other people's commits are never the candidate (while the repo still has no commit there is no review, and the turn says why once). The review derives its risk from the diff, with no model and no cost: `passive` (documentation only, 0 lenses), `medium` (1 lens, `reliability`) or `high` (4 lenses: `risk`, `resilience`, `readability`, `reliability`). Following gentle-ai's lens selection, the agent can pick the review's lenses itself with the `risk` tool (`lenses`, 1 to 4, with a `lensesReason` naming what it touched and how), and its instructions say when each lens applies; the choice applies to the candidate its turn assessed (a later `/review` of a different tree uses the default lenses); the chosen lenses replace the default at either level, and a high risk Atelier finds by itself (anything but the agent's own items) always keeps `risk`. High risk comes from paths (`auth`, `security`, `permission`, `payment`, `webhook`, `migration`, `secret`, `credential`), dependencies and environment files, and from the content of the added lines, following gentle-ai's method; the size of the change, the number of files and the model never count. Each signal is a named reason with its place: `shell_process: <path>:<line>` for a real process spawn (`spawn`, `exec`, `execFile`, `execSync`, `child_process`, `subprocess`, `popen`, `ProcessBuilder`, `os.system`, `proc_open`, `Process.Start`...; a member call such as `cp.exec(` or `childProcess.spawn(` counts only in a file that imports `child_process`, so `db.exec(` and `/re/.exec(` elsewhere are not spawns, and neither is `process.stdin.setRawMode`; spaces before the parenthesis do not hide a call) and `dangerous_sink: <path>:<line> (<sink>)` for a concrete sink: `eval`, `new Function`, disabled TLS validation, unsafe deserialization, shell commands composed from variables, `rm -rf`, `DROP TABLE`, `DELETE FROM`, world-writable modes, CSRF or JWT bypasses (the catalog is gentle-ai's, gated by language). A line that is only a comment in its file's language (`//`, `/* */`, `#`, `--`) is skipped, and so are the lines inside a block comment that an added line opens (code after its `*/` is scanned); a language Atelier does not know is never skipped. Only source, configuration and `.txt` files are scanned, never test files (`*.test.*`, `*.spec.*`, `__tests__`, `testdata`) or `docs/` and fixture folders, and only the first line of each kind per file is named. The scan fails closed: if the added bytes of scanned files pass 8 MiB the level is high with `process_scan_limit: <path>`. A change is `passive` only when every changed file is documentation proven by its content: an extension only nominates it, and a code fence, an interpreter line (`#!`), a `<script>` tag, MDX with imports, expressions or tags, binary content or text that is not UTF-8 make it not passive. Finally the level must be explained by its reasons (high needs a high reason, passive only `documentation only` over documentation files, medium none); if it is not, the level is high with a `tier_not_explained` reason. The agent's declaration can raise the level, never lower it. Following gentle-shell, the main agent closes every code change by declaring its risk with the `risk` tool: the high-risk items that apply (1 data that cannot be rebuilt or irreversible effects, 2 security, 3 contracts others consume, 4 concurrency, which includes asynchronous events or callbacks that can arrive in another order, turn or request than expected, interrupts and timeouts, races, shared mutable state and locks, 5 delivery or environment, 6 no test would catch a regression), each with a reason, or `none` with a reason (`{ "none": true, "reason": "..." }`), and optionally the lenses (`{ "items": [4], "reason": "...", "lenses": ["resilience"], "lensesReason": "..." }`). A declaration can only raise the level, never lower what the diff shows. If a code change reaches the end of the turn without a declaration, the core asks the agent once, inside the same turn, to declare it; if it still does not, the risk is not lowered (it stays at least `medium`) and the risk line says `no risk declaration`. A declaration covers only the turn it was made in: it is cleared when the next turn starts. If the agent edits, commits or resets while answering the request to declare, the candidate is frozen again (tree, base and base note are compared) and the new one is assessed. The `review_assessed` event carries the declaration (`declaration`: `items`, `none` or `missing`; absent for documentation), the reason for the chosen lenses (`lensesReason`, also on `review_consent_requested`; absent when the agent did not choose) and the base when it is not the current `HEAD` (`since`: the short id of the commit the change is measured from, so the turn's commits are included; `baseNote`: why the base fell back to the current `HEAD`, or that it is the empty tree because the turn started without commits), and both clients show them: the CLI as `◇ review medium · 1 lens (...) · declared none: <reason> · since 1a2b3c4` (with chosen lenses, `◇ review high · 2 lenses: resilience, reliability (...) · lenses chosen: <reason>`, and the consent question lists them with the reason), the desktop in the review block and the consent card. A high-risk candidate is offered for review with a consent question (review / do not review this candidate; the CLI asks on a terminal, the desktop shows a card); `/review` in the CLI and the Review button in the desktop review any risk, without asking, against `HEAD`; `/review <ref>` in the CLI (`Session.review(turnId, base)` in the core) reviews the worktree against that git ref instead, and refuses an unknown one with `Unknown git ref "<ref>": there is nothing to review against.` (the desktop button takes no ref). A receipt is keyed by the candidate tree, so the same worktree state is not offered twice whatever its base. The lenses are read-only subagents on the session's model that read the frozen tree, never the live worktree, and a context over 200 KiB is refused, not truncated. Only `blocker` or `critical` findings caused by the candidate block; a refuter confirms or discards them once, the main agent makes one correction within `min(200, ⌈n/2⌉)` changed lines (at least 2, measured by the core), and a validator checks it. The correction request says not to commit, unless the reviewed work is already committed (the base is an earlier commit, whether the agent committed during the turn or an on-demand `/review <ref>` covers commits): then it asks to commit the correction on the same branch once its checks pass, so corrected work is not left uncommitted; the verifier's correction request does the same. The verdict is `approved`, `escalated` (out of budget or unresolved: the correction stays in the worktree and nothing else is attempted), `declined` or `unavailable`. Every review leaves a JSON receipt in `<git-dir>/atelier/reviews/`, never in the worktree, and the same candidate is not offered twice. Approving never commits, pushes or opens a PR. An escalated correction can be undone: `/undo-correction` in the CLI (the repository's latest escalated review with a correction, found among the receipts in `<git-dir>/atelier/reviews/` by `createdAt`, so it works in a new session or after Atelier restarted), the Undo correction button in the desktop's review block (that review), `session.undo_correction` (`sessionId`, optional `reviewId` of a review of that session; without it, the repository's latest one as with `/undo-correction`; answered with a `turnId` like `session.send`) or `Session.undoCorrection(reviewId?)` in the core. It is a turn without a model call that puts back, in the worktree only, the files the correction changed, with the bytes and mode they had in the candidate tree (files it created are removed, with the folders that leaves empty, files it deleted come back); other files, the index and the commits are not touched. It fails closed and changes nothing when a file the correction changed is no longer as the correction left it (error `correction_changed`, naming the files), when the correction was committed since the review (`correction_committed`: HEAD moved to the corrected version of one of its files; a file HEAD already held, such as one the correction reverted to HEAD or a new file it deleted, does not count), when it was already undone (`correction_already_undone`), when the review was not escalated (`not_escalated`) or left no correction (`no_correction`), or when its receipt has no `headTree` (receipts written before Atelier kept it: `undo_failed`, saying so); these are recoverable `error` events and the turn ends with `stopReason: "error"`. On success the event `correction_undone` (`reviewId`, `restored`, `removed`) follows, the CLI prints `✓ correction undone · restored a.ts, src/auth.ts · removed src/extra.ts`, the desktop shows it in the review block, and the candidate's receipt gets `undoneAt`. Each receipt keeps `headTree`, the tree of `HEAD` when the review ended, which is how a later commit of the correction is told. If writing fails midway (a disk error, a folder that refuses the change), the files it reached are put back as the correction left them (the bytes and mode of the corrected tree, which the worktree was checked to hold before it began) and the error `undo_failed` says so; only if putting them back fails too does the message name the files that may be in neither state. Review is on by default; `--no-review` or `ATELIER_REVIEW=off` turns it off, and without git (or without a commit) it says why there is no review; `/review` in a repo without commits is refused with the same reason. See `../docs/m7-diseno.md`; measured runs are in `../docs/m7-medicion.md`.
- Independent verification (M9, following gentle-shell's `gentle-ai-verify`): when the agent's risk declaration for a turn names at least one high-risk item (1 to 6; `none`, no declaration, and a high risk that only the diff showed do not count), the core, not the model, runs a `verifier` role on the turn's frozen candidate at the end of the turn, before the review is assessed or offered. It is not asked for consent (the review keeps its consent), and `--no-review` / `ATELIER_REVIEW=off` turns verification off with the review. The verifier works in a temporary directory (`atelier-verify-*` in the system temp folder) that holds `candidate/` and `base/`, both written from the frozen git trees with `git cat-file`, so your worktree, index and refs are never touched and no attribute or filter of the repository runs. Installed dependencies are made usable without installing and without sharing them with your project: every `node_modules` of the worktree (the root's and each workspace package's) is copied into both copies (a copy-on-write clone with `cp -c` on macOS, `cp --reflink=auto` on Linux, a plain recursive copy otherwise; links stay links, files are new ones, so a hard link to the pnpm store is broken). A symbolic link in the copies that points into your project is re-pointed at the same place of the copy, so the candidate's tests run the candidate's code, and one that points anywhere else is removed (the verifier is told how many). More than 4 GiB of dependencies, more than 120 seconds of copying, or a failed copy leaves the copies with no dependencies, and the verifier is told and marks those requirements unverified; so does a project without any. What the verifier's `bash` writes in `node_modules` stays in the copy. Its `bash` is confined by the sandbox (see "Sandbox (macOS)"): it writes only this directory and has no network; without a sandbox it gets no `bash`. The copy is removed when the verification ends, also on error or interrupt. The verifier has `read`, `grep` and `bash` with that directory as working directory; its `bash` runs without asking (only there) with the same filtered environment as the agent's `bash`, plus variables that make package managers refuse to install or fetch (`npm_config_offline`, `pnpm_config_offline`, an unreachable `npm_config_registry`, `npm_config_manage_package_manager_versions=false`, `NO_UPDATE_NOTIFIER`, `COREPACK_ENABLE_NETWORK=0`, `YARN_ENABLE_NETWORK=0`, `PIP_NO_INDEX`, `CARGO_NET_OFFLINE`, `GOPROXY=off`); its mandate also forbids installing and using the network, and caps it at 80 model requests per run. It receives the user's request for the turn verbatim, a copy of the active ODD feature document (`feature/<name>.md`), the agent's declaration, a summary of base vs candidate and, since the copies have no `.git`, what the repository shows: the current branch (`none (detached HEAD)` without one), the short id and subject of each commit from the base to `HEAD` (oldest first, at most 50 listed), and whether the worktree holds uncommitted changes (so it can check requirements such as working on a branch and committing; if git cannot answer, this part is left out), and must derive the requirements, run probes (including hostile input aimed at what the declared item protects), reproduce every defect on `candidate/` and on `base/` (a defect that also happens on the base is advisory), and answer one JSON report: a verdict per requirement (`met`, `unmet`, `unverified`, with evidence) and the defects (`blocker`, `major` or `minor`, with reproduction, behavior on the candidate and on the base, `onBase`). A reply that is not a complete report (including one with no requirements) is a failed verifier, never a pass. A requirement judged `unmet` counts as a blocker even without a defect. Blocker or major defects that are not on the base, and unmet requirements (as `R1 [blocker] Requirement not met: ...`, with the verifier's evidence), go to the main agent once, inside the same turn, as a correction request; the candidate is frozen again and the verifier runs a second time. There are at most two rounds. It passes only when every requirement is `met` and no blocking defect is left; a requirement still `unverified` ends it with "needs your decision" and the list of them, never as a pass. If blocking defects remain after round 2, or the verifier failed, the turn ends with a visible "needs your decision" and the open defects; it does not loop. The review then continues on the final candidate as usual. Events: `verification_started` (`verifyId`, `items`, `declaration`), `verification_round` (`round`, `ok`/`error`, `cause`, `observed`, `requirements`, `defects`, `blocking`, `correcting`, `usage`, `costUsd`) and `verification_finished` (`outcome`: `passed`, `corrected`, `needs_decision` or `failed`; `reason`, `cause`, `observed`, `rounds`, `openDefects`, `usage`, `costUsd`); the verifier's own events are tagged `agent: "verify:verifier"` under `verifyId`, and its cost (and the correction's) is added to the turn's `turn_finished`. The CLI prints `◇ verifying · item 2`, `◇ verify · round 1 · 2 defects (blocker, major) · asking the agent to fix them`, `✓ verify passed`, `✓ verify passed after a correction · 2 rounds`, `✗ verify: needs your decision · 1 open defect` (followed by each defect and its reproduction), `✗ verify: needs your decision · 1 unverified requirement: R1 ...` and `✗ verify failed: <reason> · needs your decision`; when the event has a cause they show it with the value observed in place of the reason, as in `◇ verify · round 1 · failed: invalid_report (looks fine to me)`, `✗ verify failed: request_cap (80 requests) · needs your decision` and `✗ verify: needs your decision · open_defects (D2)` (for `needs_decision` the reason follows, since it lists the unverified requirements); the desktop shows a verification block with the declared items, each round's verdicts and defects, and the outcome. Every verifier or review that ends without a pass names why, from a closed set, never only with a message: the optional fields `cause` and `observed` (the value seen, when there is one) on `verification_round` (with `ok: false`), `verification_finished` (`needs_decision` or `failed`) and `review_finished` (`escalated` or `unavailable`), and in the review receipt. The causes: `interrupted`; `role_failed` (the verifier or a review role could not start or failed; `observed`: its error); `request_cap` (it ran out of model requests; `observed`: `80 requests`); `invalid_report` (the verifier's reply is not a complete report) and `missing_requirements` (it lists none; `observed`: `0 requirements`); `invalid_reply` (a lens, the refuter or the validator answered something unreadable); `context_too_large` (`observed`: `<bytes> bytes, limit 204800`); `patch_unreadable`; `copy_failed` (the verifier's copy could not be made); `sandbox_unavailable` (the verifier had no bash and left requirements unverified; `observed`: the sandbox's reason); `correction_failed`; `freeze_failed`; `measure_failed`; `over_budget` (`observed`: `<used> lines, budget <budget>`); `unverified_requirements`, `open_defects` and `unresolved_findings` (`observed`: their ids). A reply or an error given as `observed` is its start on one line, cut at 200 characters. The existing `reason` and `error` stay as they were. Clients show `<cause> (<observed>)`. See `../docs/m9-diseno.md`.
- Project instructions: at session start the core walks up from the working directory (`--cwd`) through every parent folder, stopping before the user's home folder (or at the disk root if the folder is not under it), and takes `AGENTS.md` from each folder, or `CLAUDE.md` when there is no `AGENTS.md`. Before them comes the user's own `~/.agents/AGENTS.md`, if there is one, as `User instructions from <path>:`. The files are appended to the main session's system prompt from the outermost folder to the closest, each preceded by `Project instructions from <path>:`, so the closest comes last and wins a contradiction. It works the same on `anthropic-api` and `claude-code`, and the files are read once, at start (editing them later does not change the running session, which keeps the prompt prefix cache intact). The total is capped at 32 KiB: over it, the outermost files are dropped first, the user's file before any project file. The first turn reports `instructions: <paths>` and, if the cap left files out, the warning `instructions over 32 KiB, left out: <paths>`; the desktop shows both in the status bar. Subagents do not get them: they keep only their task and role instructions. There is no stop at the git root, so running in `atelier/` also reads `../AGENTS.md`.
- Context compaction (M8): a long session no longer ends in a context error. On `anthropic-api`, before each model request the core compares the context (the last response's real usage plus an estimate of what was appended since) with `min(window − (max output + 16,384), 200,000)` tokens, the window coming from the models API (200,000 when it does not answer); `ATELIER_COMPACT_AT=<n>` replaces the 200,000 cap, but never goes past the window minus the reserve. Crossing it, the core asks the session's model for a summary in a fixed format (Goal, Constraints & Preferences, Progress, Key Decisions, Next Steps, Critical Context), with the session's own prefix so it reads from the prompt cache, and replaces the older history with one message: the summary, the files read and edited (from the tool calls, not from the model; a file created or replaced with `write` counts as edited), the current turn's request verbatim when it was summarized, and once the core's state (active ODD feature and task, phase, the memory of the first turn). The last ~20,000 tokens stay verbatim and a tool result never loses its call. A summary that is empty, cut short or missing a section is refused and the history stays as it was; a context overflow compacts once and retries the request. Claude Code compacts on its own: Atelier shows its compactions, forwards `/compact`, and gives the core's state with the next prompt. Both clients show the compaction (before → after, messages kept, cost), mark the cache miss that follows it as expected, show how full the context is, and accept `/compact [instructions]`. A subagent compacts by the same rules in its own session (the threshold, one compaction on an overflow) and goes on with its task; its compaction events reach the parent tagged with `parentCallId` and `agent` like its other events, both clients show them under the subagent with its own expected cache miss, and its summary is never saved to memory. If a subagent's turn fails after its compaction failed, the task's error names both: `The worker subagent failed (error): <error>; its compaction failed: <reason>`. See `../docs/m8-diseno.md`; measured runs are in `../docs/m8-medicion.md`.
- `bash` runs without `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`. That only filters its environment; the isolation is the macOS sandbox described in "Sandbox (macOS)" below. Keep approvals on (no `--yes`) for work you do not trust.

Design and decisions: `../docs/m1-diseno.md`, `../docs/m2-diseno.md`, `../docs/m3-diseno.md`, `../docs/m4-diseno.md`, `../docs/m5-diseno.md`, `../docs/m6-diseno.md`, `../docs/m7-diseno.md`, `../docs/m8-diseno.md`, `../docs/m10-diseno.md`.

## Agent profiles

A profile says which model, backend and thinking level each agent role uses. A session resolves its profile once, when it starts (the CLI and the server do; with no profile file nothing changes), and keeps it for its whole life: the roles that start later read that frozen profile, they never resolve it again. The explicit layer below is `--profile <name>` in the CLI (refused with `error: --profile needs a home directory to read ~/.atelier/profiles.json from.` when there is no home) and `profile` in `session.start` (`{ "command": "session.start", "cwd": "...", "profile": "cheap" }`); a server without a home directory reads no profiles and refuses it with `profile_unavailable` instead of dropping it. `profiles.list` (optional `cwd`) answers with the names in `profiles.json` in file order, its `active`, and with `cwd`, `effective`: the profile a session there would take without a choice (`{ "name": "cheap", "origin": "active" }`; no `name` for the default profile); without a home, or with an invalid file, `profiles` is empty.

Every `session_started` of the main agent (also the ones a correction turn or a later Claude Code init says) carries the profile the session froze, as `profile`: its `name` (absent for the default profile), its `origin` (`explicit`, `local-pin`, `repo`, `active` or `default`) and `roles`, what it sets for each role but the orchestrator, in the order of the roles below (`{ "verifier": { "backend": "anthropic-api", "model": "claude-sonnet-5-5", "thinking": "medium" } }`, each field absent when inherited). The orchestrator is the event's own `backend`, `model` and `effort`, so `--model` shows there. A session started without profiles (the core used as a library) has no `profile`.

`~/.atelier/profiles.json`:

```json
{
	"kind": "atelier.agent_model_profiles",
	"version": 1,
	"active": "cheap",
	"profiles": {
		"cheap": {
			"verifier": { "model": "anthropic-api/claude-sonnet-5-5", "thinking": "medium" },
			"review-readability": { "model": "claude-code/haiku", "thinking": "low" }
		}
	}
}
```

- **Roles**: `orchestrator`, `worker`, `explorer`, `verifier`, `review-risk`, `review-resilience`, `review-readability`, `review-reliability`, `review-refuter`, `review-validator`, `compaction`.
- **Levels**: `thinking` (or its alias `effort`) is one of `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.
- **Levels in the backends**: no level sends nothing. `minimal` is sent as effort `low`; `low` to `max` as the effort (`output_config.effort` in `anthropic-api`, the `effort` option in `claude-code`) when the model takes it. `off` turns thinking off only where Anthropic documents how: `thinking: disabled` on Haiku 5.5 and Opus 5 (both backends) and `between_tools` on Sonnet 5.5 (`anthropic-api` only; the Claude Agent SDK cannot send it). Anything else is not sent. `session_started.effort` says the effort sent, `off`, or `unsupported`, and is absent when no level was asked.
- **Inherit**: omit a field to inherit it. A role the profile does not list uses the default profile, which sets nothing; it never uses another profile.
- **Models** may only contain `A-Z a-z 0-9 . _ ~ : @ / + % -`. The prefix `anthropic-api/` (API key) or `claude-code/` (Claude Code subscription) picks the backend for that role; without a prefix the session's backend applies.
- **Invalid content** is dropped and reported, and the rest of the file still counts: an unknown role (with a "did you mean" for a close name), an unsafe model, an unknown level, a profile that is not an object. A file without the expected `kind` and `version` is invalid as a whole. A missing file means no profiles.
- **Choosing a profile**, first match wins: the explicit choice, then the local pin `<git common dir>/atelier/profile-pin.json`, then the repository's `.atelier/profile.json`, then `active` in `profiles.json`, then the default profile. A layer that names a profile that does not exist is reported and skipped. Both pins are `{ "kind": "atelier.profile_pin", "version": 1, "profile": "<name>" }`.

### How a profile reaches each role

- **`orchestrator`** is the main agent: its model and thinking level go to its backend, and its backend prefix chooses the session's backend. An explicit `--model` (or `session.start.model`) replaces its model, and an explicit `--backend` (or `session.start.backend`) its backend; with neither the profile nor a flag saying anything, the defaults are what they always were.
- **`worker`** and **`explorer`** are the `task` tool's subagents. Each starts on its entry's backend (the session's kind without a prefix), with its model and thinking level. A model the entry omits is, for the explorer, its default for that backend (`haiku` on `claude-code`, `claude-haiku-5-5` on `anthropic-api`), and for the worker, the main agent's.
- **`verifier`**, **`review-risk`**, **`review-resilience`**, **`review-readability`**, **`review-reliability`**, **`review-refuter`** and **`review-validator`** are the review's child sessions. Each runs on its own entry: its backend, its model (the main agent's where the entry sets none) and its thinking level. Every lens has its own entry.
- **`compaction`** only applies to `anthropic-api`, the one backend that makes a request to summarize its history (automatic compaction and `/compact`): that request uses the entry's model and thinking level, and the session's for what the entry omits; every other request is unchanged, and the summary is priced at its own model. The summary always runs in the session's own backend, so it never changes who pays: an entry whose prefix names another backend is dropped whole (neither its model nor its level applies) with a warning, and a prefix equal to the session's backend applies. Worker, explorer and review children on the session's backend get the same entry for their own summaries. On `claude-code`, which compacts on its own, the entry is reported as not applicable and nothing is passed on.
- A level the entry omits sends nothing, as before.

A role whose backend cannot start for lack of its credential fails with an error that names the role and the backend, and nothing retries on the other backend. For a subagent the `task` tool's result is that message, for example `worker: anthropic-api has no API key (No Anthropic API key in the Keychain. Store it with: ...)`. A role that starts but fails on its own backend (Claude Code not logged in) says so: `The explorer subagent failed on claude-code (error): ...`. A review role that fails keeps its usual failure (the verdict `unavailable` with the cause `role_failed`, or a failed verification) and its message starts with the profile role and the backend: `Lens reliability failed: review-reliability: anthropic-api has no API key (...)`. A role that uses the session's own backend fails exactly as before. The orchestrator does the same when its entry (not `--backend`) chose the backend: the CLI prints `error: orchestrator: anthropic-api has no API key (...)` and `session.start` answers with that message; a credential error during a turn (`not_logged_in`, `authentication_error`) reads `orchestrator: claude-code: Claude Code is not logged in. ...`. A role on `claude-code` never gets `ANTHROPIC_API_KEY`, whatever the environment of the session.

What resolution dropped (an unknown role, an unsafe model, an unknown level, a missing pinned profile, a stale `active`) reaches the client in the first turn as recoverable `error` events with the code `profile_warning`, one per report: `<file>: <what was dropped>`. The CLI prints them as `error: ...` without failing the run. If `profiles.json` or a pin changes (or appears, or goes away) after the session started, the session keeps the profile it froze and says so at the start of the next turn, once per changed file, as a recoverable `error` event with the code `profile_changed`: `<file> changed after the session started; this session keeps profile "<name>"` (`was created` / `was removed` instead of `changed` when the file appeared or went away; `the default profile` when no profile was chosen). The same change is not repeated. The compaction entry adds two: `compaction: the summary runs in the session's own backend (<session backend>), so the "<backend>" entry is not used` and `compaction: claude-code compacts on its own, so the compaction entry does not apply`.

The agent cannot write `~/.atelier/` or the local pin: `edit`, `write` and the `bash` sandbox refuse them.

## Sandbox (macOS)

On macOS every `bash` command of the agent, its workers and the verifier runs under the operating system's sandbox (Seatbelt, through `@anthropic-ai/sandbox-runtime` 0.0.81). It is built for macOS only: elsewhere, or if `sandbox-exec` does not answer, there is no sandbox and the commands fall back to approvals (see below). Design: `../docs/m10-diseno.md`.

### What is isolated and what is not

|         | Agent and workers                                                                                                                                                                                                                                                                                     | Verifier                                                                                                                                                                                                                                                |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writes  | the working directory, the system temporary directory, the session scratch directory and the package managers' caches under your home (`~/.npm`, `~/Library/pnpm`, `~/.local/share/pnpm`, `~/.pnpm-store`, `~/.yarn`, `~/.node-gyp`, `~/.cache`, `~/Library/Caches`), never the home directory itself | only its own temporary directory                                                                                                                                                                                                                        |
| Reads   | everything except `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains` and `~/.claude`                                                                                                                                                                                               | only its directory, the Node installation and the system toolchain (`/usr`, `/bin`, `/sbin`, `/System`, `/etc`, `/dev`, `/opt/homebrew`, `/Library/Apple/usr`, `/Library/Frameworks`); `/Library/Keychains` and the rest of `/Library` are not readable |
| Network | free, as in gentle-shell                                                                                                                                                                                                                                                                              | none                                                                                                                                                                                                                                                    |

In the working directory the agent never writes `.env`, `.env.*`, `*.pem`, `*.key`, the git hooks and configuration, shell start-up files and editor or tool configuration (`.git/hooks`, `.git/config`, `.gitconfig`, `.gitmodules`, `.bashrc`, `.bash_profile`, `.zshrc`, `.zprofile`, `.profile`, `.ripgreprc`, `.mcp.json`, `.vscode`, `.idea`, `.claude/commands`, `.claude/agents`), nor the pending steps of a rebase, a cherry-pick or a revert (`.git/rebase-merge`, `.git/rebase-apply`, `.git/sequencer`), nor `.atelier`. The same holds for the git places `git rev-parse` reports for the working directory, asked at each command: the hooks directory git runs (`core.hooksPath` included, inside the working directory or not), the `config` and `config.worktree` of the git directory and of the shared one, and the `.git` file of a linked worktree (a `.git` that is a link to a directory protects the same subset as a plain one). Also every file those configurations include (`include.path`, `includeIf.<condition>.path`, read by `git config --file <file> --no-includes` so git's whole syntax counts: quotes, escapes, continuation lines; relative to the including file, `~/` as the home, through included files up to 10 levels, whatever the condition and whether the file exists yet; your global and system configuration are not touched), `info/attributes` and `modules/` (the submodules' git directories). If git cannot read the configuration inside a repository (a broken included file), the same set is derived by reading each repository file alone with `git config --file`, so a broken file elsewhere does not lift the protection; a file git itself cannot read is parsed by a simple fallback parser and its directory's `hooks`, `config` and `config.worktree` are protected too. Outside a git repository only the conventional paths above apply.

Not covered:
- The agent's network is not restricted: a command can reach the network and anything it can read.
- Other platforms: no Linux or Windows code exists.
- The `read`, `edit`, `write` and `grep` tools are not run by the sandbox; code decides what they open, which is a separate mechanism. `edit` and `write` leave `--cwd` only with the user's approval, file by file. `read` and `grep` may leave it but refuse the same secret directories and `denyRead` entries the sandbox hides from `bash`, whether or not the sandbox is running.
- `bash` also runs without `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`; that filters its environment and is not isolation.

### What you see

At the start of a session (in its first turn) the core emits `{ type: "sandbox_status", sandboxed: boolean, mechanism?: string, reason?: string }`, computed without running a command. The CLI prints `bash: sandboxed (macOS seatbelt)` on stdout, or `bash: not sandboxed (<reason>): every command asks for approval and --yes does not apply` on stderr. The desktop shows `bash: sandboxed (macOS seatbelt)` in the status bar, or `bash: not sandboxed` in the warning style with the reason as its tooltip. Subagents do not repeat it.

When a command that failed was blocked by the sandbox, its result says what it tried and why it was stopped, after the exit code:

```
[exit code 1]
[sandbox blocked: write to /Users/ana/notes.txt (not an allowed write path)]
[sandbox blocked: read of /Users/ana/.ssh/id_rsa (denied by the sandbox policy)]
[sandbox blocked: network connect to 127.0.0.1:8080 (no network for the verifier)]
```

The causes come from the sandbox library's own violation report, nothing is guessed: if it reports nothing, nothing is added. At most five causes are listed (then `[sandbox blocked: and N more]`), network first, then writes, then reads; the system's own preference reads are left out. The output truncation rules are unchanged. `tool_call_finished` carries the same causes as `blocked: string[]`; the CLI prints them under the tool line as `  sandbox blocked: <cause>`, and the desktop shows them in the tool row. Limits: only a command that failed is asked; each run is given its own id and the library records its denials under it, so a cause is shown only for the run that produced it, never for an overlapping run of the same text, and a denial the library could not attribute to a run is not shown; and the file denials come from the system log, which can lag, so a block in the first seconds of a session may go unreported.

### Approvals and `--yes`

A command that runs in the sandbox asks for approval as always, and `--yes` approves it. `--yes` approves only what runs sandboxed.

The `bash` tool has two optional inputs, `unsandboxed: true` and a required `reason`, with which the agent asks to leave the sandbox for one command (for example to install dependencies with network access). The user is always asked, even with `--yes`, and sees the reason (CLI: `Run this command OUTSIDE the sandbox?`, then the command and `reason: ...`; desktop: a card titled `Run this command outside the sandbox?` that shows the reason; the `approval_requested` event carries `reason`). Without a terminal the CLI refuses it (`bash command asks to run outside the sandbox and needs your approval, but there is no terminal to ask (--yes does not allow this): <command>`, then `reason: <reason>`). A missing or blank `reason` is `Invalid input: reason is required with unsandboxed: ...`, and the verifier's `bash` refuses it (`Refused: the verifier's bash cannot run outside the sandbox — <command>`).

Without a sandbox (another platform, a sandbox that fails to start, `--no-sandbox` or `ATELIER_SANDBOX=off`; `SessionOptions.noSandbox` for other clients) every command asks even with `--yes`, and the verifier gets no `bash`. The core emits `{ type: "sandbox_warning", reason }` once per turn, before the first question of the turn that runs `bash`. The CLI prints `warning: bash runs without a sandbox (<reason>): every command asks for approval and --yes does not apply` on stderr, except in the turn whose start already printed the `bash: not sandboxed` line (one line, not two); the desktop shows it in the turn, as `bash runs without a sandbox (<reason>): every command asks for approval and --yes does not apply`. Without a terminal the CLI denies such a command and says `--yes does not apply because the sandbox is off or unavailable`.

### Turning it off

`--no-sandbox` or `ATELIER_SANDBOX=off` runs `bash` without the sandbox, with the behavior above. `atelier-core serve` honors `ATELIER_SANDBOX=off` for every session, and `session.start` accepts `noSandbox: true` for one session (that is how a client such as the desktop starts one without it). In the desktop it is the `run bash without the sandbox` checkbox in the toolbar, unchecked by default, which applies to the sessions opened while it is checked; such a session shows `bash: NOT SANDBOXED (turned off)` in the warning style in the status bar from the moment it opens, in place of the usual sandbox line. With the sandbox off the configuration files below are not read or validated.

### Commands that are always refused

Before the sandbox and before any approval question, even with `--yes`, for every caller (the agent, its workers and the verifier), following gentle-shell's destructive command guard: recursive removal (`rm -r`) of `/`, of `~` or `$HOME`, or of the project directory (or a directory that contains it, `.` and `./*` included), and a `find` (or `gfind`) from one of those places that deletes (`-delete`, or `-exec`/`-execdir`/`-ok`/`-okdir` running `rm`, also behind `env` or `command`), unless it has a `-name`, `-iname`, `-path`, `-ipath`, `-wholename`, `-regex` or `-iregex` test whose pattern does not match everything (a glob that is not just `*` and `?`; a regex with at least one literal character outside bracket classes, quantifiers, intervals, anchors, groups, alternatives and `.`, where an escaped punctuation character such as `\.` or `\/` counts as literal and a literal inside a group or made optional by `?`, `*` or `{0,` does not, and any alternative `|` makes it not narrow, so `'.*\.log'` narrows while `'.*.*'`, `'.{0,}'`, `'(.*)'`, `'.*|x'`, `'.*x?'`, `'(x)?.*'` or even `'[^/]*'` and `'[a-z]*'` do not) and that comes before the deleting action (so `find . -name '*.log' -delete` still runs, while a `!`, `-not`, `-o`, `-or` or `,` anywhere in the expression voids the narrowing, and `-type`, `-mtime`, `-print` or parentheses do not count as narrowing and `find . -mtime +30 -delete` is refused); `mkfs*`; `dd` with `of=/dev/...` (not `/dev/null`, `/dev/stdout`, `/dev/stderr`, `/dev/tty`); fork bombs (`:(){ :|:& };:` and any function that pipes itself into itself in the background); recursive `chmod`/`chown` on `/`; and `sudo` and `su` as a command of any segment (also behind `env` and `env -S "..."` (split into words like `env` does, with its `\_`, `\t` and quote escapes (`\c` does not end the string: every word is judged), and judged as one command together with the arguments that follow; shell operators inside the string are just text), `nohup`, `timeout`, `xargs`, `sh -c`, `eval`, `find -exec`, `$(...)`, backticks and redirections written before the command, `2>&1` and `{fd}>file` included). The tool result is `Refused: <rule> — <command>` (the rules are `recursive removal of /`, `recursive removal of the home directory`, `recursive removal of the project directory`, `mkfs`, `dd to a device`, `fork bomb`, `recursive chmod/chown on /`, `sudo`, `su`) and nobody is asked.

It only knows recognizable forms: text in quotes or in a heredoc is data, and it does not read pipes (`echo / | xargs rm -rf`), heredocs passed to a shell, redirections to a device, a bare `*`, or scripts. What it does not recognize is not refused by it; the sandbox is the next layer.

### Configuration files

Two optional files add to the agent's policy and never to the verifier's: `~/.atelier/sandbox.json` (yours) and `<cwd>/.atelier/sandbox.json` (the project's), each `{ "allowWrite"?: string[], "denyRead"?: string[] }`. A path is absolute, `~/...`, or relative to the file's base (your home for yours, the working directory for the project's). The files only add, and never remove a fixed protection. An `allowWrite` entry that is, contains or lies inside a protected place (your home itself, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains`, `~/.claude`, `~/.atelier`; so `~`, `/` and any parent of home too, also through a symbolic link) is refused, and the secret file patterns and the git and shell files above also hold inside every added directory.

A file that is invalid (not JSON, not an object, an unknown key, a value that is not an array of non-empty strings, a refused entry) stops the CLI before anything runs (exit 1, `error: Invalid sandbox configuration <file>: <problem>`) and fails `session.start` of `atelier-core serve` (`session_start_failed`, same message). A file that becomes invalid later makes each `bash` command fail with `[sandbox error: Invalid sandbox configuration <file>: <problem>]` and run nothing. It is never ignored, because that would silently widen or narrow what commands can do.

**Caveat:** the project file lives in the repository, so a repository you do not control can ship one that makes more places writable for the agent, everywhere except your home directory itself, the protected places above and `~/.atelier`. Read it before you trust the project.

### Running as root

As root (uid 0), the CLI and `atelier-core serve` refuse to start (exit 1) unless `ATELIER_ALLOW_ROOT` is exactly `I accept the risk`: `error: Atelier will not run as root (uid 0): a mistaken command could damage the whole system. To run as root anyway, set ATELIER_ALLOW_ROOT="I accept the risk" (exactly that text).`, plus `ATELIER_ALLOW_ROOT is set to "<value>", which is not that exact text.` when it is set to something else. With the exact text they start and print `warning: running as root (uid 0) because ATELIER_ALLOW_ROOT is set: every command has full control of this system.` on every start (the server prefixes both with `atelier-core: ` on stderr). `--help` and `--version` still work as root.

### Known limits

- `git config` and `git branch -u` fail inside `bash` (the library protects `.git/config`).
- Rebase, cherry-pick and revert cannot run inside `bash`: the pending steps of one (`rebase-merge/`, `rebase-apply/` and `sequencer/` in the git directory, `.git/` or a linked worktree's own directory under `.git/worktrees/<name>/`) are never writable, whether they exist or not, because an `exec` line in `rebase-merge/git-rebase-todo` would run when you later `git rebase --continue` outside Atelier. `git rebase`, a `git cherry-pick` or `git revert` of several commits (which keep their steps in `sequencer/`) and their `--continue`/`--abort` fail with `Operation not permitted`; the agent asks to run them outside the sandbox, with your approval. Commit, branch, stash, merge (with or without conflicts), tag and deleting packed refs keep working.
- In a linked git worktree (`git worktree add`), whose git data lives in the main checkout's `.git`, the agent may also write that worktree's own directory there (`.git/worktrees/<name>`) and the repository's `objects`, `refs`, `logs`, `packed-refs`, `packed-refs.lock` and `packed-refs.new`, so branches, commits and packing refs work without leaving the sandbox. What would make git run code or work on another repository stays protected: the shared `hooks` (and the hooks directory git actually runs, `core.hooksPath` included, as `git rev-parse --git-path hooks` reports it), `config` and `config.worktree`, `objects/info` (alternates), and the worktree's own `config.worktree` (a `core.hooksPath` there would run a hook the next time you commit, outside the sandbox), `commondir`, `gitdir` and `hooks`; the secret file patterns hold in those directories too, and nothing else of the main checkout becomes writable. `git gc` and `git repack`, which update `objects/info`, need to leave the sandbox. The worktree's git directories are asked from `git rev-parse` once per working directory and checked against the files git keeps for a worktree (its directory must be `<common>/worktrees/<name>`, and its `gitdir` file must point back at the worktree), so a tampered `commondir` grants nothing.
- The verifier's `git` is the real one of the active developer directory (found once with `xcrun --find git`), first on its `PATH`, with that directory's `usr/` readable and no system or global git configuration (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`): the `/usr/bin/git` shim cannot run there, because it writes a cache in your per-user temporary folder. Its commands also get `TMPDIR` inside its own directory (`<dir>/.tmp`), set in the command, so tests that create temporary directories work, and a `HOME` of their own (`<dir>/.home`, with `XDG_CONFIG_HOME` under it), because your home is not readable and tools such as git read their configuration from home even when a caller clears the `GIT_*` variables; the library's own `/tmp/claude` stays writable but the verifier cannot read `/tmp`. It also reads `/private/var/select`, where macOS records the shell `/bin/sh` runs and the developer directory. Without a developer directory the verifier has no `git`. Atelier's own suite passes inside the verifier's sandbox, apart from the tests that need a real sandbox, which are skipped there.
- Each command costs about 16 ms more (about 63 ms the first one).
- macOS cannot nest sandboxes. An Atelier that already runs inside one (Atelier running its own tests from a sandboxed command) finds out by trying the smallest sandbox there is and reads macOS's refusal; it then reports `already inside a sandbox, and macOS cannot nest them: commands stay confined by the outer one` and takes the unavailable path (every command asks, the verifier gets no `bash`). Nothing in the environment can claim this. The tests that need a real sandbox are skipped there and run in a normal `pnpm check`.
- The library is "Beta Research Preview" and global to the process; the sandbox is not reset until the process exits.

## Working on Atelier with Atelier

Changing Atelier with the Atelier you are changing breaks the tool in the middle of the work. Keep a stable copy as the tool and the repository as the workpiece:

```
atelier/          the workpiece: feat/* branches, where the agent edits
atelier-stable/   the tool: a worktree pinned to a stable-* tag, never edited
```

```bash
# once: pin the copy that works today
git tag -a stable-m8 -m "Stable Atelier"
git worktree add --detach ../atelier-stable stable-m8
pnpm -C ../atelier-stable install

# use it on the workpiece (or on any other project)
alias atelier-stable='node /path/to/atelier-stable/atelier-cli/src/main.ts'
atelier-stable --cwd /path/to/atelier
pnpm -C ../atelier-stable desktop   # the desktop starts the stable copy's own core
```

- `edit` and `write` ask for approval before changing or creating any file outside `--cwd`, and the question shows the path: do not approve a path inside `atelier-stable/` (`read` and `grep` can read it freely). The stable copy is protected by that question, not by a rule, and `--yes` does not skip it. `bash` is not isolated: keep approvals on (no `--yes`) when the workpiece is Atelier itself.
- To try a change for real, run the workpiece's CLI (`pnpm atelier` inside `atelier/`) in another terminal; the stable copy stays in charge of the work.
- Memory (Engram resolves the project from the working directory), review receipts (in the workpiece's `.git`) and the API key are shared on purpose.

Promote only what is verified: once a branch is merged into `main` with `pnpm check`, the desktop smoke and a real run green, tag it and move the copy. To go back, check out the previous tag.

```bash
git tag -a stable-m9 -m "Stable Atelier"
git -C ../atelier-stable checkout --detach stable-m9 && pnpm -C ../atelier-stable install
```
