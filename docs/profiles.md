# Agent profiles and session settings

Which model, backend and thinking level each role uses, and how an open session changes its model, effort, profile or backend.

## Agent profiles

A profile says which model, backend and thinking level each agent role uses. A session resolves its profile once, when it starts (the CLI and the server do; with no profile file nothing changes), and keeps it for its whole life: the roles that start later read that frozen profile, they never resolve it again. The explicit layer below is `--profile <name>` in the CLI (refused with `error: --profile needs a home directory to read ~/.atelier/profiles.json from.` when there is no home) and `profile` in `session.start` (`{ "command": "session.start", "cwd": "...", "profile": "cheap" }`); a server without a home directory reads no profiles and refuses it with `profile_unavailable` instead of dropping it. `profiles.list` (optional `cwd`) answers with the names in `profiles.json` in file order, its `active`, and with `cwd`, `effective`: the profile a session there would take without a choice (`{ "name": "cheap", "origin": "active" }`; no `name` for the default profile); without a home, or with an invalid file, `profiles` is empty.

Every `session_started` of the main agent (also the ones a correction turn or a later Claude Code init says) carries the profile the session froze, as `profile`: its `name` (absent for the default profile), its `origin` (`explicit`, `local-pin`, `repo`, `active` or `default`) and `roles`, what it sets for each role but the orchestrator, in the order of the roles below (`{ "verifier": { "backend": "anthropic-api", "model": "claude-sonnet-5-5", "thinking": "medium" } }`, each field absent when inherited). The orchestrator is the event's own `backend`, `model` and `effort`, so `--model` shows there. A session started without profiles (the core used as a library) has no `profile`.

`~/.atelier/profiles.json`:

```json
{
	"kind": "atelier.agent_model_profiles",
	"version": 1,
	"active": "cheap",
	"profiles": {
		"cheap": {
			"verifier": { "model": "anthropic-api/claude-sonnet-5-5", "thinking": "medium" },
			"review-readability": { "model": "claude-code/haiku", "thinking": "low" }
		}
	}
}
```

- **Roles**: `orchestrator`, `worker`, `explorer`, `verifier`, `review-risk`, `review-resilience`, `review-readability`, `review-reliability`, `review-refuter`, `review-validator`, `compaction`, `permission-classifier`.
- **Levels**: `thinking` (or its alias `effort`) is one of `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.
- **Levels in the backends**: no level sends nothing. `minimal` is sent as effort `low`; `low` to `max` as the effort (`output_config.effort` in `anthropic-api`, the `effort` option in `claude-code`) when the model takes it. `off` turns thinking off only where Anthropic documents how: `thinking: disabled` on Haiku 5.5 and Opus 5 (both backends) and `between_tools` on Sonnet 5.5 (`anthropic-api` only; the Claude Agent SDK cannot send it). Anything else is not sent. On `opencode-go`, `claude-haiku-5-5` takes what it takes on `anthropic-api`; the other models take the levels of Atelier's table of OpenCode Go models, sent as `reasoning_effort` on Chat Completions, and `off` only where the model has a value for it (`none` on `hy3` and `hy4-preview`); the Messages API models of other providers (`minimax-m3`, the Qwen models) take none. Where thinking is on by default (the Claude 5 models) and was not turned off, `anthropic-api` sends `thinking: {type: "adaptive", display: "summarized"}` and `claude-code` passes the same `thinking` option and sets `showThinkingSummaries`, so `thinking_delta` carries the summarized thinking the API would otherwise omit; it costs the same, and the first text arrives a little later. `session_started.effort` says the effort sent, `off`, or `unsupported`, and is absent when no level was asked.
- **Inherit**: omit a field to inherit it from the main session: a role without `model` runs on the main agent's model, and one without `thinking` on the main agent's level (the `orchestrator`'s, or nothing when that sets none either). A role the profile does not list uses the default profile, which sets nothing; it never uses another profile. Without a profile, every role runs on the main agent's model and level.
- **Models** may only contain `A-Z a-z 0-9 . _ ~ : @ / + % -`. The prefix `anthropic-api/` (API key), `opencode-go/` (OpenCode Go key), `claude-code/` (Claude Code subscription) or `openai-codex/` (ChatGPT subscription) picks the backend for that role; without a prefix the session's backend applies.
- **Invalid content** is dropped and reported, and the rest of the file still counts: an unknown role (with a "did you mean" for a close name), an unsafe model, an unknown level, a profile that is not an object. A file without the expected `kind` and `version` is invalid as a whole. A missing file means no profiles.
- **Choosing a profile**, first match wins: the explicit choice, then the local pin `<git common dir>/atelier/profile-pin.json`, then the repository's `.atelier/profile.json`, then `active` in `profiles.json`, then the default profile. A layer that names a profile that does not exist is reported and skipped. Both pins are `{ "kind": "atelier.profile_pin", "version": 1, "profile": "<name>" }`.

### How a profile reaches each role

- **`orchestrator`** is the main agent: its model and thinking level go to its backend, and its backend prefix chooses the session's backend. An explicit `--model` (or `session.start.model`) replaces its model, and an explicit `--backend` (or `session.start.backend`) its backend; with neither the profile nor a flag saying anything, the defaults are what they always were.
- **`worker`** and **`explorer`** are the `task` tool's subagents. Each starts on its entry's backend (the session's kind without a prefix), with its model and thinking level. A model or level the entry omits is the main agent's.
- **`verifier`**, **`review-risk`**, **`review-resilience`**, **`review-readability`**, **`review-reliability`**, **`review-refuter`** and **`review-validator`** are the review's child sessions. Each runs on its own entry: its backend, its model and its thinking level (the main agent's where the entry sets none). Every lens has its own entry.
- **`permission-classifier`** is the `auto` classifier's model call: its backend, its model and its thinking level (the main agent's where the entry sets none, so by default it runs on the session's model and level).
- **`compaction`** only applies to `anthropic-api`, `opencode-go` and `openai-codex`, the backends that make a request to summarize their history (automatic compaction and `/compact`): that request uses the entry's model and thinking level, and the session's for what the entry omits; every other request is unchanged, and the summary is priced at its own model. The summary always runs in the session's own backend, so it never changes who pays: an entry whose prefix names another backend is dropped whole (neither its model nor its level applies) with a warning, and a prefix equal to the session's backend applies. Worker, explorer and review children on the session's backend get the same entry for their own summaries. On `claude-code`, which compacts on its own, the entry is reported as not applicable and nothing is passed on.
- A level the entry omits sends nothing, as before.

A role whose backend cannot start for lack of its credential fails with an error that names the role and the backend, and nothing retries on the other backend. For a subagent the `task` tool's result is that message, for example `worker: anthropic-api has no API key (No Anthropic API key. Store one with `atelier login api-key anthropic` ...)`. A role that starts but fails on its own backend (Claude Code not logged in) says so: `The explorer subagent failed on claude-code (error): ...`. A review role that fails keeps its usual failure (the verdict `unavailable` with the cause `role_failed`, or a failed verification) and its message starts with the profile role and the backend: `Lens reliability failed: review-reliability: anthropic-api has no API key (...)`. A role that uses the session's own backend fails exactly as before. The orchestrator does the same when its entry (not `--backend`) chose the backend: the CLI prints `error: orchestrator: anthropic-api has no API key (...)` and `session.start` answers with that message; a credential error during a turn (`not_logged_in`, `authentication_error`) reads `orchestrator: claude-code: Claude Code is not logged in. ...`. A role on `claude-code` never gets `ANTHROPIC_API_KEY`, whatever the environment of the session.

What resolution dropped (an unknown role, an unsafe model, an unknown level, a missing pinned profile, a stale `active`) reaches the client in the first turn as recoverable `error` events with the code `profile_warning`, one per report: `<file>: <what was dropped>`. The CLI prints them as `error: ...` without failing the run. If `profiles.json` or a pin changes (or appears, or goes away) after the session started, the session keeps the profile it froze and says so at the start of the next turn, once per changed file, as a recoverable `error` event with the code `profile_changed`: `<file> changed after the session started; this session keeps profile "<name>"` (`was created` / `was removed` instead of `changed` when the file appeared or went away; `the default profile` when no profile was chosen). The same change is not repeated. The compaction entry adds two: `compaction: the summary runs in the session's own backend (<session backend>), so the "<backend>" entry is not used` and `compaction: claude-code compacts on its own, so the compaction entry does not apply`.

The agent cannot write `~/.atelier/` or the local pin: `edit`, `write` and the `bash` sandbox refuse them.

## Model and effort of an open session

The main agent's model and thinking level can change while the session is open, and the history stays: `Session.configure({ model?, thinking? })` in the core, `session.set_model` (`sessionId`, `model`) and `session.set_effort` (`sessionId`, `effort`) in the protocol. `effort` takes the level names profiles use (`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`); anything else is `invalid_command`, as is an empty `model`. Both answer the resulting configuration: `backend`, `model` (absent while the backend's default runs and nothing changed it), `thinking`, `permissionMode`, `profile` (as `session_started` carries it) and `pending`.
- **When it applies:** from the next turn, never in the middle of one. Between turns the backend gets the change at once; a change asked while a turn runs is held (`pending: true`, later changes merge into it) and applied when that turn ends, before its `turn_finished`. The roles that start later (verifier, lenses, worker, explorer, classifier) use the new model where their profile entry sets none. The turn parts of `turn_finished.phases` name the new model and effort from the next turn.
- **claude-code:** `Query.setModel` and `Query.applyFlagSettings({ effortLevel })`, before the next prompt is sent. Minimal goes as `low`; a model that does not take the level clears the effort (`effortLevel: null`). Turning thinking off is refused (`claude-code cannot turn thinking off in an open session.`): the Agent SDK has no way to do it in an open query.
- **anthropic-api:** the next request carries the new `model` and what the level gives there (`output_config.effort`, or `thinking` to turn it off where the model says how). The conversation is sent as it is, so changing the model starts the prompt cache again. The context window is looked up again for the new model.
- **A backend that cannot change a session** (it has no `configure`) makes the command fail with `configure_unsupported` and nothing changes; an unknown session is `unknown_session`; a backend that refuses the change is `configure_failed` and the session keeps its old configuration.
- **`session_configured`:** `{ backend, model?, thinking?, permissionMode, profile? }`, the configuration the session now runs with. It is sent when the model, the level or the permission mode (`session.set_mode`) changed, in the first events of the next turn, or at the end of the turn that applied a held change; a client that ignores it keeps working. A held change that the backend refuses at that point is said as the recoverable `configure_failed` error.
- **`options.list`** (optional `cwd`, like `profiles.list`) answers what a selector offers: `backends` (`[{ "name": "claude-code", "default": "opus", "models": ["claude-opus-5-5", "claude-sonnet-5-5", "claude-haiku-5-5"] }, ...]`: `default` is the model the backend runs when none was chosen, which the newest-first order of `models` does not say; `claude-code`'s also has `aliases`, `{ "opus": "claude-opus-5-5", ... }`, the names that stand for one of its models now, so a client marks the model an alias in use runs; see [the model catalog](models.md)), `models` (`[{ "provider": "claude-code", "model": "claude-opus-5-5", "name": "Claude Opus 5.5", "contextWindow": 1000000, "images": true }, ...]`, `name`, `contextWindow` and `images` each absent when the catalog does not know it: the models of only the backends signed in to now, in the same order; a client names each `provider/model`, the prefix profiles use), `efforts`, `modes`, and what `profiles.list` answers (`profiles`, `active`, and with `cwd`, `effective`). A model outside the lists still works.
  - **Signed in** means what the CLI's check at start finds nothing missing for: Claude Code's own login (`claude auth status --json`, local, about 0.1 s once warm and a few seconds the first time) for `claude-code`; `ANTHROPIC_API_KEY`, the key in `~/.atelier/auth.json` or the Keychain entry for `anthropic-api`; `OPENCODE_API_KEY` or the stored key for `opencode-go`; the ChatGPT sign-in in `auth.json` for `openai-codex`. It is asked again at every `options.list`, so a `/login` or `/logout` shows at the next one. With `ATELIER_LOGIN_CHECK=off` the server asks nothing and offers every backend's models, and the model catalog reads no credential (it asks models.dev only); the echo backend offers none, and so does a check that fails (an unreadable `auth.json`, say), while the rest of the answer stands.
  - **The lists** come from one place, the server's `ModelCatalog` (`catalog` option; `BASE_CATALOG`, which answers `BACKEND_MODELS`, when none is given): `backends` and `models` both read it. A catalog that fails for a backend leaves it its list in the code, so `options.list` never fails for it. `atelier-core serve` gives it the dynamic catalog, the code's list of each backend followed by the models its provider listed (see [model catalog](models.md)); the echo backend keeps `BASE_CATALOG`. The desktop's own selectors read `BACKEND_MODELS` directly.

## Profile of an open session

`session.set_profile` (`sessionId`, `profile`) in the protocol, `Session.setProfile(frozenProfile)` in the core: the session resolves and freezes the named profile again, the way `session.start` does (the name is the first layer, then `profiles.json`, the pins), and keeps it until the next change. It answers the resulting configuration like `session.set_model`, and `session_configured` carries the new `profile` in the same shape as `session_started.profile`. Choosing the profile the session already has freezes it again, which picks up edits to `profiles.json`.
- **When it applies:** from the next turn, never in the middle of one. A turn that is running finishes with the previous profile; the change is held (`pending: true`) and applied when the turn ends, like a held model. From then on the worker and explorer subagents, the verifier, the review lenses, the refuter and validator, the permission classifier and the compaction entry use the new profile. What the new profile dropped (`profile_warning`) and later changes to its files (`profile_changed`) are said in the next turn, once, as at start.
- **Precedence for the main agent:** the new profile's `orchestrator` entry sets the main model and thinking level, through the same path as `session.set_model` and `session.set_effort`, unless the user chose them for this session: `--model`, `session.start.model`, `session.set_model` and `session.set_effort` (or `Session.configure`) win over any profile, now and in later profile changes, as they do at start. An entry that sets nothing leaves the current model or level as they are. On `anthropic-api` the compaction entry also reaches the session's own summary request.
- **No backend change:** if the `orchestrator` entry names another backend than the session's (`anthropic-api/...` on a `claude-code` session, say), the command fails with `profile_backend_change` and nothing changes; the message points at `session.set_backend`, which is a separate step: change the backend first, then set the profile (see [Backend of an open session](#backend-of-an-open-session)).
- **Refusals, all leaving everything as it was:** `unknown_profile` for a name that is not in `~/.atelier/profiles.json` (it says the nearest name; unlike `session.start`, which reports a missing profile and falls back to the next layer, this never swaps in another profile), `profile_unavailable` when the server has no home to read profiles from, `unknown_session`, `configure_unsupported` when the profile would change the main agent and the backend cannot, and `configure_failed` when the backend rejects the change. An empty `profile` is `invalid_command`.

## Backend of an open session

`session.set_backend` (`sessionId`, `backend`, optional `model`) in the protocol, `Session.setBackend(backend, model?)` in the core: the session moves to another backend (`claude-code`, `anthropic-api`, `opencode-go` or `openai-codex`) without closing. Do not combine it with `session.set_profile`: change the backend first, then the profile.
- **What is lost:** the new backend does not get the conversation but a summary of it, like after a compaction (`The conversation history before this point was compacted into the following summary: <summary>...</summary>`, plus the core's `<state>` block), given with the first prompt of the next turn. Detail is lost, and so is the prompt cache: the first request on the new backend reads nothing from the cache. A client should say both before it confirms.
- **How the summary is made:** the backend being left makes it, and the history stays as it is until the new backend is running. `anthropic-api` (and `opencode-go`, its same loop) and `openai-codex` send one summary request over the whole history (the compaction's instruction and format, with the compaction entry's model and level when the profile sets them) and lists the files read and edited; `claude-code` runs its own `/compact` and takes the summary from its `PostCompact` hook. A backend with no `summarize` makes the command fail with `summary_unsupported` instead of inventing one. With nothing said yet in the session there is nothing to carry: the switch happens with no summary (`summarized: false`).
- **The new backend** starts with the session's folder, tools and system prompt, the level the session runs with, and the model: `model` when given (the user's choice, which later profile changes do not override), else the profile's `orchestrator` model when that entry names the new backend, else the backend's default. The old backend is closed once the new one runs, and the summary is saved to Engram when memory is connected, exactly as a compaction summary is (same type, title and per-session key, so a later compaction updates it; the same credential check and warnings, which arrive as recoverable `memory_summary_*` errors in the next turn when the change was made between turns).
- **When it applies:** from the next turn, never in the middle of one. Between turns the change is made when the command arrives, and a prompt sent while it is being made waits for it. While a turn runs the command is held (`pending: true`) and made when the turn ends, before its `turn_finished`; a `session.set_model` asked meanwhile chooses the model of the coming backend. Asking for the backend the session runs on takes back a held change.
- **The answer** is the session's configuration (`backend`, `model` absent while the backend's default runs, `thinking`, `permissionMode`, `profile`, `pending`) plus `backendChange: { from, summarized }`. `session_configured` carries the same `backendChange` once, in the first events of the next turn (or at the end of the turn that made a held change). `turn_finished.phases.handoff` is the summary's cost (it also counts in the totals), in the next turn after the change.
- **Failure:** if the summary or the start of the new backend fails, the session keeps the old backend untouched and the command fails; a held change that fails at the end of the turn is said as a recoverable `error` event with the same code. Codes: `summary_failed` (`The summary of the conversation could not be made, so the session stays on <backend>: <why>`), `summary_unsupported`, `backend_start_failed` (`<backend> could not start, so the session stays on <backend>: <why>`), `same_backend` (the session already runs on it; use `session.set_model`), `unknown_session`, and `missing_api_key` / `keychain_error` when the server cannot create the backend, as `session.start` answers. An unknown backend name is `invalid_command`. A summary that was made and then not used (the new backend did not start) is still charged in the next turn's `handoff` part.
