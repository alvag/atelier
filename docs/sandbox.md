# Sandbox and permissions

The macOS sandbox for `bash`, the permission modes, the command guard and the configuration files.

On macOS every `bash` command of the agent, its workers and the verifier runs under the operating system's sandbox (Seatbelt, through `@anthropic-ai/sandbox-runtime` 0.0.81). It is built for macOS only: elsewhere, or if `sandbox-exec` does not answer, there is no sandbox and the commands fall back to approvals (see below).

## What is isolated and what is not

|         | Agent and workers                                                                                                                                                                                                                                                                                                                                                            | Verifier                                                                                                                                                                                                                                                                                                                                                     |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Writes  | the working directory, the system temporary directory, the session scratch directory and the package managers' caches under your home (`~/.npm`, `~/Library/pnpm`, `~/.local/share/pnpm`, `~/.pnpm-store`, `~/.yarn`, `~/.node-gyp`, `~/.cache`, `~/Library/Caches`), never the home directory itself                                                                        | only its own temporary directory                                                                                                                                                                                                                                                                                                                             |
| Reads   | everything except `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains`, `~/.claude`, Atelier's credentials (`~/.atelier/auth.json`, `~/.atelier/mcp-auth.json`, `~/.atelier/.credentials-tmp`) and other tools' credential files (`~/.codex/auth.json`, `~/.local/share/opencode/auth.json`, `~/.netrc`, `~/.git-credentials`, `~/.config/git/credentials`) | only its directory, the Node installation and the system toolchain (`/usr`, `/bin`, `/sbin`, `/System`, `/etc`, `/dev`, `/opt/homebrew`, `/Library/Apple/usr`, `/Library/Frameworks`), plus the `package.json` of each folder above its directory, which Node looks up to resolve a module; `/Library/Keychains` and the rest of `/Library` are not readable |
| Network | free, as in gentle-shell                                                                                                                                                                                                                                                                                                                                                     | none                                                                                                                                                                                                                                                                                                                                                         |

In the working directory the agent never writes `.env`, `.env.*`, `*.pem`, `*.key`, the git hooks and configuration, shell start-up files and editor or tool configuration (`.git/hooks`, `.git/config`, `.gitconfig`, `.gitmodules`, `.bashrc`, `.bash_profile`, `.zshrc`, `.zprofile`, `.profile`, `.ripgreprc`, `.mcp.json`, `.vscode`, `.idea`, `.claude/commands`, `.claude/agents`), nor the pending steps of a rebase, a cherry-pick or a revert (`.git/rebase-merge`, `.git/rebase-apply`, `.git/sequencer`), nor `.atelier`. The same holds for the git places `git rev-parse` reports for the working directory, asked at each command (and at each `edit` or `write`, once when it is checked and again just before it writes, so a change made while you were asked counts): the hooks directory git runs (`core.hooksPath` included, inside the working directory or not), the `config` and `config.worktree` of the git directory and of the shared one, and the `.git` file of a linked worktree (a `.git` that is a link to a directory protects the same subset as a plain one). Also every file those configurations include (`include.path`, `includeIf.<condition>.path`, read by `git config --file <file> --no-includes` so git's whole syntax counts: quotes, escapes, continuation lines; relative to the including file, `~/` as the home, through included files up to 10 levels, whatever the condition and whether the file exists yet; your global and system configuration are not touched), `info/attributes` and `modules/` (the submodules' git directories). If git cannot read the configuration inside a repository (a broken included file), the same set is derived by reading each repository file alone with `git config --file`, so a broken file elsewhere does not lift the protection; a file git itself cannot read is parsed by a simple fallback parser and its directory's `hooks`, `config` and `config.worktree` are protected too. Outside a git repository only the conventional paths above apply. Below the working directory and each `allowWrite` directory (not one that holds the working directory), no `.git` can be created, replaced, moved or written, whether it is a directory, a file or a link, at any depth: a new or changed one would point git at another repository whose configuration and hooks git runs when someone runs it there. The `.git` at the top of the working directory keeps the narrower protections above, and one that is missing cannot be created there either. The temporary directories are not covered: `git init` in `$TMPDIR` works.

The tool that owns a hidden credential file cannot read it inside the sandbox either: `codex`, `opencode`, `gh`, `claude`, or git and curl when they take a password from `~/.netrc` or git's `store` helper, fail there and work from a command run outside it (`unsandboxed`, with approval, or a `bash` rule). git with the macOS Keychain helper (`osxkeychain`) is not affected. Only those files are hidden: the rest of `~/.codex`, `~/.local/share/opencode` and `~/.config/git` stays readable. No command in the sandbox writes them either, not even under an `allowWrite` directory, and `edit` and `write` refuse them, approved or not; a command a `bash` rule covers may write them, so the owning tool can sign in and refresh its tokens.

Not covered:
- The agent's network is not restricted: a command can reach the network and anything it can read.
- Other platforms: no Linux or Windows code exists.
- The `read`, `edit`, `write` and `grep` tools are not run by the sandbox; code decides what they open, which is a separate mechanism. `edit` and `write` leave `--cwd` only with the user's approval, file by file. `read` and `grep` may leave it but refuse the same secret directories and `denyRead` entries the sandbox hides from `bash`, whether or not the sandbox is running.
- `bash` also runs without `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `OPENCODE_API_KEY`; that filters its environment and is not isolation.

## What you see

At the start of a session (in its first turn) the core emits `{ type: "sandbox_status", sandboxed: boolean, mechanism?: string, reason?: string }`, computed without running a command. The CLI prints `bash: sandboxed (macOS seatbelt)` on stdout, or `bash: not sandboxed (<reason>): every command asks for approval in normal mode, and goes to the classifier in auto mode` on stderr. The desktop shows `bash: sandboxed (macOS seatbelt)` in the status bar, or `bash: not sandboxed` in the warning style with the reason as its tooltip. Subagents do not repeat it.

When a command that failed was blocked by the sandbox, its result says what it tried and why it was stopped, after the exit code:

```
[exit code 1]
[sandbox blocked: write to /Users/ana/notes.txt (not an allowed write path)]
[sandbox blocked: write to /Users/ana/project/sub/.git (git state that runs code)]
[sandbox blocked: read of /Users/ana/.ssh/id_rsa (denied by the sandbox policy)]
[sandbox blocked: network connect to 127.0.0.1:8080 (no network for the verifier)]
```

A denied write in a `.git` of the working directory or of an `allowWrite` directory says `(git state that runs code)`: there the only reason is one of the git protections; anywhere else, and for the verifier, it says `(not an allowed write path)`. The causes come from the sandbox library's own violation report, nothing is guessed: if it reports nothing, nothing is added. At most five causes are listed (then `[sandbox blocked: and N more]`), network first, then writes, then reads; the system's own preference reads are left out. The output truncation rules are unchanged. `tool_call_finished` carries the same causes as `blocked: string[]`; the CLI prints them under the tool line as `  sandbox blocked: <cause>`, and the desktop shows them in the tool row. Limits: only a command that failed is asked; each run is given its own id and the library records its denials under it, so a cause is shown only for the run that produced it, never for an overlapping run of the same text, and a denial the library could not attribute to a run is not shown; and the file denials come from the system log, which can lag, so a block in the first seconds of a session may go unreported.

## Permission modes

`SessionOptions.permissionMode` says what the user is asked before a tool call: `normal` (the default), `auto` or `yolo`. Every `session_started` the session emits carries it as `permissionMode`. No mode asks about a command that runs in the sandbox: it runs, unless it is one of the commands the guard asks about in every mode ("Commands that always ask" below). `normal` asks about what the sandbox does not contain: a command outside it (below), any command when there is no sandbox, and an `edit` or `write` outside the usual places. In `auto`, what `normal` would ask is decided by a classifier instead (below). `yolo` asks nothing there: those run too (the guard's confirmations, except a plain `git push` or `git rebase`, still ask), and an `edit` or `write` outside the working directory is allowed for the rest of the session as if approved. An `mcp_call` to the user's MCP servers is asked of the classifier in `auto` only, and runs without asking in `normal` and `yolo` ([MCP](mcp.md#how-the-agent-uses-them)). In every mode the destructive command guard refuses first, the protected paths (secrets, git state, `.atelier/`, `~/.atelier/`, the feature documents) are refused without asking, and subagents run in `normal` whatever the parent's mode. In the CLI, `--mode <mode>` picks the mode and `-y`/`--yes` is a deprecated alias of `--mode normal`; the protocol's `session.start.autoApprove` is ignored.

What the model is told about `yolo`: the gates enforce every mode, and a session that starts in `yolo` also gets a short block in its system prompt saying what it covers. Commits, pushes and pull requests within the task go ahead without asking; the guard's destructive confirmations still ask; yolo covers the task given, so the agent asks before widening its scope; it never answers a question meant for the user or gives a consent on the user's behalf, in text or with a tool; and subagents run in `normal`. The system prompt does not change during the session, so a later change of mode (`/mode`, `session.set_mode`) is said at the head of the next prompt the model gets, once: the same block on entering `yolo`, and `The session left yolo mode: its rules no longer apply, and tool calls ask as in normal mode again.` on leaving it. A change between `normal` and `auto`, or one undone before the next prompt, says nothing. A note counts as said once the model took its prompt: when the backend fails before that, the next prompt carries it again. A compaction or a change of backend carries the latest of those notes in its state, so the model does not lose it with the history. A saved session keeps what the model was last told, so one resumed in another mode gets the note in its first prompt.

Order of the question: the core calls `approve` (and the review `consent` callback) only after the client has read every event emitted before it, `approval_requested` (or `review_consent_requested`) included, and asked the turn's iterator for the next one, so a client prints what came first, such as `auto: undecided`, before it asks. A client must therefore keep reading while the question is open. If the turn ends before that (the client stopped reading, or the turn was interrupted), the callback is not called: the call is denied and the review consent counts as not answered.

The `auto` classifier (`SessionOptions.permissionClassifier = { createBackend, timeoutMs? }`; `atelier-core serve` gives every session one, on the session's own backend) handles each call whose gate would ask the user, except a command the guard asks about, which asks you and never reaches it. It makes one separate model call, in a child session with no tools that never sees the whole conversation, with the user's prompt of the current turn verbatim, the tool, the command and the agent's `reason` when there is one. After the first turn it also gets, for context, the previous turn: the user's prompt verbatim and the agent's last message (its text after its last tool call, the last 4000 characters), so a short follow-up such as "go ahead" accepts only what that message proposed. The agent's text (that message, the tool and the command, each in its own block, and the `reason`) reaches it with `&`, `<` and `>` escaped as `&amp;`, `&lt;` and `&gt;`, so it cannot open or close the prompt's blocks or pass itself off as the user's request. It answers only `{ "decision": "allow" | "deny", "reason": "..." }`, with the reason, which the user reads, in the language of the user's request, judging whether this one action stays within what the user asked: when in doubt it denies, the agent's `reason` is a claim and never shows on its own that the user asked for something, earlier approvals are not precedent, and it never allows what destroys data, publishes or touches credentials unless the request clearly asks for exactly that. `allow` runs the call without a question (an `edit` or `write` outside the working directory stays allowed for the session, as in `yolo`). `deny` asks nobody and fails the call with `Denied by the permission classifier (auto mode): <reason>. Do not retry the same action; find another way to do what the user asked, within the request, or ask the user.` It fails closed: a timeout (60 s), an error, an invalid or missing answer, an interrupt, or a session with no classifier backend asks the user as `normal` does. After 3 denials in a row, 20 in the turn or 3 failures in the turn the classifier stops for the rest of the turn and every such call asks the user; the counters start again with each turn, and an allow resets only the denials in a row. Every classified call emits `{ type: "permission_classified", callId, decision: "allow" | "deny" | "undecided", reason, paused?: true }` before it runs or is refused: `undecided` carries the failure (`classifier unavailable: <why>`) or the pause (`paused after 3 denials in a row`, `paused after 20 denials in this turn`, `paused after 3 failures in this turn`, with `paused: true`) and means the user is asked next. Its model calls are the `classifier` part of `turn_finished.phases` (role `permission-classifier`). Subagents run in `normal`, so they never use it.

The default mode for new sessions is the file `~/.atelier/permission-mode.json`, `{ "kind": "atelier.permission_mode", "version": 1, "default": "normal" }` (`default` is `normal`, `auto` or `yolo`), which the agent cannot write (`~/.atelier/` is protected). `readDefaultPermissionMode(home)` and `writeDefaultPermissionMode(home, mode)` in the core read and write it (the write goes through a temporary file and a rename). A missing file is `normal`. A file that is invalid (not JSON, another `kind` or `version`, a `default` that is not one of the three modes, or unreadable) is also `normal`, and the first turn of the session says so once, as a recoverable `error` event with the code `permission_mode_invalid`: `<file>: <reason>; using normal`. `SessionOptions.permissionModeProblem` carries that message for other clients. `Session.setPermissionMode(mode)` changes the mode of that session for its next tool calls (never its subagents, which stay in `normal`), and the later `session_started` events carry the new mode. In the protocol, `session.start` takes an optional `mode` (`normal`, `auto` or `yolo`; anything else is `invalid_command`); without it the server reads the default file from its home directory (the user's home when the server has none) and gives the session that mode, and the warning above when the file is invalid. `autoApprove` is still accepted and ignored. `session.set_mode` (`sessionId`, `mode`) changes the mode of a running session and answers `{ "mode": "<mode>" }`; an unknown session is answered `unknown_session`.

In the CLI the session's mode is `--mode <normal|auto|yolo>`; an unknown value is a usage error (`--mode must be normal, auto or yolo.`, exit 2). Without `--mode` the CLI reads the default file from its home directory (the user's home when it has none) and shows a recoverable error when the file is invalid. `-y`/`--yes` is an alias of `--mode normal` that prints `warning: --yes is deprecated: normal, the default mode, already runs sandboxed commands without asking; use --mode` once on stderr; with `--mode` too, `--mode` wins. In an interactive session `/mode` prints `mode: <mode>`; `/mode <mode>` changes the session's mode (`mode: <mode> (this session)`); `/mode default <mode>` saves the default file without changing the running session (`default mode: <mode> (saved in ~/.atelier/permission-mode.json)`); anything else after `/mode` prints `usage: /mode [normal|auto|yolo] | /mode default <normal|auto|yolo>` on stderr and changes nothing. The header gets `· mode <mode>` when the mode is not `normal`. In `auto` the CLI prints what the classifier decided on its own line, before the tool's result line, as `  auto: allowed — <reason>`, `  auto: denied — <reason>` (the command does not run and nothing is asked) or `  auto: undecided — <reason>; asking you` (the question follows as in `normal`); a subagent's line is indented like its tool lines, and the reason, which comes from a model, shows invisible and control characters as visible markers. The classifier's cost is the `classifier` part in the `phases:` line under the turn's tokens. `--help` says that `auto` sends what `normal` would ask to a classifier model (the session's unless the profile's `permission-classifier` role sets one), which allows or denies it, and that you are asked when it cannot decide.

In the desktop, the toolbar's `mode` selector (`default`, `normal`, `auto`, `yolo`) is sent as `session.start.mode` for the next session, and `default` sends none, so the core applies the saved default. While a session is open the status bar shows its mode, from the main agent's `session_started.permissionMode` (a subagent's is ignored), as a selector: choosing another sends `session.set_mode` (`sessionId`, `mode`; answered with `{ mode }`) and the bar shows the mode the core answered, keeping the previous one and showing the error if the command fails. `yolo` is shown in the warning style. A broken default file arrives as the recoverable `error` event `permission_mode_invalid`, shown like any other error. In `yolo` the desktop shows no approval card for a command outside the sandbox or an `edit`/`write` outside the working directory, because nothing is asked; a command the guard asks about still shows its card (`Run this command? (guard: recursive removal)`), except a plain `git push` or `git rebase`. The `auto` option of both selectors has the tooltip `auto: a classifier model decides what normal would ask`. In `auto` the tool row shows what the classifier decided, from `permission_classified` (matched by `callId`, also for a subagent's row), as `auto: allowed — <reason>`, `auto: denied — <reason>` (warning style) or `auto: undecided — <reason>; asking you` (the approval card follows as in `normal`); the reason comes from a model, so it is shown as plain text, never as HTML or markdown, with invisible and control characters as visible markers. The classifier's cost is the `classifier` line in the turn's folded cost breakdown.

The `bash` tool has two optional inputs, `unsandboxed: true` and a required `reason`, with which the agent asks to leave the sandbox for one command (for example to install dependencies with network access). In `normal` the user is asked, and in `auto` too when the classifier does not decide (below), and sees the reason (CLI: `Run this command OUTSIDE the sandbox?`, then the command and `reason: ...`; desktop: a card titled `Run this command outside the sandbox?` that shows the reason; the `approval_requested` event carries `reason`, and `confirm` too when the guard asks about the command). Without a terminal the CLI refuses it (`bash command asks to run outside the sandbox and needs your approval, but there is no terminal to ask (--mode yolo allows it): <command>`, then `reason: <reason>`). A missing or blank `reason` is `Invalid input: reason is required with unsandboxed: ...`, and the verifier's `bash` refuses it (`Refused: the verifier's bash cannot run outside the sandbox — <command>`).

Without a sandbox (another platform, a sandbox that fails to start, `--no-sandbox` or `ATELIER_SANDBOX=off`; `SessionOptions.noSandbox` for other clients) every command asks in `normal` (in `auto` the classifier decides, and the user is asked when it cannot; in `yolo` it runs, except when the sandbox failed to start, below), and the verifier gets no `bash`. A sandbox that failed to start on macOS (its library or a dependency failed, or its socket folder was refused) is not a choice of the user's, so `yolo` does not take it as leave to run commands without it: every command asks there as in `normal`, also one the agent sends with `unsandboxed: true`, so a denied command cannot come back that way without a question. Its `approval_requested` (and `ApprovalRequest`) carries `sandboxFailed: true`. Without a terminal the CLI denies it, in every mode, and says `bash command needs approval and there is no terminal to ask; the sandbox failed to start: <command>` (with `unsandboxed`, the usual message without `(--mode yolo allows it)`), since `--mode yolo` would not let it run either. Another platform, a nested sandbox and a sandbox turned off still run in `yolo` without asking. The core emits `{ type: "sandbox_warning", reason }` once per turn, before the first question of the turn that runs `bash`. The CLI prints `warning: bash runs without a sandbox (<reason>): every command asks for approval in normal mode, and goes to the classifier in auto mode` on stderr, except in the turn whose start already printed the `bash: not sandboxed` line (one line, not two); the desktop shows it in the turn with the same text, and as the tooltip of `bash: not sandboxed` in the status bar. Without a terminal the CLI denies such a command and says `the sandbox is off or unavailable (--mode yolo allows it)`.

## Rules you allowed

A question about a `bash` command outside the sandbox (`unsandboxed: true`, or any command without a sandbox), or about an `edit` or `write` outside the working directory, can be answered `Allow`, `Allow in this session`, `Allow always` (or `Allow always in this project`, see below) or `Deny`. `Allow in this session` and the `Allow always` answers remember a rule, so the next command it covers is not asked about and does not fail in the sandbox first. The session needs `SessionOptions.permissionRules` (a `PermissionRules`, given the user's home) for this; without it only `Allow` and `Deny` exist. Subagents share the parent's rules.

A rule is a program, or a program and its subcommand, read from the command as the guard reads it (assignments, redirections, heredoc bodies and the wrappers `env`, `command`, `nohup`, `timeout`, `nice`, `time`, `xargs` are passed over). The subcommand is the first argument when it is a plain lowercase word; otherwise the rule is the program alone, which covers every use of it. The program is compared as written (`/usr/bin/open` is not `open`). A line is covered only when each of its commands is. Examples:

| Command                                | Rules                                       | `Allow always`  |
| -------------------------------------- | ------------------------------------------- | --------------- |
| `ego-browser nodejs <<EOF ...`         | `ego-browser nodejs`                        | yes             |
| `mkdir -p x && ego-browser nodejs ...` | `mkdir`, `ego-browser nodejs` (both needed) | yes             |
| `open file.png`                        | `open`                                      | yes             |
| `npm install foo`                      | `npm install` (not `npm publish`)           | in this project |
| `node script.js`                       | `node`                                      | no              |

Never covered, so always asked: a line with a `$(...)` or backtick substitution (also in an unquoted heredoc body), a process substitution `<(...)`, `eval`, `source`, `.`, a shell given `-c`, a control structure (`for`, `if ... fi`, `case`, `{ ... }`), a program named by a variable or a glob, a command behind more than 8 wrappers (see `nested too deeply` below), a redirection that writes a file (`>`, `>>`, `&>`; `/dev/null` and `2>&1` are fine), any mention of `.atelier` or `permissions.json`, an environment assignment before the command or on its own (`PATH=./bin open x`, `env FOO=1 npm test`, `env -P ...`, `PATH=./bin; open x`), the builtins that change what later commands run (`export`, `declare`, `typeset`, `local`, `readonly`, `alias`, `set`, `unset`, `shopt`, `trap`), runners of another command (`caffeinate`, `stdbuf`, `arch`, `watch`, `script`, `parallel`, `flock`, `chroot`, `unbuffer`, `ionice`, `taskset`, `sandbox-exec`), `find` with `-exec`, `-execdir`, `-ok` or `-okdir`, `git` with an option or subcommand that runs other code (`-c`, `--config-env`, `--exec`, `-x`, `--upload-pack`, `--receive-pack`, `--extcmd`, `submodule foreach`, `bisect run`, `filter-branch`, `difftool`, `mergetool`), and an interpreter or shell named among the arguments after the subcommand (`open -a Terminal bash`). A subcommand named like an interpreter (`ego-browser nodejs`) is covered only by the rule that names it, never by the program's alone, and a shell subcommand given `-c` never. A command the guard asks about ("Commands that always ask") is never covered and its question offers only `Allow` and `Deny`; the refused commands stay refused. Interpreters and launchers of arbitrary code are offered `Allow in this session` but never `Allow always`: `node`, `nodejs`, `deno`, `bun`, `python`, `python3` and their versions, `pypy`, `pythonw`, `py`, `julia`, the shells (`bash`, `sh`, `zsh`, `dash`, `ksh`, `fish`, `csh`, `tcsh`), `ruby`, `irb`, `perl`, `php`, `lua`, `osascript`, `awk`, `tclsh`, `expect`, `pwsh`, `Rscript`, `npx`, `pnpx`, `bunx`, `uvx`, `sudo`, `npm exec`, `npm x`, `pnpm dlx`, `pnpm exec`, `yarn dlx`, `yarn exec`, `pipx run` and `uv run`, also behind a wrapper (`xargs node`). A launcher subcommand counts wherever the program's options put it (`pnpm -C . dlx foo` is `pnpm dlx`), and only the rule that names it covers it: a rule `pnpm`, allowed always for `pnpm -r build`, never covers `pnpm dlx` or `pnpm exec` (nor `npm` `npm exec`, `yarn` `yarn dlx`, `pipx` `pipx run`, `uv` `uv run`).

Commands that run code the repository defines are offered `Allow always in this project` instead of `Allow always`, never a rule for every folder, so allowing `npm install` once never runs a freshly cloned repository's `postinstall` outside the sandbox: the whole program, whatever its subcommand (a rule `pnpm` from `pnpm -r build` too), for `npm`, `pnpm`, `yarn`, `make`, `gmake`, `just`, `rake`, `gradle`, `mvn`, `cargo`, `go`, `pip`, `pip3`, `poetry`, `pdm`, `hatch`, `uv`, `composer`, `bundle`, `mix`, `dotnet`, `swift`, `xcodebuild`, `cmake`, `ninja`, `pytest`, `tox`, `nox`, `vitest` and `jest` (also as an absolute path, `/opt/homebrew/bin/npm`), and any program written as a relative path (`./gradlew`, `bin/dev`, `scripts/build.sh`). Their launchers keep their own rule and stay for the session (`pnpm dlx`, `npm exec`, `uv run`, ...); `bun` is an interpreter. A line with one of them and no interpreter offers the project for all its rules (`mkdir -p x && pnpm install` keeps `mkdir` and `pnpm install` for the project). A rule allowed in a project covers a command only when no command of the line can take it elsewhere, whatever rule covers that other command (`printf '%s' /tmp | make -f -` is asked about): never a line with `cd`, `pushd` or `popd`, nor one with a word that may name a place outside the project, failing closed: any `..`, `~`, `$` (a variable such as `$HOME`), backtick, `{` (a brace list) or unquoted glob (`l?nk`, `lin[k]`, `l*`), or an absolute path by itself or attached to an option or a value (the program itself may be absolute: a rule `/usr/bin/make` covers `/usr/bin/make -C .`; one with `..` in it, `../other/gradlew`, never) (`pnpm -C /other install`, `make -C../other`, `make -f../other/Makefile`, `make -C "$HOME/other"`, `pnpm --dir=/x install`, `npm install file:../lib`); nor one with a command behind `xargs`, whose input adds arguments the words do not show; nor a command whose standard input the line gives, which can be code the words do not show (`make -f - <<'EOF'`, `make -f - <<< 'include ...'`, `make -f - < file`, also attached as in `make -f -<file`, `printf ... | make -f -`, also `|&` and into a subshell, where every command of the line counts as given input), while `pnpm test 2>&1 | tail -5` stays covered; nor one with a word (or what follows any `=`, `:`, `@` or `,` in it, any point of a cluster of short options, `-kCdir`, or a program written as a relative path) that names, relative to the working directory, a place whose real path is outside the checkout the session works in (the project, or the linked worktree of it the session runs in), followed through every link up to its nearest existing folder, and a dangling link to where it points, a part at a time as the system does, so a `..` after a link goes up from where the link leads (`pivot/../victim` where `pivot` leads out; `make -C link` where `link` leads to another checkout, or `touch out` where `out` is a dangling link to `/tmp/x`); a link that loops or a place that cannot be read counts as outside; those are asked about.

Beyond those bounds, a rule allowed in a project covers a line only when every argument of every command of it, after its quotes are taken off, is a simple word; any other line is asked about (session and global rules cover it as before). A simple word has only letters, digits and `. _ - @ + , : %` (`*` and `?` only quoted); `/` only inside a relative path, never first, after `=`, `:` or `,`, nor in an option (`-I/x`, `-C/x`, `-f/x`); no two dots in a row anywhere (`..`, `-kC..`, `foo@../x`; three or more, as in `go test ./...`, are fine) and nothing starting with `~`; no space, tab, line break or control character; and `=` only in a long option `--name=value` whose value is a simple word too, never an assignment `NAME=value`, as an argument or before the command. The words before the command count too: a wrapper's options (`nice -n 10 make` is covered, `nice -n ' 0' make` is asked about). Redirections (`2>&1`, `>/dev/null`) are not arguments. Some options run code whatever their value and a project rule never covers them: `make` `--eval` and `-E`; `npm`, `pnpm` and `yarn` `--node-options`, `--script-shell`, `--shell`, `--userconfig` and `--globalconfig` (and `pnpm` `--config.<key>`); `cargo` `--config` and `-Z`; `go` `-exec` and `-toolexec`; `gradle` and `./gradlew` `--init-script` and `-I` (a short one also in a cluster, `-kE`; a long one also under any prefix of it, as npm and make take them: `--script-shel`, `--ev`). Covered, with a project rule for the program: `pnpm test`, `pnpm -r build`, `pnpm --filter "@app/*" build`, `npm run lint -- --fix`, `make -j4 test`, `make -C sub`, `cargo test -p foo`, `go test ./...`, `pytest tests/unit -k smoke`, `vitest run src/a.test.ts`, `./gradlew build`, `pnpm test 2>&1 | tail -5`. Asked about: `make MAKEFLAGS=-I/tmp/x`, `make -I/tmp/x`, `make --include-dir=/tmp/x`, `make --eval='include /tmp/x.mk'`, `make -E 'x'`, `make CC=/tmp/cc`, `make V=1`, `npm --node-options=--require=/tmp/x run test`, `cargo --config 'build.rustc-wrapper="/tmp/x"' build`, `pytest --rootdir=/tmp`, `pnpm test "a b"`.

The list is not complete: a program that runs a project's code and is not in it is still offered `Allow always`.

Known limits of a project rule: it trusts the project's content and your environment. The project's files and links are trusted as its code is, which the agent can edit anyway; the rule only keeps a command from being pointed at another project or at a freshly cloned repository. So:
- A link inside the project that leads out of it is seen only where the command line names it, resolved from the session's working directory. A program that changes its own directory first is not followed: in `make -C sub -f evil.mk`, where `sub/evil.mk` is a link out of the project, `evil.mk` is resolved from the working directory, not from `sub`, and the makefile outside runs.
- The environment you start Atelier with reaches the covered command as it is: `MAKEFLAGS`, `MAKEFILES`, `npm_config_*` and the like, exported by you, can change what it reads or runs. Only an assignment written in the command line itself is asked about.
- Links are resolved when the coverage is decided: a link changed between that moment and the command's start is not seen.

For `edit` and `write` the rule is the file's folder (its real path), which covers the files in it and below for both tools; when that folder is `/`, your home or a folder that contains it, the rule is the file alone. `Allow` keeps today's meaning: that one file for the rest of the session. The protected places (secrets, other tools' credential files, git state, `.atelier/`, `~/.atelier/`, the feature documents) are refused before any rule is looked at, so no rule reaches them. `web_fetch` and `web_search` never ask, so they have no rules.

What a `bash` rule does in each mode: in `normal` the command is not asked about, in `auto` it does not reach the classifier, and in every mode, `yolo` included, it runs outside the sandbox from the start, even when the agent did not set `unsandboxed`. It runs under a macOS profile that allows everything except writing `~/.atelier` (by its name, its real path or through a link), so a command a rule covers cannot change the rules or the default mode, and except what the main sandbox never lets a command write because it runs code later or holds secrets, read at each command as the sandbox reads it: the git hooks and configuration (`core.hooksPath` and the included files too), the pending steps of a rebase, cherry-pick or revert, a `.git` below the working directory (creating or replacing one, or writing in one that exists), the shell start-up files, the editor and tool configuration, `.atelier`, and the secret files (`.env`, `.env.*`, `*.pem`, `*.key`) of the working directory and the `allowWrite` directories (see "What is isolated and what is not"); each is denied by its real path too, and, as the main sandbox does, none of them nor any folder above them (the working directory and `.git` included) can be moved or replaced, so a place cannot be renamed, written under another name and put back. A covered command that writes `.git/hooks/pre-commit` fails. Where that profile cannot run (another platform, or inside another sandbox) rules cover nothing, the question is asked, and it offers only `Allow` and `Deny` (no `remember`) for `bash`; an `edit` or `write` outside the working directory still offers its folder rules, which do not depend on it. The result of such a command ends with `[ran outside the sandbox: the user allows <rules> there without asking; do not set unsandboxed for it]`, and the system prompt lists the rules saved when the session starts: `The user allows these bash commands outside the sandbox without asking: <rules>. They run there on their own: do not set unsandboxed for them.` (with `In this project the user also allows these bash commands outside the sandbox without asking: <rules>.` before the last sentence for the project's rules).

`Allow in this session` keeps the rule in the core's memory: it is gone when the session closes or is resumed. `Allow always` saves it in `~/.atelier/permissions.json`, yours and never the repository's, so a repository cannot give itself permissions; it applies in every folder and to every session, read again at each decision. The file is `{ "kind": "atelier.permissions", "version": 1, "allow": [{ "bash": "ego-browser nodejs" }, { "path": "/Users/ana/notes" }] }`, written with mode `0600` through a new temporary file and a rename (two processes saving at the same moment can still lose one rule).

A rule for a command that runs code the repository defines is never saved for every folder: `Allow always in this project` saves it in `~/.atelier/project-permissions.json`, also yours and never the repository's, with the project's real path: `{ "kind": "atelier.project-permissions", "version": 1, "allow": [{ "bash": "pnpm test", "project": "/Users/ana/code/app" }] }`. It covers that command only in sessions whose project is that path. The project is settled when the session opens, from its working directory followed through symbolic links: the git checkout that holds it (a subfolder counts as its checkout; a linked worktree counts as its main checkout, so every worktree of a repository shares its rules, but only when the main checkout knows it: its `.git` file (a plain file, never a link) must point into the main checkout's `.git/worktrees/`, at a folder whose `gitdir` points back at that same `.git` file, otherwise the folder holding the `.git` is its own project; a submodule is its own project; inside a bare repository, the repository: a folder with `HEAD`, `objects/` and `refs/` (links followed) is its own project unless its `config`, also followed through a link, says with certainty that `core.bare` is false; a missing `config`, one that is not a regular file (a pipe or a device is never waited on) or one with no `core.bare` counts as unclear; `core.bare` is read as git reads it: only in the `[core]` section, the last value wins, `true`, `yes`, `on`, `1` or the key alone, comments left out, quoted text read as git reads it; a folder that looks like a bare repository whose `config` cannot be read with certainty, with a backslash anywhere, an unclosed quote, a header or a line that is no section, key or comment, or a `bare` that is no boolean (`maybe`), ends the search and is its own project, from any folder in it, never the checkout around it), or the working directory itself outside git. It is read from the files git leaves; git is never run for it. These rules are in a file of their own so an Atelier that does not know them keeps reading `permissions.json` as before. A broken project file is ignored whole like the other (`<file>: <reason>; no saved project rule is used`), and the rules of `permissions.json` keep working.

The agent cannot write either file: `edit` and `write` refuse `~/.atelier`, the sandbox does not let `bash` write the home, and a covered command runs under the profile above. A file that is not valid (not JSON, another `kind` or `version`, an unknown key, an entry that is not one `bash` or `path`, a `bash` entry that is no command rule, writable by other users, not yours) is ignored whole, never overwritten, and said once per session as the recoverable `error` event `permission_rules_invalid`: `<file>: <reason>; no saved rule is used`. An entry of `permissions.json` that is a valid rule no longer allowed in every folder (a command that runs code the project defines, such as `npm install` saved by an earlier Atelier, or an interpreter) is not used, the others are, and the file keeps it; the session says it once as the recoverable `error` event `permission_rules_ignored`: `<file>: not used in every folder anymore, as they run code the project defines or any code given to them: "npm install". Allow them again in a project if you want, and remove these from the rules list`. An `Allow always` that cannot be saved (that broken file, or an interpreter's rule a client sent anyway) is kept for the session and said as `permission_rules_not_saved`. `approval_requested` and `ApprovalRequest` carry `remember: { rules, always, project? }` when the answer can remember: `always: false` offers no `Allow always`, and `project` (the project's real path) offers `Allow always in this project` in its place, for a line one of whose commands runs code the project defines and none of whose runs arbitrary code; `approve` may answer `true`, `false` or `{ remember: "session" | "project" | "always" }`. A `project` or `always` answer the question did not offer is kept for the session and said as `permission_rules_not_saved`. `Session.permissionRules()` lists the rules in force (`{ id, scope: "session" | "project" | "always", kind: "bash" | "path", value, project?, ignored? }`: the session's first, then this project's with their `project`, then those of every folder, and last the saved ones no longer used, with `ignored: true`) and `Session.removePermissionRule(id)` removes one. `PermissionRules` takes the session's `cwd` to know its project; without it nothing is offered for a project.

In the protocol (all additive; the version stays 7, and a client that knows none of it keeps offering `Allow` and `Deny`): `approval_requested` carries `remember`; `session.approve` takes an optional `remember` (`"session"`, `"project"` or `"always"`, anything else is `invalid_command`), used only with `approved: true` and when the question offered it (`project` only when `remember.project` is set, `always` only when `remember.always` is true, otherwise the rules are kept for the session and `permission_rules_not_saved` says so); a client that does not know `project` offers only the session for those questions; `session.permissions` (`sessionId`) answers `{ rules: [{ id, scope, kind, value, project?, ignored? }] }`; `session.permissions_remove` (`sessionId`, `ruleId`: an `id` from that list) removes that rule and answers the rules left, or fails with `unknown_rule` (`rules_not_saved` when the saved file cannot be written, as when it is broken). `atelier-core serve` gives every session the rules of its home directory (the user's home when it has none) and the project of its `cwd`.

## Turning it off

`--no-sandbox` or `ATELIER_SANDBOX=off` runs `bash` without the sandbox, with the behavior above. `atelier-core serve` honors `ATELIER_SANDBOX=off` for every session, and `session.start` accepts `noSandbox: true` for one session (that is how a client such as the desktop starts one without it). In the desktop it is the `run bash without the sandbox` checkbox in the toolbar, unchecked by default, which applies to the sessions opened while it is checked; such a session shows `bash: NOT SANDBOXED (turned off)` in the warning style in the status bar from the moment it opens, in place of the usual sandbox line. With the sandbox off the configuration files below are not read or validated.

## Commands that are always refused

Before the sandbox and before any approval question, in every mode, for every caller (the agent, its workers and the verifier), following gentle-shell's destructive command guard: recursive removal (`rm -r`) of `/`, of `~` or `$HOME`, or of the project directory (or a directory that contains it, `.` and `./*` included), and a `find` (or `gfind`) from one of those places that deletes (`-delete`, or `-exec`/`-execdir`/`-ok`/`-okdir` running `rm`, also behind `env` or `command`), unless it has a `-name`, `-iname`, `-path`, `-ipath`, `-wholename`, `-regex` or `-iregex` test whose pattern does not match everything (a glob that is not just `*` and `?`; a regex with at least one literal character outside bracket classes, quantifiers, intervals, anchors, groups, alternatives and `.`, where an escaped punctuation character such as `\.` or `\/` counts as literal and a literal inside a group or made optional by `?`, `*` or `{0,` does not, and any alternative `|` makes it not narrow, so `'.*\.log'` narrows while `'.*.*'`, `'.{0,}'`, `'(.*)'`, `'.*|x'`, `'.*x?'`, `'(x)?.*'` or even `'[^/]*'` and `'[a-z]*'` do not) and that comes before the deleting action (so `find . -name '*.log' -delete` still runs, while a `!`, `-not`, `-o`, `-or` or `,` anywhere in the expression voids the narrowing, and `-type`, `-mtime`, `-print` or parentheses do not count as narrowing and `find . -mtime +30 -delete` is refused); `mkfs*`; `dd` with `of=/dev/...` (not `/dev/null`, `/dev/stdout`, `/dev/stderr`, `/dev/tty`); fork bombs (`:(){ :|:& };:` and any function that pipes itself into itself in the background); recursive `chmod`/`chown` on `/`; `git reset --hard`, `git clean` with `-f` or `--force` (also in a cluster such as `-fd` or `-xdf`, even with `-n`), and a force push (`git push` with `--force`, `-f` or a cluster containing it, `--force-with-lease`, or a `+src[:dst]` refspec), long options also as any prefix git accepts (`--ha`, `--fo`, `--force-w`), with git's global options before the subcommand (`git -C dir`, `-c key=value`, `--config-env`, `--no-pager`), as gentle-shell always denies them; and `sudo` and `su` as a command of any segment (also behind `env` and `env -S "..."` (split into words like `env` does, with its `\_`, `\t` and quote escapes (`\c` does not end the string: every word is judged), and judged as one command together with the arguments that follow; shell operators inside the string are just text), `nohup`, `timeout`, `xargs`, `sh -c`, `eval`, `find -exec`, `$(...)`, backticks and redirections written before the command, `2>&1` and `{fd}>file` included). The tool result is `Refused: <rule> — <command>` (the rules are `recursive removal of /`, `recursive removal of the home directory`, `recursive removal of the project directory`, `mkfs`, `dd to a device`, `fork bomb`, `recursive chmod/chown on /`, `git reset --hard`, `forced git clean`, `force push`, `sudo`, `su`) and nobody is asked. `git reset --soft`, `git clean -n`, a plain `git push` and a command that only mentions them (`grep "git reset --hard"`, `echo git push --force`) are not refused.

A `\` before a newline joins the lines as the shell does (`git re\` + newline + `set --hard`), also in an unquoted heredoc body (where it can join a line with the terminator), except inside single quotes, a comment or a quoted heredoc body, and a quote inside a heredoc body is text; such a command is judged both joined and as written. It only knows recognizable forms: text in quotes or in a heredoc is data (a `<<` outside quotes, comments and `$((...))`, not `<<<`, whose delimiter is the whole word after it with its quotes removed, as the shell builds it (`<<'EOF'x` ends at `EOFx`), and whose body ends at the first line that is that delimiter, with leading tabs for `<<-`; with no such line it is not data), except the `$(...)` and backticks of a heredoc whose delimiter is unquoted, which the shell runs and the guard judges like any other (inside `<<'EOF'` or `<<"EOF"` nothing runs), and it does not read pipes (`echo / | xargs rm -rf`), heredocs passed to a shell, redirections to a device, a bare `*`, or scripts. What it does not recognize is not refused by it; the sandbox is the next layer.

## Commands that always ask

A second category of the same guard, following gentle-shell's confirm list, is not refused but asked about in every mode, inside the sandbox or not: the command is one the sandbox cannot make safe, because what it deletes or publishes is the project's own work or leaves the machine. The `bash` gate gives it an approval with `confirm: "<rule>"`, `approval_requested` carries the same `confirm` (`{ type: "approval_requested", callId, command, reason?, tool?, confirm? }`) and so does `ApprovalRequest` (`confirm?: string`); several rules are joined with `, ` (`recursive removal, git push`). The rules:

| `confirm`                | Matches                                                                                                                                                                                                                                                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `recursive removal`      | `rm` with `-r`, `-R` or `--recursive` (or a prefix, `--rec`), anywhere, the project included (of `/`, `~` or the project itself it is refused, above)                                                                                                                                                                  |
| `find deletion`          | `find`/`gfind` with `-delete`, or `-exec`/`-execdir`/`-ok`/`-okdir` running `rm`                                                                                                                                                                                                                                       |
| `SQL deletion`           | `psql`, `mysql`, `mariadb` or `sqlite3` given (as an argument, the value of a long option such as `--command=`/`--execute=` or a prefix of one, a heredoc, or piped from `echo`/`printf`) a `DROP TABLE/DATABASE/SCHEMA/INDEX/VIEW`, a `TRUNCATE`, or a `DELETE FROM` with no `WHERE` or with `WHERE 1=1`/`WHERE TRUE` |
| `git push`               | `git push`, also with global options (`git -C dir push`)                                                                                                                                                                                                                                                               |
| `git rebase`             | `git rebase`                                                                                                                                                                                                                                                                                                           |
| `forced branch deletion` | `git branch -D`, `-df`, or `--delete --force` (or prefixes)                                                                                                                                                                                                                                                            |
| `npm publish`            | `npm publish`                                                                                                                                                                                                                                                                                                          |
| `nested too deeply`      | a command behind more than 8 levels of nesting, where each wrapper (`env`, `nohup`, `xargs`, ...) and each command line run by another (`sh -c`, `eval`, `find -exec`, `$(...)`) is one level: the guard reads no deeper, so it asks, and no rule covers it                                                            |

It is recognized by command position, like the refusals: in every segment of a compound command, behind wrappers (`env`, `command`, `nohup`, `timeout`, `xargs`, ...), in `sh -c`, `eval`, `find -exec`, `$(...)` and backticks, with line continuations joined as for the refusals (a command split with `\` and a newline is never waived in `yolo`). Text that only mentions a command (`grep "git push" file`, `echo git push`, a quoted argument, a heredoc body) is data and asks nothing. A catastrophic command is refused first, and nobody is asked.

How each mode treats it:
- `normal` and `auto` ask you. `auto` does not send it to the classifier: it is never decided by a model.
- `yolo` asks too, except for the reversible delivery gentle-shell's YOLO waives: a plain `git push` (remote and refs as plain words, `src:dst` refspecs, and only `-u`/`--set-upstream`, `-q`/`--quiet`, `-v`/`--verbose`, `--tags`, `--follow-tags`, `--no-verify`, `--porcelain`), a plain `git rebase` (plain refs, `--onto`, `--continue`, `--abort`, `--skip`, `--autostash`; not `-i` or `--exec`), `git -C <path>` before either, output redirections that write nothing (`2>&1`, `>/dev/null`) and a pipe into `tail`, `head`, `cat`, `grep` or `wc`. Each segment is judged on its own: `git push && rm -r data` still asks for the `rm`. A force push is refused (above); `--delete`, `:branch` refspecs, `--mirror`, `--prune`, `--all`, `-o`, `--receive-pack`, `git -c ...`, a push inside `sh -c`, `xargs`, `$(...)` or in the background, and every other rule always ask. `gh pr create` is not in the list, so it asks in no mode.
- Subagents always run in `normal`, so a worker's `rm -r` asks. The verifier's `bash` is the exception, as it is for every question: it runs in a throwaway copy of the tree, so it is not asked.
- The CLI asks `Run this command? (guard: recursive removal)` (`Run this command OUTSIDE the sandbox? (guard: ...)` with a `reason`); without a terminal it denies the command and says `bash command matches a guard rule (<rule>) and needs your approval, but there is no terminal to ask: <command>`. The desktop card has the same title.

A force push, `git reset --hard` and a forced `git clean` are not asked about: they are always refused (above). Shell recognition here is lexical, like the refusals: it is not a sandbox.

## Configuration files

Two optional files add to the agent's policy and never to the verifier's: `~/.atelier/sandbox.json` (yours) and `<cwd>/.atelier/sandbox.json` (the project's), each `{ "allowWrite"?: string[], "denyRead"?: string[] }`. A path is absolute, `~/...`, or relative to the file's base (your home for yours, the working directory for the project's). The files only add, and never remove a fixed protection. An `allowWrite` entry that is, contains or lies inside a protected place (your home itself, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/Library/Keychains`, `~/.claude`, `~/.atelier`; so `~`, `/` and any parent of home too, also through a symbolic link) is refused, and the secret file patterns and the git and shell files above also hold inside every added directory. Other tools' credential files (`~/.codex/auth.json` and the rest of the list above) are not refused that way, so an entry such as `~/.local/share` stays valid, but they stay unwritable inside it.

A file that is invalid (not JSON, not an object, an unknown key, a value that is not an array of non-empty strings, a refused entry) stops the CLI before anything runs (exit 1, `error: Invalid sandbox configuration <file>: <problem>`) and fails `session.start` of `atelier-core serve` (`session_start_failed`, same message). A file that becomes invalid later makes each `bash` command fail with `[sandbox error: Invalid sandbox configuration <file>: <problem>]` and run nothing. It is never ignored, because that would silently widen or narrow what commands can do.

**Caveat:** the project file lives in the repository, so a repository you do not control can ship one that makes more places writable for the agent, everywhere except your home directory itself, the protected places above and `~/.atelier`. Read it before you trust the project.

## Running as root

As root (uid 0), the CLI and `atelier-core serve` refuse to start (exit 1) unless `ATELIER_ALLOW_ROOT` is exactly `I accept the risk`: `error: Atelier will not run as root (uid 0): a mistaken command could damage the whole system. To run as root anyway, set ATELIER_ALLOW_ROOT="I accept the risk" (exactly that text).`, plus `ATELIER_ALLOW_ROOT is set to "<value>", which is not that exact text.` when it is set to something else. With the exact text they start and print `warning: running as root (uid 0) because ATELIER_ALLOW_ROOT is set: every command has full control of this system.` on every start (the server prefixes both with `atelier-core: ` on stderr). `--help` and `--version` still work as root.

## Known limits

- `git config` and `git branch -u` fail inside `bash` (the library protects `.git/config`).
- `git init`, `git clone` and `git worktree add` into a folder of the working directory, `git submodule update`, and commits or any other write in a repository nested in it fail inside `bash` (`Operation not permitted`), because each writes a `.git` below the working directory; the agent asks to run them outside the sandbox, with your approval. In `$TMPDIR` they work.
- Rebase, cherry-pick and revert cannot run inside `bash`: the pending steps of one (`rebase-merge/`, `rebase-apply/` and `sequencer/` in the git directory, `.git/` or a linked worktree's own directory under `.git/worktrees/<name>/`) are never writable, whether they exist or not, because an `exec` line in `rebase-merge/git-rebase-todo` would run when you later `git rebase --continue` outside Atelier. `git rebase`, a `git cherry-pick` or `git revert` of several commits (which keep their steps in `sequencer/`) and their `--continue`/`--abort` fail with `Operation not permitted`; the agent asks to run them outside the sandbox, with your approval. Commit, branch, stash, merge (with or without conflicts), tag and deleting packed refs keep working.
- In a linked git worktree (`git worktree add`), whose git data lives in the main checkout's `.git`, the agent may also write that worktree's own directory there (`.git/worktrees/<name>`) and the repository's `objects`, `refs`, `logs`, `packed-refs`, `packed-refs.lock` and `packed-refs.new`, so branches, commits and packing refs work without leaving the sandbox. What would make git run code or work on another repository stays protected: the shared `hooks` (and the hooks directory git actually runs, `core.hooksPath` included, as `git rev-parse --git-path hooks` reports it), `config` and `config.worktree`, `objects/info` (alternates), and the worktree's own `config.worktree` (a `core.hooksPath` there would run a hook the next time you commit, outside the sandbox), `commondir`, `gitdir` and `hooks`; the secret file patterns hold in those directories too, and nothing else of the main checkout becomes writable. `git gc` and `git repack`, which update `objects/info`, need to leave the sandbox. The worktree's git directories are asked from `git rev-parse` once per working directory and checked against the files git keeps for a worktree (its directory must be `<common>/worktrees/<name>`, and its `gitdir` file must point back at the worktree), so a tampered `commondir` grants nothing.
- The verifier's `git` is the real one of the active developer directory (found once with `xcrun --find git`), first on its `PATH`, with that directory's `usr/` readable and no system or global git configuration (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`): the `/usr/bin/git` shim cannot run there, because it writes a cache in your per-user temporary folder. Its commands also get `TMPDIR` inside its own directory (`<dir>/.tmp`), set in the command, so tests that create temporary directories work, and a `HOME` of their own (`<dir>/.home`, with `XDG_CONFIG_HOME` under it), because your home is not readable and tools such as git read their configuration from home even when a caller clears the `GIT_*` variables; the library's own `/tmp/claude` stays writable but the verifier cannot read `/tmp`. It also reads `/private/var/select`, where macOS records the shell `/bin/sh` runs and the developer directory, and the time zone: the time zone database in `/private/var/db/timezone` and the `/var` link itself (not what it leads to), through which `/etc/localtime` leads, so tools such as `diff -u` that resolve it link by link get no denial. Without a developer directory the verifier has no `git`. Atelier's own suite passes inside the verifier's sandbox, apart from the tests that need a real sandbox, which are skipped there.
- Each command costs about 16 ms more (about 63 ms the first one).
- macOS cannot nest sandboxes. An Atelier that already runs inside one (Atelier running its own tests from a sandboxed command) finds out by trying the smallest sandbox there is and reads macOS's refusal; it then reports `already inside a sandbox, and macOS cannot nest them: commands stay confined by the outer one` and takes the unavailable path (every command asks, the verifier gets no `bash`). Nothing in the environment can claim this. The tests that need a real sandbox are skipped there and run in a normal `pnpm check`.
- The library is "Beta Research Preview" and global to the process; the sandbox is not reset until the process exits.
- The library's proxy listens on a Unix socket it makes in the temporary folder, whose path macOS limits to 104 bytes. When `TMPDIR` is too long for it (the socket path `<TMPDIR>/srt-mux-<pid>-0.sock` over 103 bytes), the library starts with Node's `os.tmpdir()` answering `/tmp/atelier-<uid>`, made with mode `0700` if it is missing, and `os.tmpdir()` goes back as soon as the library has started, even if it fails. Only that function changes, never the `TMPDIR` variable, so a process started meanwhile (a `bash` command of another session, an MCP server, the memory server) gets your `TMPDIR`. A link there, or a folder of another user or that others can open, is refused, also when it changes before the library starts (it is checked again right then), and the sandbox is unavailable with the reason `/tmp/atelier-<uid> is not a directory of this user's own (mode 0700)`. A start that takes more than 10 s gives the folder back and leaves the sandbox unavailable with `the sandbox did not start within 10 s`, and so does a reset while it starts (`the sandbox was reset while it was starting`). The library's start goes on alone, but Atelier keeps it: when it finishes, started or failed, the library is reset, so no proxy or socket is left running, and a reset that comes after it finished waits for that. The next start waits for it too (up to the same 10 s, or it fails with `an earlier start of the sandbox has not finished`), because the library is one per process: there is never more than one start of it at a time. A reset also voids every start under way or still waiting to begin: none of them starts or keeps the library, and they answer `the sandbox was reset while it was starting`. Atelier's own temporary directories and their sweep never run during that moment: they wait for it, and it waits for them, so they always go in your `TMPDIR`, as do the full results of an MCP call outside a session. The commands themselves still get the library's `TMPDIR=/tmp/claude`, as always.
