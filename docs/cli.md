# CLI reference

The `atelier` command: options, output, the interactive TUI and the line-by-line session.

## Options and output

```bash
atelier "add email validation to src/user.ts and run the tests"   # one turn
atelier                                                          # interactive; /exit or Ctrl+D to quit
```

In a clone of the repository, `pnpm atelier` runs the clone's own CLI the same way.

| Option                             | Effect                                                                                                                                                                                                                                                                                               |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--mode <mode>`                    | Permission mode of the session: `normal` (default), `auto` (what `normal` would ask goes to a classifier model, which allows or denies it; you are asked when it cannot decide) or `yolo` (see [Permission modes](sandbox.md#permission-modes)). Without it, the default saved with `/mode default`. |
| `-y`, `--yes`                      | Deprecated alias of `--mode normal`; prints a warning on stderr.                                                                                                                                                                                                                                     |
| `--backend <name>`                 | `claude-code` (default, Claude subscription) or `anthropic-api` (Atelier's own loop, billed to the API key).                                                                                                                                                                                         |
| `--model <name>`                   | Model to use (default: `opus` on `claude-code`, `claude-sonnet-5-5` on `anthropic-api`).                                                                                                                                                                                                             |
| `--profile <name>`                 | Agent profile for this session (see [Agent profiles](profiles.md#agent-profiles)); `--model` and `--backend` still replace the main agent's.                                                                                                                                                         |
| `--cwd <dir>`                      | Working directory (default: current directory).                                                                                                                                                                                                                                                      |
| `--continue`                       | Resume the newest saved session of the working directory (see [Saved sessions](sessions.md)).                                                                                                                                                                                                        |
| `--resume <id>`                    | Resume that saved session of the working directory; `--model`, `--mode` and `--profile` replace what it saved.                                                                                                                                                                                       |
| `--no-session`                     | Do not save this session; it cannot be resumed. Not combined with `--continue` or `--resume`.                                                                                                                                                                                                        |
| `--no-fullscreen`                  | Run the interactive TUI in the terminal's main screen, under what was there, instead of the full screen (over `tui.fullscreen` in the [settings](#settings)).                                                                                                                                        |
| `--no-review`                      | Do not review changes or verify them (same as `ATELIER_REVIEW=off`).                                                                                                                                                                                                                                 |
| `--no-sandbox`                     | Run `bash` without the macOS sandbox (same as `ATELIER_SANDBOX=off`).                                                                                                                                                                                                                                |
| `-h`, `--help` / `-v`, `--version` | Help and version.                                                                                                                                                                                                                                                                                    |

Output starts with the main agent's header, `atelier · <backend> · <model> · <auth>`, plus `· effort <level>` when a thinking level was asked and `· mode <mode>` when the mode is not `normal`, and a line with the session's profile (repeated with every header): `profile cheap (local-pin) · verifier claude-code/claude-sonnet-5-5 thinking medium`, its name, the layer it came from and what it sets for each role but the main agent, or `profile default` when none applies. The first turn then says what the session loaded: `instructions: <paths>` and `skills: <names>` (see [Skills](architecture.md)), with a warning for each skill that has a problem, `skill <path>: <message>`. Then streamed text, one line per tool call (`▸ edit src/user.ts (1 edit) ✓`) and the turn's tokens: input, output, cache reads and writes, the share of the prompt served from the cache (`cacheRead / (input + cacheRead + cacheWrite)`), the number of model requests and the cost. A `cache miss` line says why the prompt cache could not be reused. When the backend reports it, the tokens line also says how full the context is (`context 45,000 / 200,000 (23%)`). A turn with more than one part (the main agent plus the risk declaration, the verifier or a review) gets a compact line under it with each part's cost and requests, or its tokens when neither is known, and, when the part says who ran in it, `on` and each distinct model with its effort, prefixed by its backend only when it is not the session's: `phases: main $0.0400 (1 req) on claude-opus-5-5 high · verify $0.0021 on codex/gpt-5.5 medium · lenses 2 req on claude-sonnet-5-5 medium, claude-haiku-5-5`. When no level was asked and the backend says the effort it applied, the model shows it as `effective`: `main 1 req on claude-opus-5-5 effective xhigh`. In the interactive session, `/compact [instructions]` summarizes the older history now; `/mode` prints the session's permission mode, `/mode <mode>` changes it for this session and `/mode default <mode>` saves the default for new sessions (see [Permission modes](sandbox.md#permission-modes)). On `claude-code`, a warning appears when the session is not using a Claude subscription.

Exit codes: `0` ok, `1` failed turn, `2` usage error, `130` interrupted.
## Subcommands

A subcommand is the first word, exactly and unquoted; anything else is a prompt, so `atelier "update the readme"` is a prompt. A subcommand takes no session options (`--model`, `--mode`, `--cwd`...): with one, or with extra words, it is a usage error (exit 2) that prints its usage.
- `atelier update [vX.Y.Z | --main]` moves a copy installed with `install.sh` to the newest release, or to the one given (older too): `git fetch --tags`, a detached checkout of the tag, then `pnpm install --frozen-lockfile --prod` (the full install, and a rebuild of the desktop, when the desktop is installed). It prints `Updated atelier v0.1.0 → v0.2.0`, or `atelier is already at v0.2.0`. It refuses, changing nothing, a development clone (`error: atelier update only updates a copy installed with install.sh; <dir> is a development clone (use git there).`), a copy with local changes and a release that does not exist (listing the ones that do). If the install fails it goes back to the previous release, reinstalls that release's dependencies (the same variant, so `node_modules` is not left half way between both) and says how to retry; if that reinstall fails too, the message adds `Reinstalling the dependencies of <version> failed too: ...` and `Repair them with: cd '<dir>' && pnpm install --frozen-lockfile --prod` (without `--prod` when the desktop is installed); if only the desktop rebuild fails, the CLI stays updated, the old desktop build is removed (so `atelier desktop` never opens a different version) and the message says to retry with `atelier desktop`, which builds it when the output is missing.
  `atelier update --main` puts the copy on the latest `main` of GitHub instead (`git fetch --tags`, a fetch of `main`, a detached checkout of `origin/main`'s commit, the same install, rollback and desktop rebuild). It prints `Updated atelier v0.1.0 → main (20c5424)` (seven-character short id), or `atelier is already at main (20c5424)`, and adds the line `channel=main` to the install marker (`.git/atelier-install`, next to `desktop=`). While the marker says so, `atelier --version` prints `atelier 0.2.0 (main 20c5424)` and the update messages name the current commit `main (20c5424)`. A later `atelier update` or `atelier update vX.Y.Z` goes to a release, even one older than `main`, and removes the line. `--main` takes no version and is valid only with `update`; otherwise it is a usage error (exit 2).
- `atelier mcp list` connects to every enabled server of `~/.atelier/mcp.json`, waits for each (up to its `timeout`), prints each server as `<name> (<transport>): <state>` with its tools on the next line, a failed server's error and the end of its stderr, each invalid entry and each problem of the file, then stops the servers. It exits with 1 when an entry is invalid, the file has a problem or an enabled server is not connected, and prints `No MCP servers: configure them in <file>.` when there are none. `atelier mcp login <server>` signs a remote server in with OAuth: it prints `Signing in to <server>: the browser opens the authorization page; waiting for it…`, opens the page, and prints `Signed in to <server>.` once the browser came back and the server connects; `atelier mcp logout <server>` deletes the sign-in (`Signed out of <server>.`). Both exit with 1 and `error: <why>` when they cannot. In a session, `/mcp login <server>` and `/mcp logout <server>` do the same and connect the server again; any other words after `/mcp` print `usage: /mcp | /mcp login <server> | /mcp logout <server>`. They take no options; to give a prompt that starts with "mcp", quote it. See [MCP servers](mcp.md).
- `atelier stats [--since 7d|30d|all|YYYY-MM-DD] [--project <dir>] [--by day|project|model|phase|role] [--json]` shows what the saved sessions of `~/.atelier/sessions` spent: the period's totals (cost, turns, requests, input, output and cache tokens) and a breakdown by day, by project (the working directory), by model, by phase (the parts of a turn of `turn_finished.phases`, then `subagent`) and by role (the profile role of the agents of each part: `orchestrator`, `verifier`, `review-risk`..., and the subagent's name, `explorer` or `worker`, for a subagent's turns). `--since` takes a number of days back from now, a date (from that local midnight on) or `all` (default `30d`); `--project` keeps one working directory (`.` is the current one); `--by` prints only that breakdown; `--json` prints the same as one JSON object for scripts (`since`, `sessions`, `total`, `byDay`, `byProject`, `byModel`, `byPhase`, `byRole`, `skipped`, each row with `key`, `turns`, `requests`, `usage`, `billedUsd`, `subscriptionUsd` and `unpriced`). Costs are never guessed: what a backend billed per use (an API key) is `billed`; what Claude Code reports on a subscription is shown apart as `≈$X sub`, an API-equivalent figure that is not billed and is not added to `billed`; a turn, part or subagent's turn whose backend reported no cost counts as `unknown`, never as `$0`. The total leaves `billed` out when nothing was billed and something else was. A part of a turn where several models or roles ran (the lenses, the verifier and its correction) is split by the turns those roles saved (the verifier's and each review role's own `turn_finished`, with their model and cost); what they do not explain goes to the part's other agents, and stays a `mixed` row, explained under the table, only when those still differ. A turn is dated by its `at` (the time it ended) and, in sessions saved before `at`, by the session's start. A subagent's turns are not in its parent's `turn_finished`, so they are added to the totals and to the parent's day and project; the verifier's and the review's are already in its parts. It only reads, one file at a time and line by line, parsing only the lines that hold a configuration or a turn's cost; it writes nothing and uses no network. A file whose header is not a session's, with another format version, or with a line it needs that is not JSON (other than the last one, cut by a crash) is skipped; the text ends with `Skipped N session files: ...` and `--json` lists them in `skipped` with the reason. A bad `--since` or `--by`, a session option, or `--since`, `--project`, `--by` or `--json` without `stats`, is a usage error (exit 2).

  ```
  atelier stats · last 30 days · 2 sessions · 2 projects

  Total    $1.50 billed · ≈$3.00 subscription (API-equivalent, not billed) · 1 turn with no known cost
           3 turns · 14 requests
  Tokens   in 1.2k · out 3.4k · cache read 2.1M · cache write 50k

  By day       cost                     turns   requests     in    out   cache r   cache w
  2026-10-20   $1.50                        1         12   1.2k   3.4k      2.1M       50k
  2026-10-21   ≈$3.00 sub · 1 unknown       2          2     20     40         0         0
  ```
- `atelier desktop` opens the desktop app in the same version as the CLI and returns at once (`Opened Atelier desktop 0.1.0`). In an installed copy without the desktop, the first time it runs the full install and `pnpm -C atelier-desktop build` (Electron, about 200 MB), then records it; it builds again when the build is missing. In a clone it only builds, with the dependencies the clone has.

The installed copy is marked by `.git/atelier-install` (key=value lines, `desktop=0` or `desktop=1`), written by `install.sh`.

## Interactive TUI

Without a prompt, when stdin and stdout are both terminals, the session runs in a terminal interface built on [pi-tui](https://github.com/earendil-works/pi) (see [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)). It runs full screen, in the terminal's alternate screen: the terminal starts clean, the header (`Atelier 0.2.0 · ~/code/app` and the model with its level) and the transcript scroll in the space above, and the editor and the footer stay fixed at the bottom. The transcript follows new output while the view is at its end and stays where it is once scrolled up, with a `↓ Jump to latest · Ctrl+End` label that goes back to it; the mouse wheel, PageUp and PageDown scroll it, Ctrl+Home and Ctrl+End go to its start and end, and Ctrl+Shift+F searches it. Text dragged over with the mouse is selected and copied to the clipboard (OSC 52) when the button is released; since the TUI takes the mouse, the terminal's own selection usually needs a modifier key (Shift in most terminals, Option in iTerm2). On exit the terminal gets its screen back and the header and the transcript are printed in it, without the editor or the footer. `--no-fullscreen` (or `"fullscreen": false` in the [settings](#settings)) runs it in the terminal's main screen instead, under what was there, with the transcript in the terminal's scrollback. The core runs as a separate process (`atelier-core serve`) and the TUI speaks the protocol with it, as the desktop does; `--no-sandbox` and `--no-review` reach it as `ATELIER_SANDBOX=off` and `ATELIER_REVIEW=off`, and `--continue`/`--resume` go through `sessions.list` and `session.resume`, then `--mode`, `--profile` and `--model` are applied to the resumed session.
- **Transcript:** one blank line between each prompt, the agent's text, each block of calls, each card, each note (such as `/status`'s) and the turn's end, never two; each prompt as a full-width block on a subtle background, `›` before its first line and the rest lined up under it (the terminal's own background made a little lighter, or darker on a light one, once the terminal says it; the palette's bright black until then or when it does not; after `❯`, without a background, when there is no color), the agent's text as Markdown after a bold `●`, its other lines under the text, so it stands apart from the dimmed activity (a code block with a language highlight.js knows, like ` ```ts `, ` ```bash ` or ` ```json `, has its tokens colored; one without a language, with another one or without color shows as plain text), and the calls the agent makes between two of its texts as one dimmed block, with the model's thinking among them when the backend sends it (see [thinking display](profiles.md)): dimmed, italic and magenta after `✻`, or `✻ Thinking…` while it is folded; Ctrl+R opens or folds all of it, and a folded block shows its thinking above its line. Full screen, a click on a block opens or folds that block alone, and a click on its thinking opens or folds that thinking; what a click changed holds until the next Ctrl+O or Ctrl+R, which open or fold everything again (a click and a drag still select text). While a call runs, the block shows it in one place, replaced by the next one, with what is done so far: `⎿ ◐ bash pnpm test…  (ran 2 commands · read 1 file)`; a `task` call shows the call its subagent runs, `◐ task worker · edit src/a.ts…`. Then the block folds to one line, `⎿ Ran 3 commands · read 1 file · edited 1 file` (`searched`, `fetched`, `ran N subagents` and `used N other tools` for the rest; a file read or edited twice counts once), and keeps in sight under it every call that failed, `✗ bash pnpm test · exit 1` (a subagent's too, `✗ worker · edit a.ts · …`), and what the sandbox blocked. Ctrl+O opens every block into its calls, each as a card, `▸ bash pnpm test · exit 0 ✓` (`✗` when it failed, what the sandbox blocked under it); a `task` call has a line with its subagent, `└ worker · claude-sonnet-5-5 · 3 tools`; the verifier and each review role get the same line under the step that ran them. Ctrl+O also expands or folds every card (and the verifier's, below): the whole command, an edit's removed and added lines, the start of a written file, the subagent's prompt, its tool calls and its last text, and where a truncated output was saved. The rest of the events show as the line-by-line CLI prints them, except the ODD phase, which only the footer shows, and the feature's progress: the `feature` tool's calls show only when they fail, and of `feature_changed` only a dimmed `◆ now T2 Footer` when the task in progress changes, and what the session runs with as usual: the header and profile lines, `bash: sandboxed (…)`, `instructions: …`, `skills: …` and `memory: …` are left to `/status`, which prints the newest of each (a later `bash: not sandboxed` or `no memory` replaces what it said before) and the session's cost so far (`cost: $0.0745 this session`). Their warnings and errors still show, and so does whatever runs with less protection: `bash: not sandboxed`, `no review: …` and, when the session starts in `yolo`, `mode: yolo · what normal mode would ask runs without asking`. Each turn ends with `◇ 12.3s · 3 requests · 14:42`, the local time it ended at in hours and minutes as the system writes them (`2:42 PM` in a 12-hour locale), and its phases, both without prices (`phases: main 1 req on claude-opus-5-5 high · verify 2 req on codex/gpt-5.5 medium`): the TUI shows no prices in the transcript, neither in the cards, the reviews, the verifications nor a compaction; the cost is in the footer and in `/status`. Text from the model, a file or a tool shows control characters as markers.
- **ODD:** over the editor, the active feature (from the main agent's `feature_changed`) folded in one line, `◆ M14 – TUI · 1/5 done · now T2 Hot profile · Ctrl+T or /feature: tasks`; Ctrl+T or `/feature` opens it into a table of every task's ID, state and deliverable, the task in progress marked `▸`, and folds it again (with no feature active, they say so). The footer's `T2 1/5` comes from the same events and the same count. A new or resumed session starts with no feature shown until its own events say one, and the panel stays open or folded as it was. Each review is one block in the transcript that grows with it: its risk level, how many lines in how many files and its lenses (`◇ review high · 12 lines in 2 files · lenses risk, reliability`, or `· no review due`), why, the lenses' reason, what the agent declared and the base; `waiting for your answer` while the consent question is open, or `· allowed for this session` when the user answered `Review all this session` earlier; every `review_progress` step (`· lens risk done · 2 findings`, `· refuting 2 findings`); a line for each role's work; and the result: the verdict with the correction, the follow-ups left (`✓ review approved · 1 follow-up`, `✗ review escalated: …`), each blocking finding (`F1 blocker src/a.ts:3 — claim`) and the receipt's path, relative to the working directory when it is inside it. Each verification is a card that grows with its rounds, folded like the tool cards and opened with them by Ctrl+O: `▸ verify · items 2, 6 · round 2…` (the round running until it ends), a line for the verifier's work, each round as the line CLI says it (`round 1 · 1 defect (major) · 1 met, 1 unmet · asking the agent to fix them`) with its verdict on every requirement (`✓ S1 met · …`, `✗ S2 unmet · …`, `? S3 unverified · …`) and its defects (`D1 major · yolo accepted`), and how it ended (`✓ verify passed after a correction · 2 rounds`, `✗ verify: needs your decision · …` with the open defects). Open, the card adds what the agent declared, each requirement's evidence and how to reproduce each defect. A verification that ends needing your decision shows, even folded, the evidence of the last round's requirements not met or not verified and how to reproduce each open defect, as the line CLI does; the rest stays folded.
- **Footer:** the status line, fixed under the editor. By default: model and effort, the working folder's name, the git branch (read from the repository's `HEAD`, without running git but honoring `GIT_CEILING_DIRECTORIES` as git does (split on `:`, or `;` on Windows, symlinks resolved), when the TUI starts and after each turn, so a branch the agent switched to shows), profile, mode, sandbox, how full the context is, the session's cost, the ODD phase and the task in progress with the tasks done (`claude-opus-5-5 high · atelier · main · profile claude · auto · sandbox ✓ · ctx 34% · $0.42 · implementing · T2 2/5`); its items and their order are chosen in `~/.atelier/settings.json` (see [Settings](#settings)). It starts with what `session.start` (or `session.resume`) answered, follows every change made from the TUI, and fills in the rest as the session's events say each part; an item not known yet is left out, and the line is cut to the terminal's width.
- **Editor:** a band on the same background as the prompts, with `›` before the text and a dimmed `Ask Atelier to do anything` while it is empty (without color, between two lines and without the placeholder); multi-line, with history (Up/Down), a paste kept as one prompt, and completion of `/model`, `/effort`, `/profile`, `/mode`, `/backend`, `/feature`, `/mcp`, `/permissions`, `/new`, `/resume`, `/review`, `/undo-correction`, `/compact`, `/status` and `/exit` (and of paths). While a slash command runs (a list, a backend move, `/new` or `/resume` starting), Enter does not send and what was typed stays in the editor. While a turn runs, Enter queues what was typed as a steer, which the agent gets with its next tool result (or, when the turn ends before another tool runs, as a turn of its own), and Alt+Enter queues it as a follow-up, which runs as a turn of its own once the turn ends well (with no turn running, Alt+Enter sends like Enter); a slash command typed then is not queued and stays in the editor (`commands run when the turn ends; it stays in the editor`). Over the editor, the queue shows one dimmed line per message, cut to the width (`↳ steer: use tabs`, `↳ follow-up: now the docs`; five at most, then `… 2 more`), and `Alt+↑ edit`. Alt+Up takes the whole queue back into the editor, before what it holds and each message apart from the next by a blank line, to edit and send again; an interrupted or failed turn gives it back the same way, and none of it runs. A queued message shows in the transcript as a prompt when it enters the conversation. When the core does not take a message (`session.queue` fails, as with `turn_ended` while an interrupted turn ends), it goes back to the editor with the error. Terminals that do not send Option as Alt (Terminal.app unless "Use Option as Meta key" is on) leave Alt+Enter and Alt+Up out.
- **Selectors:** `/model`, `/effort`, `/profile`, `/mode`, `/backend` and `/resume` without an argument open a list from `options.list` (or `sessions.list`) that starts on the one in use, marked `current` (the file's `active` profile is marked `active`, each mode says what it does); Up/Down and Enter choose, Esc changes nothing. With an argument (`/model claude-sonnet-5-5`, `/effort high`, `/profile cheap`, `/mode auto`, `/backend anthropic-api`, `/resume <id>`) they skip the list. A change counts from the next turn and says so (`model: claude-sonnet-5-5 from the next turn; the prompt cache starts over`); the footer shows what the core answered. `/backend` asks first, starting on Stay, because the new backend gets a summary of the conversation instead of the conversation (detail and the prompt cache are lost). `/new` starts another session with the mode in use and what was chosen on the command line or with the lists (the model is dropped after a backend change); `/resume` lists the folder's other saved sessions that can be resumed, newest first (`name or last prompt   3h ago · 4 turns · claude-opus-5-5`), and shows the chosen one's transcript. Either way the new session goes under a `── new session ──` or `── resumed session ──` rule, the one before stays on screen, and it is closed once the new one runs; if the new one fails to start, the old one goes on. A new session whose chosen level the core refuses is closed, the old one goes on, and the level is not asked for again. A slash command with more arguments than it takes prints its usage (`usage: /model [name]`) and is not sent to the model.
- **Questions:** an approval (`Run this command?`, `Edit a file outside the working directory?`, ...) and the review consent are a list in a frame, with the same text the line-by-line CLI asks (a subagent's approval adds `(asked by worker)`). A command's approval shows only its first line with text, cut to one row, with `… 2 more lines (Ctrl+O)` when there is more (every line of the reason to leave the sandbox included); Ctrl+O opens the whole command and folds it again. An approval whose answer can be remembered lists `Allow`, `Allow "<rules>" in this session`, `Allow "<rules>" always` (only when offered; `edits in <folder>` for `edit` and `write`) and `Deny`, sent as `session.approve` with `remember`; `/permissions` and `/permissions remove <n>` work as in the line-by-line CLI, over `session.permissions` and `session.permissions_remove` (see [Rules you allowed](sandbox.md#rules-you-allowed)). An approval starts on Allow and, for its first 400 ms, its choices take no key (Ctrl+O still works), so a key typed before it appeared does not answer it; neither does the rest of a paste begun before it, in the editor say; Esc denies. The review consent, `Review this high-risk change?`, shows only its three answers (`Review this change`, `Skip this time`, `Review all this session`, each with what it does, dimmed; see [review](review.md)), starts on `Review this change` behind the same 400 ms guard, and Esc skips. Up/Down and Enter choose, and a paste answers nothing, however many chunks the terminal splits it into. Questions still open when the turn ends or is interrupted go away: the core has denied them.
- **Keys:** Esc interrupts the running turn (and gives the queue back to the editor); Ctrl+C interrupts it, and with no turn running clears the editor or, when it is empty, quits (exit 130); Ctrl+D on an empty editor and `/exit` quit (exit 0). Ctrl+T opens or folds the feature panel, as `/feature` does. Ctrl+R opens or folds the model's thinking. Quitting closes the session and then the core; if the core does not answer `session.close` within 3 seconds, the core is closed anyway. Shift+Tab takes the mode between `normal` and `auto` (from `yolo` it goes to `normal`; `yolo` is only chosen by name or from `/mode`'s list), shown in the footer at once; when the newest change is refused, the footer goes back to the last mode the core accepted, and the answers of a session the TUI has left change nothing. Strings from events (agent, tool and model names, guard rules, footer fields) and from the lists show control characters as markers, as in the line CLI.

The TUI also tells the terminal what it is doing, so terminals like Orca show it as an agent with a live state: it sets the title to `Atelier - <working directory name>` and reports `idle`, `working`, `blocked` (while the core waits for an approval or a review consent), `done`, `error` or `idle` again (interrupted) with the OSC 7501 Program Status Protocol, and clears it on exit. Terminals that do not answer the protocol are not sent anything.

Inside a Herdr pane (`HERDR_ENV=1`, a `HERDR_PANE_ID` and a `HERDR_SOCKET_PATH` that is a Unix socket), the TUI also reports itself to Herdr through that socket as the agent `atelier` (source `atelier`), its state first, since Herdr takes a resume command only from a reporter that holds the pane: `pane.report_agent_session` with the session's id at start and whenever it moves to another session (`/new`, `/resume`, `/backend`), with the command `atelier --resume <id>` when the session is saved; `pane.report_agent` with `working` while a turn runs, `blocked` while the core waits (`Approval awaiting input` or `Review consent awaiting input`, never the command or the question) and `idle` at start and when a turn ends; and `pane.release_agent` on exit. Herdr derives `done` from `working` followed by `idle`. Herdr 0.9.5 shows the pane as `atelier` with that state, over its own detection of the Claude Code backend's process, and leaves the pane with no agent after `/exit`; it answers the session report but keeps neither the session's id nor its resume command (it keeps a session only for the agents it knows), so it does not resume Atelier after a restart: run `atelier --resume <id>` or `atelier --continue` yourself. A Herdr that does not answer within 500 ms, then 1500 ms, or answers an error, is ignored. The TUI starts its core with `ATELIER_HERDR_PANE=<pane id>`, which the commands of its tools inherit: an Atelier started from one of them in the same pane reports nothing, so it does not take the pane over. Line mode, a prompt run, the desktop and subagents never report to Herdr.

While a turn runs, the ODD task in progress (the one the footer shows) goes to the pane's metadata as `◐ <ID> <title>` (source `atelier:activity`), in the tokens `summary` and `summary2`: two rows at most, each as wide as Herdr's sidebar less 5 columns (24 when Herdr's `session.json` does not say), the first broken between words (inside the title's first word when that does not fit) and the second ending in `…` when the title is cut, each within Herdr's limits of 80 characters and 128 bytes, `…` included, and without control or bidi characters. It lives 30 seconds and is reported again every 10 seconds while the turn runs; both tokens are cleared when no task is in progress, when the turn ends and on exit. To show them, add the rows to the Agents layout in Herdr's `config.toml`:

```toml
[ui.sidebar.agents]
rows = [
  ["state_icon", "machine", "workspace", "tab"],
  ["agent"],
  ["$summary"],
  ["$summary2"],
]
```

### Settings

`~/.atelier/settings.json` sets how the TUI looks and when it notifies, and whether your prompts go to memory; every field is optional (`fullscreen` is `true` and `hideThinking` `false` unless set):

```json
{
	"kind": "atelier.settings",
	"version": 1,
	"tui": {
		"fullscreen": true,
		"hideThinking": false,
		"statusLine": [
			"model",
			"effort",
			"cwd",
			"git-branch",
			"profile",
			"mode",
			"sandbox",
			"context",
			"cost",
			"phase",
			"task"
		],
		"notifications": {
			"enabled": true,
			"via": "auto",
			"sound": false,
			"minSeconds": 10
		}
	},
	"memory": {
		"prompts": true
	}
}
```

`memory.prompts: false` keeps your prompts out of long-term memory, like `ATELIER_MEMORY_PROMPTS=off`, in the TUI, the line-by-line CLI and the desktop alike; it is read when each session starts. While memory is on, prompts are saved unless the variable or this field says no; a file that cannot tell (not JSON, another `kind`, a `prompts` that is not `true` or `false`) keeps them out too.

`hideThinking: true` starts the model's thinking folded to `✻ Thinking…`; Ctrl+R still opens it. `statusLine` lists the footer's items in order (the default is the list above); a list with no known item gives the default line, with a warning. The items: `model` (the backend while the backend's default model runs), `effort`, `backend`, `cwd` (the working folder's name), `git-branch` (the short commit when `HEAD` is detached), `profile`, `mode`, `sandbox`, `context`, `cost`, `phase`, `task` and `version`. An `effort` right after `model` goes with it (`claude-opus-5-5 high`). The file is read when the TUI starts. A wrong file or field does not stop the session: the TUI starts with the default for it and says why in the transcript (`warning: …/settings.json: unknown status line item "weather"; skipped`).

### Notifications

The TUI notifies when a main turn ends (`Turn finished`, or `Turn failed` when it failed: `error`, a Claude Code `error_*` result, `turn_limit` or `incomplete`; the model's own stops, such as `max_tokens` or `stop_sequence`, are finished) after running at least `minSeconds` (10 by default), and when the session waits for the user (`Waiting for approval`, `Waiting for review consent`), once for each question as it comes on screen. A turn the user interrupted is not told, and nothing is told while the terminal has the focus: the TUI asks the terminal for focus reports (`CSI ? 1004 h`), keeps them out of the editor and the questions, and, until one arrives, takes the terminal as without the focus. The notice's title is `Atelier · <working directory name>`; it never holds the command or the prompt.

`via` chooses how; `auto`, the default, picks by where the TUI runs:

| Where                                               | `auto` sends                                          |
| --------------------------------------------------- | ----------------------------------------------------- |
| A Herdr pane (`HERDR_ENV=1`)                        | Nothing: Herdr notifies `blocked` and `done` itself   |
| An Orca terminal (`ORCA_PANE_KEY`)                  | The bell, which Orca turns into its own notification  |
| iTerm2, Ghostty, WezTerm or kitty, not through tmux | An OSC 9 notification, shown by the terminal          |
| Elsewhere on macOS                                  | `osascript` (`display notification`)                  |
| Elsewhere on Linux                                  | `notify-send` when it is on the `PATH`, else the bell |
| Elsewhere                                           | The bell                                              |

`terminal` always sends OSC 9, `system` always the system's notification (`osascript` on macOS, `notify-send` on Linux, the bell when neither is there) and `bell` always the bell, wherever the TUI runs. `sound: true` adds a sound: the notification's own with `osascript`, the system sound `Glass` (`afplay`) with OSC 9 on macOS, and the bell otherwise. A notification that fails is ignored. `osascript`'s notification shows as Script Editor's, and clicking it does not bring the terminal forward. `"enabled": false` turns the notices off; the OSC 7501 status is reported either way.

`ATELIER_TUI=off` keeps the line-by-line session described above, and so does `ATELIER_RECORD_SDK` (the SDK messages are recorded in the CLI's own process).

Line by line (with a prompt, `ATELIER_TUI=off`, or a session that is not interactive; the TUI below does its own), when stdin and stdout are both terminals, the CLI reads the terminal in raw mode and turns on bracketed paste (`\e[?2004h`), and turns both off when it exits, Ctrl+C, SIGTERM and SIGHUP included (`\e[?2004l`; the last two exit 143 and 129). It takes the terminal over before the session starts, so anything typed while it starts counts as typed before a question. A pasted block, line breaks included, becomes one prompt that Enter sends. Line editing is Backspace, Ctrl+U (erase the line), Ctrl+W (erase a word) and Ctrl+D on an empty line (end the session); other keys are ignored.

A `write` outside `--cwd` asks `Write a file outside the working directory?` the same way (row: `▸ write src/new.ts (120 bytes) ✓`), and without a terminal the CLI refuses it (`write asks to create or replace a file outside the working directory and needs your approval, but there is no terminal to ask (--mode yolo allows it): <path>`) and writes nothing. An `edit` of a file outside `--cwd` asks `Edit a file outside the working directory?` and shows the real absolute path; in `yolo` it is not asked, and without a terminal the CLI refuses it (`edit asks to change a file outside the working directory and needs your approval, but there is no terminal to ask (--mode yolo allows it): <path>`) and leaves the file alone. A question that can remember its answer (a command outside the sandbox or without one, an `edit` or `write` outside `--cwd`; not a command the guard asks about) adds the rules it would keep and takes `s` or `a` too: `  s: Allow "ego-browser nodejs" in this session`, `  a: Allow "ego-browser nodejs" always` (`edits in <folder>` for `edit` and `write`) and `[y/N/s/a]`; for an interpreter or a launcher (`node`, `python3`, `npx`, ...), or without a home directory to save in, only `s` is offered (`[y/N/s]`). Where commands a rule covers cannot run under their profile (another platform, or inside another sandbox), a `bash` question offers neither and stays `[y/N]`. `y` allows this call, `s` keeps the rules for the session, `a` saves them in `~/.atelier/permissions.json`, anything else denies (see [Rules you allowed](sandbox.md#rules-you-allowed)). In a session, `/permissions` lists the rules in force, numbered (`1. always  bash  ego-browser nodejs`, `2. session path  /Users/ana/notes`; `No permission rules.` when there are none), and `/permissions remove <n>` removes one (`removed: always bash ego-browser nodejs`; `error: no rule <n>` when there is none); anything else after `/permissions` prints `usage: /permissions | /permissions remove <number>`. A question (a `bash`, `edit` or `write` approval, `[y/N]`, or the review consent, `Review this high-risk change? y: review this change · N: skip this time · a: review all this session` with `[y/N/a]`, where anything but `y` or `a` skips) only takes an answer typed after it appears: lines typed or pasted before it are dropped (a pasted block counts as one line), and the CLI says how many. An answer line that had pasted text in it, even a pasted `y` or a paste erased before typing `y`, is never a yes: the CLI prints `pasted text does not answer this question` and takes it as no. Ctrl+C interrupts the running turn (and answers no to a pending approval); with no turn running, or pressed twice, it closes the session.
