# Desktop app

The Electron app: what it shows and how it talks to the core.

```bash
pnpm desktop            # dev mode with hot reload
pnpm -C atelier-desktop smoke   # build + Playwright smoke test (echo backend, no network)
```

Open a folder, pick a backend and a model, and chat. The desktop has no sign-in: `opencode-go` and `anthropic-api` use the key stored with `atelier login` (or set in the environment), and the status line says what the session is billed to (`billed to your OpenCode Go plan`). When `~/.atelier/profiles.json` has profiles, a `profile` selector lists them (asked with `profiles.list` each time the core is ready): `by layers (active: <name>)` lets the core resolve it, and a name is sent as `session.start.profile` for the next session; a chosen name the core no longer lists (after a restart, or when the list fails) goes back to `by layers`, so what the selector shows is what is sent; the backend and model pickers are still sent, so they replace the orchestrator's. Next to it a `mode` selector (`default`, `normal`, `auto`, `yolo`) picks the permission mode of the next session: `default` sends no `mode`, so the core uses the default saved with `/mode default`; the others are sent as `session.start.mode` (see [Permission modes](sandbox.md#permission-modes)). The status bar shows the model with its effort (`opus · effort high`; from `session_started`, and from `session_configured` when a change lands: one that moves to another backend without a model shows none until that backend says it, and a finished turn keeps in its summary the model that answered it, the main agent its `turn_finished.phases` names), the session's permission mode as a selector (`normal`, `auto` or `yolo`, from the main agent's `session_started`; `yolo` in the warning style; changing it sends `session.set_mode` and shows the mode the core answered, and if the command fails the previous mode stays and the error is shown like any other) and the session's profile (`profile: cheap (repo)`, or `profile: default`; kept when a later `session_started` carries none), with what it sets for each role in its tooltip. Each tool call shows as a row with its status; `bash` commands ask for approval in a card that shows invisible and control characters as visible markers; an `edit` of a file outside the working directory asks in the same card (`Edit a file outside the working directory?`, with `edit <absolute path>`; a `write` asks as `Write a file outside the working directory?`, with `write <absolute path>`). When the question can remember its answer (`approval_requested.remember`), the card has four buttons: `Allow`, `Allow "<rules>" in this session`, `Allow "<rules>" always` (only when offered; `edits in <folder>` for `edit` and `write`) and `Deny`; the answer goes as `session.approve` with `remember`, and the card then says `Allowed for this session` or `Allowed always` (see [Rules you allowed](sandbox.md#rules-you-allowed)). The desktop has no list of the rules: `/permissions` in the CLI lists and removes them. Every turn ends with a one-line summary of its tokens and cost that unfolds into the token breakdown and, when the turn had more than one part, one line per part (`main`, `declare`, `verify`, `lenses`, `refuter`, `correction`, `validator`) with its tokens, requests and cost, and who ran in it as the CLI's `phases:` line says it (`main · 3K tokens · 1 request · on claude-opus-5-5 effective xhigh`); the status bar shows the core status, whether `bash` is sandboxed, warnings and the latest error, how full the context is when the backend says it (`ctx ▰▰▱▱▱▱▱▱ 23% · 200k`, the share of the window, with the tokens and where it compacts on hover; in the warning style past 70% of where it compacts and in the error style past 90%; `ctx ▱▱▱▱▱▱▱▱ ? · 1M` as soon as the main agent compacts, until a request measures it; left out when the backend or the model changes (a `session_started` or `session_configured` with another one), until a turn measures the new window), and in the transcript, once the context reaches 90% of where it compacts, `⚠ context at 18% of the 1M window (182,000 tokens), near where it compacts (200,000)`, and, from the first turn, `skills: <n>` (each skill's name and `SKILL.md` on hover) and `skills: <n> warnings` in the warning style when some skill has a problem (each path and message on hover); a command the sandbox stopped lists why under its row (see [Sandbox (macOS)](sandbox.md)). If the core process dies, the app says so and offers a restart.

While a turn runs, the composer queues instead of sending (its button says `Queue`): Enter queues a steer, which the agent gets with its next tool result, and Alt+Enter a follow-up, which runs as a turn of its own once the turn ends well (see [How Atelier works](architecture.md)). The queue shows over the composer, one row per message with `steer` or `follow-up`, an `Edit` button that edits the text in place (`Save` sends `session.queue_edit`; a message that entered meanwhile is left as it went) and `×`, which takes it off the queue (`session.unqueue`). A steer shows in its turn where it entered, under the turn's prompt; a follow-up starts a turn of its own with it as the prompt. When a turn is interrupted or fails, or the core stops, the queue comes back to the composer, before what is being typed, and none of it runs; so does a message the core did not take (`session.queue` failed), with the error in the status bar.

When the session has MCP servers, the status bar shows `MCP <connected>/<enabled>` from `mcp_status`, in the warning style when a server failed, an entry is invalid or the file has a problem. Clicking it asks the core for the servers as they are now (`session.mcp`) and opens a side panel with each server's state, tools, error and the end of its stderr, and the file's problems; a server that needs a sign-in has a `Sign in` button, which asks the core to sign it in (`session.mcp_login`) through the browser. Clicking the label again closes the panel. When the classifier leaves an MCP call to you in `auto`, the approval card is titled `Call this MCP tool?`. See [MCP servers](mcp.md).

The desktop starts the core with Electron's own Node (no system Node needed) and talks to it over the Atelier protocol (version 7): one JSON message per line on stdin/stdout, a `hello` with the protocol version, an `id` on every command and exactly one response per command, and events tagged with their session.
