# How Atelier works

The core, its events, tools, backends, subagents, ODD, memory, project instructions, skills and compaction. Review and verification have their own page: [review.md](review.md).
- The core emits plain-JSON `AtelierEvent`s; clients only render them. Every turn ends with exactly one `turn_finished`, which says in `at` the ISO time the turn ended.
- `turn_finished` carries `phases`, the turn's cost by part: `handoff` (the summary of a backend change, in the next turn after it; see [Backend of an open session](profiles.md#backend-of-an-open-session)), `main` (the main agent), `classifier` (the permission classifier of `auto`), `declare` (the request to declare the risk), `verify` (the verifier and its correction), `lenses`, `refuter`, `correction` and `validator`, each with `usage` and, when its backends report them, `requests` and `costUsd`. Each part also lists in `agents` who ran in it, once each in the order they first ran: the profile role (`orchestrator` for the main agent in `main`, `declare`, `correction` and the correction inside `verify`; `permission-classifier` in `classifier`; `verifier`; `review-risk`, `review-resilience`, `review-readability`, `review-reliability`, `review-refuter`, `review-validator`), and the `backend`, `model` and `effort` that agent's `session_started` said (`effort` absent when no level was asked). When no level was asked and the backend says the effort it applied to the turn, the agent also has `effectiveEffort`; only `claude-code` says it, from the `effort.level` its `Stop` hook receives (Claude Code's own default for the model, since the session does not read the user's settings), so the main agent's in `main` and in the correction turns has it, and `session_started` never does; `agents` is absent when no agent of the part said `session_started`. A part that did not run is absent (an on-demand `/review` has no `main`), and the parts add up to the turn's `usage`, `requests` and `costUsd`.
- Messages queued while a turn runs live in the core's session, so every client sees the same queue. A `steer` goes to the model with the turn's next tool result, as text apart from the tool's output (`anthropic-api` adds it after the request's tool results; `claude-code` as a second text block of the tool's result, as Claude Code does with what you type while it works, so it never enters Claude Code's own queue, which an interrupt could leave behind to run as a turn of its own), and is said with `queued_message { id, kind, text }` where it entered. A `follow_up` waits for the turn to end and then runs as a turn of its own, whose first event is its `queued_message`; a steer that no tool result took (the model answered without tools, or the turn was a compaction or a review) runs the same way, before any follow-up, one turn each. Each change of the queue sends it whole, `queue_update { messages }`. A turn that is interrupted or fails runs none of it: just before its `turn_finished` the core empties the queue, what was queued while the turn was ending included, and gives it back in `queue_update { messages: [], returned }`, for the client to put in its editor; from then until the turn is over, `session.queue` fails with `turn_ended` and the client keeps the message. Clients queue with `session.queue { kind, text }` (answers `{ id }`; with no turn running the message starts one at once and the answer adds its `turnId`), change a queued message with `session.queue_edit { messageId, text }` (`not_queued` once it entered or left the queue) and take one back, or all of them without a `messageId`, with `session.unqueue` (answers `{ messages }`). Like the events, these commands only add to protocol 7: a client that does not use them sees the same turns as before.
- The agent only has Atelier's tools: `read`, `edit`, `write`, `bash`, `grep`, `web_fetch`, `web_search`, and `mcp_search` and `mcp_call` when the user configured MCP servers ([mcp.md](mcp.md)). The core executes them and owns approval. `read` and `grep` of the main agent and its workers open any path, absolute or `../`, except the protected secret locations (the home's secret directories and the `denyRead` entries of the sandbox configuration, the same list the sandbox hides from `bash`; a symbolic link into one is refused too, with `Path is a protected secret location: <path>`; `grep` skips them while walking, and drops any match whose real path is one, whatever the glob or the file name). This holds with the sandbox off or unavailable. `edit` writes without asking in the working directory, the session's scratch directory and the `allowWrite` directories of the sandbox configuration. `write` (`path`, `content`) creates a file, or replaces an existing one whole keeping its mode (a new file is `0644`), and creates the missing folders only after the gate; use `edit` to change part of a file that exists and `write` to create one or replace it entirely. It follows `edit`'s policy: the same places without asking, and anywhere else the same approval, with `{ command: "write <path>", reason: "outside the working directory", tool: "write" }` shared with `edit` (a file approved for one is allowed for the other, for the rest of the session). The content is capped at 1 MiB (1,048,576 bytes of UTF-8): over it the answer is `Not written: the content is <n> bytes and write takes at most 1048576 (1 MiB); write the file in parts or generate it with bash.` and nothing is written. `edit` and `write` share one path policy, compared by real path as well as by name (a link or a move gives a file no other name): a symbolic link to a missing file, or a folder on the way that is one, is refused without asking (`Not written: <path> is a symbolic link to a missing file.`, `Not edited: ...` for `edit`), and the protected places (secret directories and files, `.atelier/`, `odd/tasks/`, git state) are compared folding letter case and Unicode form, on any filesystem; the approval covers that one real path, and if the path leads elsewhere when the write happens the call is refused (`Not written: <path> led to <approved> when the user was asked, but now leads to <now>.`, `Not edited: ...` for `edit`). Both also refuse, without asking, the files the sandbox denies `bash` because git runs code from them (`.git/hooks`, `.git/config`, `.gitconfig`, `.gitmodules`, the pending steps of a rebase or cherry-pick, and what git reports for the repository of the working directory, wherever its git directory is: the hooks directory git runs, `core.hooksPath` included, in a main checkout too, the `config` and `config.worktree` of the git directory and of the shared one, the files they include, `info/attributes`, `modules/` and the `.git` file of a linked worktree; a subdirectory of a repository protects the repository's `.git` too): `<path> is git state that runs code: the agent does not write it.` `edit` also refuses the project's `.atelier/` (`<path> is project configuration: the agent does not write .atelier/.`) and the feature documents, whatever name or link reaches them. `write` also refuses, without asking, the feature documents (`<path> is a feature document: change it with the feature tool, not write.`) and the project's `.atelier/` (`<path> is project configuration: the agent does not write .atelier/.`); a denial answers `Not written: <path> is outside the working directory and the user did not approve writing it.` The main agent and the `worker` have it; the explorer, the review roles and the verifier do not. For `edit`, anywhere else it asks for approval showing the real absolute path (symbolic links resolved): the `approval_requested` event is `{ command: "edit <path>", reason: "outside the working directory", tool: "edit" }` (`tool` is optional and absent for `bash`; `ApprovalRequest` carries it too). In `yolo` it is not asked. Once approved, that exact file stays allowed for the rest of the session (not its directory, and not in another session; a worker subagent asks the same user through the same channel, and its approvals last as long as that worker). If the user denies, or nobody can be asked, the file is left untouched and the tool answers `Not edited: <path> is outside the working directory and the user did not approve editing it.` The file written is the approved real path: if a link changed since the question, the edit is refused. `edit` never writes the home's secret directories or `~/.atelier` (`Path is a protected secret location: <path>`), nor outside the working directory a `.env`, `.env.*`, `*.pem` or `*.key` file, approved or not, and nobody is asked. `bash` is not confined and is gated by approval instead. The review roles and the verifier keep `read` and `grep` inside the frozen tree or their own directory. The shared system prompt says so too: `Paths are relative to the working directory; read and grep also take absolute and ../ paths outside it (except the user's secrets), and edit and write outside it ask for approval. Use edit to change a file that exists and write to create one or replace it whole.`, so the agent reads another folder with `read` instead of `bash`. It also says `Use web_fetch to read a web page and web_search to look something up, not curl or wget in bash; never put secrets or private code in a URL or a search query.`, so the web goes through the address guard of `web_fetch`; `anthropic-api`'s own prompt no longer says that no tool can leave the working directory.
- `ClaudeCodeBackend` drives Claude Code through the Claude Agent SDK, isolated from your `~/.claude` setup (no settings, hooks, plugins, skills, CLAUDE.md or other MCP servers) and without `ANTHROPIC_API_KEY`, so it uses your subscription.
- `AnthropicApiBackend` runs Atelier's own loop on the Messages API. It owns the prompt: tools and system prompt are fixed for the session, and three cache breakpoints (last tool, system, last message) keep the prefix cached. Each request asks the API to compare its prefix with the previous response, which is how cache misses are reported.
- `web_fetch` (`url`, optional `offset`) downloads an `http` or `https` page from the core, not from the backend, so it works with any provider, and returns its text: HTML becomes Markdown (Readability, linkedom and Turndown), text, Markdown and JSON come back as they are, and any other type (PDF, images, binaries) is refused naming the type (`Cannot fetch application/pdf: only HTML, text and JSON.`). Limits: 30 s, a 5 MiB body (over it the call fails, nothing is cut), at most 5 redirects. It refuses loopback, private (`10/8`, `172.16/12`, `192.168/16`), link-local (`169.254/16`, the cloud metadata address included), unspecified and IPv6 loopback, unique-local (`fc00::/7`) and link-local addresses, also IPv4-mapped ones: the address is checked for a literal IP, for every address a name resolves to (the connection goes to the address that was checked, so a second lookup cannot change it) and again after each redirect, answering `Refused: <address> is ...`. A response carries at most 30,000 characters; when there is more, it ends with `[Showing characters <from>-<to> of <total>. Call web_fetch again with offset <to> to continue.]`, and a call with an `offset` for a page already fetched in the same session is served from an in-memory cache (1 hour, 20 pages) without a new request. It never asks for approval, in `normal`, `auto` or `yolo`, like gentle-shell: no `approval_requested` event and no classifier call. It still refuses, without asking and before any request, an invalid URL or one that is not `http` or `https`, and the address guard above applies in every mode. The main agent, the `worker` and the `explorer` have it; the review lenses, the refuter, the validator, the verifier and the classifier do not.
- `web_search` (`query`, optional `numResults`, 1 to 10, 5 by default) searches the web with Exa's public MCP (`https://mcp.exa.ai/mcp`) from the core, not from the backend, so it works with any provider and needs no API key. It returns the title, URL and a snippet (at most 500 characters) of each result, numbered; use `web_fetch` to read one. The query goes to Exa anonymously from your IP address, and Exa limits the anonymous service per IP (by its defaults, 50 searches a day and 2 a second). It waits at most 30 s and reads at most 1 MiB. A failure never ends the turn; it comes back as the tool's result, `Web search failed: <reason>`: the limit (HTTP 429) says `Exa's anonymous rate limit was reached (429): ...` and that API keys will be supported later, and a network error, a timeout or an answer that cannot be read says so; text with no result block in it is a failure that quotes its first 200 characters (`Exa's answer is not in the format this tool reads: "..."`), unless Exa says it found nothing, which answers `No results for "<query>".`. Like `web_fetch`, it never asks for approval in any mode (`normal`, `auto` or `yolo`). The main agent, the `worker` and the `explorer` have it; the review lenses, the refuter, the validator, the verifier and the classifier do not.
- Subagents: the agent can delegate with a `task` tool to `explorer` (read, grep, web_fetch, web_search) or `worker` (read, edit, write, grep, bash, web_fetch, web_search), both on the session's model and thinking level unless the agent profile sets theirs (see [Agent profiles](profiles.md#agent-profiles)). A subagent runs in its own session with only the task prompt and its role's instructions, on a fresh backend of the same kind. Only its final report, cut in code at 8,000 characters, returns to the parent. Its work shows nested under the task call: indented under `↳ agent · model` in the CLI, in a foldable block in the desktop, each with its own token line. Its bash commands ask for approval like any other.
- ODD (Organic Driven Development) is core state, not prompt prose. A small task takes the small path from gentle-shell: the agent reads only what it changes and its helpers, in one batch, and runs the focused test and the suite in one command. For large work the agent keeps a feature document in `odd/tasks/<name>.md` (`## Specs`, `## Tasks`, `## Log`) through the `feature` tool, the only way to change it: `edit` and `write` refuse that directory. Atelier writes the log's user entries itself, verbatim (L1 is the original request), so the model never paraphrases you. Each change is validated and written as one transaction, so the document stays well formed. A later session resumes with `open`. The current phase (exploring, implementing, checking…) is inferred from the tools (`edit` and `write` mean implementing), or declared with the `phase` tool. The CLI prints `· <phase>` and `◆ <feature>: n/m done`; the desktop shows the phase in the status bar and the feature's tasks in a side panel.
- Long-term memory (M6): with Engram 3.4.0 or newer installed, each session gets the project's memory (Engram resolves the project from the working directory). The agent searches and saves through the `memory` tool; a compact context of recent memory comes with the first message, outside the system prompt. Rules enforced in code: the user's prompts are saved to memory as prompts, never captured along with a memory: each prompt that starts a turn and each steer that enters one, from the main session only (not `/compact`'s instructions, review requests or a subagent's task), with the credentials Atelier recognizes replaced by `[REDACTED]`, best effort (a credential in another form is saved as written): a private key whole, from its `BEGIN` line through its `END` line, or to the end of the prompt without one; the whole value of an `Authorization` or `Proxy-Authorization` header, whatever its scheme (up to its closing quote, or to the end of the line), and of a bearer token; the value assigned with `=` or `:` to a name containing `PASSWORD`, `PASSWD`, `SECRET`, `TOKEN`, `API_KEY`, `ACCESS_KEY`, `PRIVATE_KEY` or `CREDENTIAL`, in any case (an `AWS_SECRET_ACCESS_KEY=` among them; the name stays); the password of a `scheme://user:password@host` URL; and Anthropic, OpenAI-style, GitHub, Google, AWS access key and Slack keys. The whole prompt is masked first and only then cut to 2,000 characters, never inside a `[REDACTED]`, so a cut cannot leave part of a credential; it is kept out when one of those keys is still found across words; it needs Engram's `mem_save_prompt`, each prompt is one attempt, and the first failure is the recoverable error `memory_prompt_failed` (`Your prompts are not being saved to memory: <reason>`), once per session. `ATELIER_MEMORY_PROMPTS=off` or `"memory": { "prompts": false }` in `~/.atelier/settings.json` ([settings](cli.md#settings)) keeps them out; anything shaped like a credential is refused when the agent saves a memory, subagents get no memory, and a finished ODD feature is saved under `odd/<name>/tasks` without the user's verbatim messages. A save that Engram keeps but could not check for conflicting memories (`candidate_detection_status: "incomplete"`) is not retried: the tool's answer says `Saved memory #<id>. Warning: ...`, and a feature mirror sends a recoverable `memory_mirror_warning` error. Each compaction that succeeds, on either backend (threshold, overflow or `/compact`), saves its summary as a `session_summary` titled `Session summary: <project>, <YYYY-MM-DD>` under the key `session/<id>/summary`, one per session, so later compactions of the same session update it; the turn waits for the save, and a summary shaped like a credential (`memory_summary_skipped`), a failed save (`memory_summary_failed`) or a save with a warning (`memory_summary_warning`) is a recoverable error, never retried. After saving it, the core fetches the recent memory again (the same 2 KiB context as at start, one attempt) and puts a recovery notice before the next prompt, once, on either backend (Claude Code reports its compactions through its `PostCompact` hook): `<memory-recovery>`, `The conversation was compacted. Recent memory of project <project>:` and that memory, then what to do about the summary: when it was saved, `The compaction summary is already in memory; do not save it again.`; when the save got no answer (a timeout or a closed Engram, so it may have landed), to search memory for it first and save it once only if absent; when Engram refused it (an error answer or a protocol error such as invalid params), to save its key points once with the `memory` tool under the session's summary key; when it looked like a credential, not to save it. The notice counts as given only once the backend takes that prompt: if the backend fails before (it throws, or answers only with an error), the notice goes with the next prompt. The core's state that goes with the same prompt leaves the memory out, since the notice brings it, and so does the first turn's `<memory>` when the session compacted before its first prompt. If the recent memory does not come, the notice still says what to do, and the turn gets the recoverable error `memory_recovery_failed`. When Engram has `mem_session_start` and `mem_session_end`, each session registers itself at start as `atelier-<id>` in its folder (the same id as its summary key) and every write it makes (memories, summaries, prompts) names it; closing the session ends it in Engram, once, and a failure there is ignored. If the registration fails, the writes go without a session, as before, and the first turn gets the recoverable error `memory_session_failed`. Without Engram, sessions work and say why there is no memory (`memory: <project>` / `no memory: <reason>`); `ATELIER_MEMORY=off` turns it off. Only `atelier-core/src/memory/engram.ts` knows Engram, and a test enforces it.
- Review with receipts and independent verification: see [review.md](review.md).
- Project instructions: at session start the core walks up from the working directory (`--cwd`) through every parent folder, stopping before the user's home folder (or at the disk root if the folder is not under it), and takes `AGENTS.md` from each folder, or `CLAUDE.md` when there is no `AGENTS.md`. Before them comes the user's own `~/.agents/AGENTS.md`, if there is one, as `User instructions from <path>:`. The files are appended to the main session's system prompt from the outermost folder to the closest, each preceded by `Project instructions from <path>:`, so the closest comes last and wins a contradiction. It works the same on `anthropic-api` and `claude-code`, and the files are read once, at start (editing them later does not change the running session, which keeps the prompt prefix cache intact). The total is capped at 32 KiB: over it, the outermost files are dropped first, the user's file before any project file. The first turn reports `instructions: <paths>` and, if the cap left files out, the warning `instructions over 32 KiB, left out: <paths>`; the desktop shows both in the status bar. Subagents do not get them: they keep only their task and role instructions. There is no stop at the git root, so running in `atelier/` also reads `../AGENTS.md`.
- Skills: at session start the core looks for skills, following the [Agent Skills](https://agentskills.io) format, in `.agents/skills/` of the working directory and of each parent folder up to the repository root (the first folder with a `.git`, a folder or a worktree's file; outside a repository, the working directory alone), then in the user's `~/.agents/skills/`. It does not read `~/.claude/skills` or `.claude/skills`. A skill is a folder directly inside one of those (hidden folders are skipped, linked folders are followed) holding a `SKILL.md` whose YAML frontmatter has a `description`; its `name` defaults to the folder's. A `SKILL.md` without a description, with a description that is not a string, or whose frontmatter cannot be parsed or is never closed by `---`, is not loaded; nor is one in a place `read` refuses (a folder linked into `~/.claude`, say). A name that is not lowercase letters, digits and hyphens of at most 64, loads with a warning, and so does a description over 1,024 characters, which the prompt gets cut to 1,024; a name unlike its folder's is accepted silently. Of two skills with the same name the first found wins (the closest project folder first, the user's last) and the other is reported. The main session's system prompt gets, after the project instructions, a short instruction to read a skill's `SKILL.md` with `read` when a task matches it and to resolve its relative paths against the skill's folder, and an `<available_skills>` list with each skill's name, description and the absolute path of its `SKILL.md`; the body is never in the prompt. The block is capped at 24 KiB, its instructions included: the skills found after it fills up are not listed and each gets a warning. If the sandbox configuration is invalid, the places `read` refuses are unknown, so no skill is loaded and, when there were skills to load, a single warning says why. Project skills load without asking for trust, like `AGENTS.md`, and are read once, at start. `read` opens them without approval, since it reads outside the working directory everywhere but the protected locations. The first turn sends `skills_loaded` (`skills`: name and path; `warnings`: path and message) when there are skills or warnings; the CLI prints `skills: <names>` and one `skill <path>: <message>` warning each, the desktop shows them in the status bar. Subagents do not get the list: the agent names the `SKILL.md` in the task's prompt when a subagent needs it.
- Context compaction (M8): a long session no longer ends in a context error. On `anthropic-api`, before each model request the core compares the context (the last response's real usage plus an estimate of what was appended since) with `min(window − (max output + 16,384), 200,000)` tokens, the window coming from the models API (200,000 when it does not answer); `ATELIER_COMPACT_AT=<n>` replaces the 200,000 cap, but never goes past the window minus the reserve. Crossing it, the core asks the session's model for a summary in a fixed format (Goal, Constraints & Preferences, Progress, Key Decisions, Next Steps, Critical Context), with the session's own prefix so it reads from the prompt cache, and replaces the older history with one message: the summary, the files read and edited (from the tool calls, not from the model; a file created or replaced with `write` counts as edited), the current turn's request verbatim when it was summarized, and once the core's state (active ODD feature and task, phase, the memory of the first turn). The last ~20,000 tokens stay verbatim and a tool result never loses its call. A summary that is empty, cut short or missing a section is refused and the history stays as it was; a context overflow compacts once and retries the request. Claude Code compacts on its own: Atelier shows its compactions, forwards `/compact`, and gives the core's state with the next prompt. Both clients show the compaction (before → after, messages kept, cost), mark the cache miss that follows it as expected, show how full the context is, and accept `/compact [instructions]`. A subagent compacts by the same rules in its own session (the threshold, one compaction on an overflow) and goes on with its task; its compaction events reach the parent tagged with `parentCallId` and `agent` like its other events, both clients show them under the subagent with its own expected cache miss, and its summary is never saved to memory. If a subagent's turn fails after its compaction failed, the task's error names both: `The worker subagent failed (error): <error>; its compaction failed: <reason>`.
- `bash` runs without `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`. That only filters its environment; the isolation is the macOS sandbox described in [the sandbox page](sandbox.md). Do not use `yolo` for work you do not trust.
- Temporary directories: each session's scratch directory, the verifier's copy, the temporary index of a freeze and the full output of a `bash` command run without a session are `atelier-session-*`, `atelier-verify-*`, `atelier-freeze-*` and `atelier-bash-*` in the system temporary folder. Each holds `.atelier-owner` (the pid and start time of the process that made it) next to `work/`, which is all the agent, the verifier, git or the tool sees. Closing removes them; a process that dies (`kill -9`, a crash, a closed terminal) leaves them behind. The first one a process creates starts a sweep of that folder in the background, once per process, which never delays the start. It deletes the directories whose owner process is gone or whose pid now belongs to a process that started more than 5 s after the owner (`ps` gives the start to the second), and those without an owner file (from Atelier 0.4.0 or older) once neither the directory nor anything right inside it has changed for 7 days. It looks only at those names and only at real directories of the current user, never at the current process's own, and keeps whatever it cannot tell for sure: a process of another user (`EPERM`), a live process whose start time `ps` does not give, an unreadable owner file, and everything on Windows. Before deleting, it moves the directory aside with one rename to an `atelier-trash-*` of its own and checks that what moved is the same real directory (device, inode, user and owner file) it found stale; anything else, such as a symbolic link or a new directory put in its place, goes back. The owner file is deleted last, and a deletion that fails part-way goes back to its name, owner file included, so the next process tries again. `ATELIER_SCRATCH_SWEEP=off` turns the sweep off; the test suite runs with it off (`vitest.config.ts`) and only `scratch.test.ts` turns it on, over a folder of its own. Known limits, accepted as they are:
  - Putting a directory back is a check followed by a rename: an empty directory that another process creates under the original name in between is replaced by it (one that is not empty is kept, and the directory stays as `atelier-trash-*`).
  - Once the moved directory passed its check, another process of the same user that swaps it for a symbolic link makes the deletion walk the link's target. Node has no `openat`/`unlinkat` to close this, and such a process can already delete those files itself.
  - On Windows, a directory without an owner file that is more than 7 days old is still deleted by the age rule, which comes before the Windows guard.
