# How Atelier works

The core, its events, tools, backends, subagents, ODD, memory, project instructions, skills and compaction. Review and verification have their own page: [review.md](review.md). The main-agent structured-question tool, its lifecycle and client behavior is in [ask-user.md](ask-user.md).
- The core emits plain-JSON `AtelierEvent`s; clients only render them. Every turn ends with exactly one `turn_finished`, which says in `at` the ISO time the turn ended.
- `turn_finished` carries `phases`, the turn's cost by part: `handoff` (the summary of a backend change, in the next turn after it; see [Backend of an open session](profiles.md#backend-of-an-open-session)), `main` (the main agent), `classifier` (the permission classifier of `auto`), `declare` (the request to declare the risk), `verify` (the verifier and its correction), `lenses`, `refuter`, `correction` and `validator`, each with `usage` and, when its backends report them, `requests` and `costUsd`. Each part also lists in `agents` who ran in it, once each in the order they first ran: the profile role (`orchestrator` for the main agent in `main`, `declare`, `correction` and the correction inside `verify`; `permission-classifier` in `classifier`; `verifier`; `review-risk`, `review-resilience`, `review-readability`, `review-reliability`, `review-refuter`, `review-validator`), and the `backend`, `model` and `effort` that agent's `session_started` said (`effort` absent when no level was asked). When no level was asked and the backend says the effort it applied to the turn, the agent also has `effectiveEffort`; only `claude-code` says it, from the `effort.level` its `Stop` hook receives (Claude Code's own default for the model, since the session does not read the user's settings), so the main agent's in `main` and in the correction turns has it, and `session_started` never does; `agents` is absent when no agent of the part said `session_started`. A part that did not run is absent (an on-demand `/review` has no `main`), and the parts add up to the turn's `usage`, `requests` and `costUsd`.
- Messages queued while a turn runs live in the core's session, so every client sees the same queue. A `steer` goes to the model with the turn's next tool result, as text apart from the tool's output (`anthropic-api` adds it after the request's tool results; `claude-code` as a second text block of the tool's result, as Claude Code does with what you type while it works, so it never enters Claude Code's own queue, which an interrupt could leave behind to run as a turn of its own), and is said with `queued_message { id, kind, text }` where it entered. A `follow_up` waits for the turn to end and then runs as a turn of its own, whose first event is its `queued_message`; a steer that no tool result took (the model answered without tools, or the turn was a compaction or a review) runs the same way, before any follow-up, one turn each. Each change of the queue sends it whole, `queue_update { messages }`. A turn that is interrupted or fails runs none of it: just before its `turn_finished` the core empties the queue, what was queued while the turn was ending included, and gives it back in `queue_update { messages: [], returned }`, for the client to put in its editor; from then until the turn is over, `session.queue` fails with `turn_ended` and the client keeps the message. Clients queue with `session.queue { kind, text }` (answers `{ id }`; with no turn running the message starts one at once and the answer adds its `turnId`), change a queued message with `session.queue_edit { messageId, text }` (`not_queued` once it entered or left the queue) and take one back, or all of them without a `messageId`, with `session.unqueue` (answers `{ messages }`). Like the events, these commands only add to protocol 7: a client that does not use them sees the same turns as before.
- Background jobs: `bash_background` (`command`, an optional `label`, and `unsandboxed` with its `reason` as in `bash`) starts a command and answers at once, `Started background job <id> ("<label>"). Output: <file>` and `You get a notice when it ends; job_list shows it and job_stop stops it.` It goes through the same gate as `bash` (the guard, the user's and the project's rules, the questions of each mode, the sandbox or the profile of covered commands), and its output goes to `job-<id>.log` in the session's scratch directory, at most 50 MB. At most 16 jobs run at once in a session (`Refused: 16 background jobs are running; stop one with job_stop or wait for one to end.`). `job_list` shows the running jobs and the last 20 to end (by when they ended, whenever they started), one line each (`<id>  <status>  <elapsed>  <label>  <file>`); `job_stop { id }` kills the job's whole process tree (SIGTERM, then SIGKILL after 2 s) and no notice follows. When a job ends the agent gets one notice: `Background job <id> ("<label>") ended: exit code <n> after <time>.` (or `killed by signal <name>`, or `could not start: <reason>`), the command, the output file, and the end of the output quoted as data between `<job_output>` tags (the last 40 lines, at most 4 KB, hidden characters shown as markers and each line then cut at 500 characters), with what the sandbox blocked when it failed. In a turn that answers a prompt the notice goes with the next tool result, after the steers; if no tool result takes it, it starts a turn of its own once that turn ends; with no turn running, it starts one at once. A turn a notice woke waits a quarter of a second before it takes the notices, then takes all there are, so the notices of jobs that end together, or one left by a turn and one of a job that ends just after it, go to one turn (the RPC server starts it, as for a follow-up; another caller gets `SessionOptions.wake` and runs `nextQueued`). That turn's prompt is the notices alone: it is not logged or saved to memory as the user's words, and in `auto` the classifier has no request, so the user is asked. Notices a prompt took whose backend failed before answering wait again, before any that came since (`jobs_status` says how many). A turn that is interrupted or fails holds the notices until the user's next prompt, which gets them before its words: those it left and those of jobs that end after it, which start no turn of their own and show as waiting (`job_finished.waiting`). Such an end, with no turn running and none to start, is said at once outside any turn: `SessionOptions.idleEvent` hears it, and the RPC server sends it as `{ type: "session_event", sessionId, event }` (no `seq` or `turnId`; `RpcClient.onSessionEvent`) only to a session whose `session.start` or `session.resume` asked for it with `sessionEvents: true` (the TUI and the desktop do), so protocol 7 clients that do not ask never get it; without `idleEvent`, as for those, it goes first in the next turn. It is saved with the session as a turn's events are, with an empty `turnId`. The events are `job_started { jobId, label, command, outputPath, running }`, `job_finished { jobId, label, status, exitCode?, signal?, durationMs, outputPath, notified, running, waiting }` (`status` is `exited`, `stopped` or `failed`; in the running turn, else first in the turn its notice wakes or the next) and `jobs_status { running, waiting }` once the agent read the notices that waited, or they wait again; they only add to protocol 7. Closing the session stops every job, also when another part of the close fails (the close still rejects with that failure), and jobs are not restored on resume. A job ends even when the caller's cleanup or end callback throws. Each job runs in a process group of its own under a guardian whose watcher, when Atelier quits or dies however it does, kills the group, the processes that carry the job's mark (`ATELIER_JOB` in their environment) and every descendant of either; `job_stop` and a job's end do the same from Atelier. The process listing gets 2 s (`ps`, or `/proc` on Linux, read without blocking the core); without an answer, or where it is refused, only the group and what was already found are killed. A process that left the job's group, whose parents are gone and whose environment cannot be read (macOS hides it for its own signed programs, such as `/bin/sleep`) or was cleared, is not found. Subagents do not get these tools.
- The agent only has Atelier's tools: `read`, `edit`, `write`, `bash`, `grep`, `web_fetch`, `web_search`, `bash_background`, `job_list`, `job_stop`, and `mcp_search` and `mcp_call` when the user configured MCP servers ([mcp.md](mcp.md)). The core executes them and owns approval. `read` and `grep` of the main agent and its workers open any path, absolute or `../`, except the protected secret locations (the home's secret directories, Atelier's credential files `~/.atelier/auth.json` and `~/.atelier/mcp-auth.json`, other tools' credential files such as `~/.codex/auth.json` and `~/.netrc` (the list is in [sandbox.md](sandbox.md)), and the `denyRead` entries of the sandbox configuration, the same list the sandbox hides from `bash`; a symbolic link into one is refused too, with `Path is a protected secret location: <path>`; `grep` skips them while walking, and drops any match whose real path is one, whatever the glob or the file name). This holds with the sandbox off or unavailable. `grep` takes `pattern`, `path`, `glob` and four optional fields: `ignoreCase`, `literal` (a fixed string, not a regular expression), `context` (0 to 20 lines before and after each match, shown as `path-N-text` next to the `path:N:text` matches, with a `--` line between blocks) and `limit` (1 to 1000 matches, 100 by default; context lines do not count). Neither `grep` returns a line, match or context, of a protected location or a secret file (`.env`, `.env.*`, `*.pem`, `*.key`, by name or by real path); a `path` that names one, as written or through a link, is refused with `Path is a protected secret location: <path>`, also by the `grep` that stays inside the working directory. Both engines skip hidden files and directories and `node_modules` during a folder search. An explicitly named file is searched even when its name starts with a dot (for example, `.eslintrc`), and `glob` does not filter that target; the common secret-file and protected-location checks still apply. It runs ripgrep with `--no-config`, so `RIPGREP_CONFIG_PATH` changes nothing, and the system grep fallback behaves the same. Ripgrep's stdout `WARNING:` lines, including `stopped searching binary file after match`, are discarded: they are neither shown nor counted against the match limit, and never become the next result's path. The separate `binary file matches (...)` diagnostic takes precedence over warning detection and is still shown and counted as one match, even when the file name contains `WARNING:`; the system grep fallback skips binary files. When there are more matches it ends with `[Showing the first <n> matches. Narrow the pattern, path or glob, or call grep again with limit: <2n>.]` (without the suggestion at 1000 or when the output size cut it). `edit` writes without asking in the working directory, the session's scratch directory and the `allowWrite` directories of the sandbox configuration; its `tool_call_finished` adds `startLines`, the line each edit starts at in the file before it, and `newStartLines`, the line its new text starts at in the file after it (after what the edits before it added or removed, on the same line too), both in the order of the edits, so a client can number its diff (the fields are absent for the other tools). `write` (`path`, `content`) creates a file, or replaces an existing one whole keeping its mode (a new file is `0644`), and creates the missing folders only after the gate; use `edit` to change part of a file that exists and `write` to create one or replace it entirely. It follows `edit`'s policy: the same places without asking, and anywhere else the same approval, with `{ command: "write <path>", reason: "outside the working directory", tool: "write" }` shared with `edit` (a file approved for one is allowed for the other, for the rest of the session). The content is capped at 1 MiB (1,048,576 bytes of UTF-8): over it the answer is `Not written: the content is <n> bytes and write takes at most 1048576 (1 MiB); write the file in parts or generate it with bash.` and nothing is written. `edit` and `write` share one path policy, compared by real path as well as by name (a link or a move gives a file no other name): a symbolic link to a missing file, or a folder on the way that is one, is refused without asking (`Not written: <path> is a symbolic link to a missing file.`, `Not edited: ...` for `edit`), and the protected places (secret directories and files, `.atelier/`, `odd/tasks/`, git state) are compared folding letter case and Unicode form, on any filesystem; the approval covers that one real path, and if the path leads elsewhere when the write happens the call is refused (`Not written: <path> led to <approved> when the user was asked, but now leads to <now>.`, `Not edited: ...` for `edit`). Both also refuse, without asking, the files the sandbox denies `bash` because git runs code from them (`.git/hooks`, `.git/config`, `.gitconfig`, `.gitmodules`, the pending steps of a rebase or cherry-pick, and what git reports for the repository of the working directory, wherever its git directory is: the hooks directory git runs, `core.hooksPath` included, in a main checkout too, the `config` and `config.worktree` of the git directory and of the shared one, the files they include, `info/attributes`, `modules/` and the `.git` file of a linked worktree; a subdirectory of a repository protects the repository's `.git` too; and, as the sandbox does, any `.git` below the working directory, and one at its top when it has none): `<path> is git state that runs code: the agent does not write it.` `edit` also refuses the project's `.atelier/` (`<path> is project configuration: the agent does not write .atelier/.`) and the feature documents, whatever name or link reaches them. `write` also refuses, without asking, the feature documents (`<path> is a feature document: change it with the feature tool, not write.`) and the project's `.atelier/` (`<path> is project configuration: the agent does not write .atelier/.`); a denial answers `Not written: <path> is outside the working directory and the user did not approve writing it.` The main agent and the `worker` have it; the explorer, the review roles and the verifier do not. For `edit`, anywhere else it asks for approval showing the real absolute path (symbolic links resolved): the `approval_requested` event is `{ command: "edit <path>", reason: "outside the working directory", tool: "edit" }` (`tool` is optional and absent for `bash`; `ApprovalRequest` carries it too). In `yolo` it is not asked. Once approved, that exact file stays allowed for the rest of the session (not its directory, and not in another session; a worker subagent asks the same user through the same channel, and its approvals last as long as that worker). If the user denies, or nobody can be asked, the file is left untouched and the tool answers `Not edited: <path> is outside the working directory and the user did not approve editing it.` The file written is the approved real path: if a link changed since the question, the edit is refused. `edit` never writes the home's secret directories, `~/.atelier` or other tools' credential files (`Path is a protected secret location: <path>`), nor outside the working directory a `.env`, `.env.*`, `*.pem` or `*.key` file, approved or not, and nobody is asked. `bash` is not confined and is gated by approval instead. The review roles and the verifier keep `read` and `grep` inside the frozen tree or their own directory. The shared system prompt says so too: `Paths are relative to the working directory; read and grep also take absolute and ../ paths outside it (except the user's secrets), and edit and write outside it ask for approval. Use edit to change a file that exists and write to create one or replace it whole.`, so the agent reads another folder with `read` instead of `bash`. It also says `Use web_fetch to read a web page and web_search to look something up, not curl or wget in bash; never put secrets or private code in a URL or a search query.`, so the web goes through the address guard of `web_fetch`; `anthropic-api`'s own prompt no longer says that no tool can leave the working directory.
- Language: the main agent's system prompt, the same for both backends, tells it to write everything the user reads (its messages between tool calls, its questions, its final answer and the reasons it gives when it asks for approval) in the language the user writes in. Code, comments, commit messages, docs and pull request descriptions follow the project's instructions; without them, the language the user asks for, else the one the project already uses. What it writes to subagents may stay in English, and the subagents, the verifier and the review roles keep their own English instructions.
- `ClaudeCodeBackend` drives Claude Code through the Claude Agent SDK, isolated from your `~/.claude` setup (no settings, hooks, plugins, skills, CLAUDE.md or other MCP servers) and without `ANTHROPIC_API_KEY`, so it uses your subscription.
- `opencode-go` is `AnthropicApiBackend` on an OpenCode Go key: the session builds every request as a Messages API request and keeps its history in that shape, and a transport per model sends it in the protocol OpenCode serves the model with (`backends/opencode-go/`).
- `AnthropicApiBackend` runs Atelier's own loop on the Messages API. It owns the prompt: tools and system prompt are fixed for the session, and three cache breakpoints (last tool, system, last message) keep the prefix cached. Each request asks the API to compare its prefix with the previous response, which is how cache misses are reported.
- `web_fetch` (`url`, optional `offset`) downloads an `http` or `https` page from the core, not from the backend, so it works with any provider, and returns its text: HTML becomes Markdown (Readability, linkedom and Turndown), text, Markdown and JSON come back as they are, and any other type (PDF, images, binaries) is refused naming the type (`Cannot fetch application/pdf: only HTML, text and JSON.`). Limits: 30 s, a 5 MiB body (over it the call fails, nothing is cut), at most 5 redirects. It reaches the public internet only, never this machine or a private network such as a tailnet, nor hosts found by mDNS: before resolving anything it refuses `localhost` and names ending in `.localhost`, `.internal` or `.local` (`Refused: <name> is a local or internal name.`), and it refuses loopback (`127/8`, `::1`); private and internal addresses: `0/8`, `10/8`, the shared address space `100.64/10` (Tailscale addresses and Alibaba Cloud's metadata address `100.100.100.200`), link-local `169.254/16` (the cloud metadata address included), `172.16/12`, `192.168/16`, `::`, unique-local `fc00::/7`, link-local `fe80::/10`, site-local `fec0::/10` and local-use NAT64 `64:ff9b:1::/48`; and reserved, multicast and documentation ranges: `192.0.0/24`, `192.0.2/24`, `198.18/15`, `198.51.100/24`, `203.0.113/24`, `224/4`, `240/4`, `100::/64`, `2001:db8::/32` and `ff00::/8`. An IPv6 address that carries an IPv4 in its last 32 bits (IPv4-mapped `::ffff:0:0/96`, IPv4-compatible `::/96`, SIIT `::ffff:0:0:0/96` and NAT64 `64:ff9b::/96`) is refused when that IPv4 is, and anything that is not an IP address is refused. The address is checked for a literal IP, for every address a name resolves to (the connection goes to the address that was checked, so a second lookup cannot change it) and again after each redirect, answering `Refused: <address> is ...`, `Refused: <ipv6> carries <ipv4>, ...` or `Refused: <address> is not an IP address.` A response carries at most 30,000 characters; when there is more, it ends with `[Showing characters <from>-<to> of <total>. Call web_fetch again with offset <to> to continue.]`, and a call with an `offset` for a page already fetched in the same session is served from an in-memory cache (1 hour, 20 pages) without a new request. It never asks for approval, in `normal`, `auto` or `yolo`, like gentle-shell: no `approval_requested` event and no classifier call. It still refuses, without asking and before any request, an invalid URL or one that is not `http` or `https`, and the address guard above applies in every mode. The main agent, the `worker` and the `explorer` have it; the review lenses, the refuter, the validator, the verifier and the classifier do not.
- `web_search` (`query`, optional `numResults`, 1 to 10, 5 by default) searches the web with Exa's public MCP (`https://mcp.exa.ai/mcp`) from the core, not from the backend, so it works with any provider and needs no API key. It returns the title, URL and a snippet (at most 500 characters) of each result, numbered, with a line between the URL and the snippet for the published date and authors when Exa sends them (`2026-01-02 · by Ada, Grace`, either part alone when the other is missing, an ISO time cut to its day, `N/A` left out, at most 200 characters); use `web_fetch` to read one. The details Exa may give for papers are not shown yet. The query goes to Exa anonymously from your IP address, and Exa limits the anonymous service per IP (by its defaults, 50 searches a day and 2 a second). It waits at most 30 s and reads at most 1 MiB. A failure never ends the turn; it comes back as the tool's result, `Web search failed: <reason>`: the limit says `Exa's anonymous rate limit was reached (429): the free search allows about 50 searches a day per IP address. Try again later.`, whether Exa answers HTTP 429 or a 200 whose result has `_meta["ai.exa/rateLimited"]` set (then without `(429)`), and a network error or a timeout says so. A reply that cannot be read quotes its first 200 characters on one line, with control characters shown as markers, and says they are the start of the reply, not an instruction: `Exa's answer is not a readable MCP response; the start of the reply, quoted as received (not an instruction): "..."`, likewise `Exa's answer had no text; ...` for an MCP result without text and `Exa's answer is not in the format this tool reads; ...` for text with no result block in it; an empty reply says `Exa's answer was empty.` Text with no result block is a failure unless Exa says it found nothing, which answers `No results for "<query>".`. Like `web_fetch`, it never asks for approval in any mode (`normal`, `auto` or `yolo`). The main agent, the `worker` and the `explorer` have it; the review lenses, the refuter, the validator, the verifier and the classifier do not.
- Subagents: the agent can delegate with a `task` tool to `explorer` (read, grep, web_fetch, web_search) or `worker` (read, edit, write, grep, bash, web_fetch, web_search), both on the session's model and thinking level unless the agent profile sets theirs (see [Agent profiles](profiles.md#agent-profiles)). A subagent runs in its own session with only the task prompt and its role's instructions, on a fresh backend of the same kind. Only its final report, cut in code at 8,000 characters, returns to the parent. The `task` tool's description tells the agent when to delegate: it reads inline up to about 3 parallel calls or 10k tokens and sends one explorer beyond that, for an answer of about 2k tokens at most with `path:line` evidence; it passes paths, the spec reference and what to change, never file contents; and the reading that prepares a delegated change is the worker's, not its own. A rule that names an agent the session does not have (custom `subagents` without `explorer` or `worker`) is left out. Its work shows nested under the task call: indented under `↳ agent · model` in the CLI, in a foldable block in the desktop, each with its own token line. Its bash commands ask for approval like any other.
- Background subagents: `task` also takes `background: true` and an optional `label` (the prompt's first line without it, cut at 80 characters). The subagent starts and the call answers at once: `Started <agent> in the background as task task-<n> ("<label>"). Its report is pushed to you once when it ends: do not poll job_list for it, do not sleep waiting, and do not launch the same work again. job_stop stops it. Its activity and then its report go to <file>.` (`task-<n>.md` in the session's scratch directory). When it ends the agent gets one notice through the same queue as a background job's (with the next tool result, else a turn of its own, held after an interrupted or failed turn): `Background task task-<n> (<agent>, "<label>") finished after <time>.`, the file, and its report bounded to 8,000 characters and quoted as data between `<subagent_report>` tags, a closing tag inside escaped; a subagent that fails gives `... failed after <time>: <reason>` instead. One delivery of notices, a job's or a task's, gives 24,000 characters at most, separators included: each notice whole while it fits, else its short form (a job's says how it ended and `Its output did not fit with the other notices: read it at <file>`; a task's, how it ended, its changes and `Its report did not fit with the other notices: read it at <file>`), and from the first that fits in neither a last line says `<n> more notices did not fit: job_list lists the jobs and tasks that ended.` `job_list` lists tasks after the jobs (`task-<n>  <status>  <elapsed>  <agent>: <label>  <file>`), and `job_stop { id: "task-<n>" }` stops one (its subagent is interrupted, and closed if it does not end within 2 s) with no notice; closing the session stops them all, and interrupting a turn stops none. At most 4 run at once (`Refused: 4 background tasks are running; stop one with job_stop or wait for one to end.`). Everything that refuses does so before the subagent starts: a session without `wake` (`Refused: this session cannot receive a background result; run the task without background.`; the parameter's description says it is not available), an agent other than `explorer` and `worker`, which the profile does not route, and a profile that reported problems when it was read, so the subagent's backend and model cannot be confirmed (it never falls back to the parent's). A background worker works in a git worktree of its own, so two never write in the same folder, nor in the parent's: the core takes a snapshot of the parent's working tree (HEAD plus what is not committed, tracked and untracked files but not ignored ones, written with an index of its own, so the user's index, branches and stash are never touched), adds a detached worktree at it in `worktrees/<n>/` of the session's scratch directory (git runs none of the repository's programs for the snapshot, the worktree or the patch: no hooks, no file system monitor, every filter driver the configuration names off, also one that only the worktree's own configuration turns on (it is checked out from inside it), no textconv or external diff, no signing), and starts the worker in the folder that stands where the parent's working directory does. The call's answer adds `It works in its own git worktree, from your working tree as it is now (HEAD <id> plus uncommitted changes); its changes come back as a patch.`, and the worker is told not to commit. So that it can run the project's tests there, each `node_modules` folder git ignores in the parent's checkout becomes the worker's own: cloned into the worktree (`cp -c` on APFS, `cp --reflink=always` on Linux: the copy shares its blocks until written), or copied whole where the file system cannot clone, never linked, so what the worker writes there never reaches the parent's; a folder that cannot be copied refuses the launch (`The worker's worktree could not be made: ...`). The call's answer then adds `Its node_modules folders are copy-on-write copies of yours.` or `Its node_modules folders are copies of yours.`, and the worker is told to use them and install nothing. Those folders are left out of the patch, whatever the worker made of them. When it ends, what changed in the worktree (commits or not) against the snapshot is written to `task-<n>.patch` in the scratch directory and the notice says `Its changes: <n> files changed, +<a> -<d>, as a patch against your working tree as it was when the task started: <file>. Apply it from <top> with git apply and check it.`, or `It changed no files.`; then `Files it changed that also changed in your working tree since: ...` and `Files the patch of task-<m> also changed: ...` name what may clash (the latest 20 patches are compared). The agent applies and checks it; nothing is applied on its own. The worktree is removed when the worker ends (also when its session fails to close), is stopped (its changes are dropped) or the session closes; a launch the close catches midway starts no subagent, removes what it made and answers `Refused: the session is closing.`, and the close waits for it, and before the next one is added the worktrees of Atelier's that a crash left (their folder gone) are removed one by one; a worktree of the user's is never touched, nor pruned. Nothing is left in the repository's `.git` but the snapshot's objects: the index is a file in the scratch directory, never split (`core.splitIndex` would write a shared index in `.git`), and no gc, maintenance or submodule runs. Outside a git repository with a commit a background worker is refused (`Refused: a worker runs in the background in a git worktree of its own, and <folder> is not in a git repository with a commit; run it without background.`); a background explorer runs in the parent's folder. A background subagent runs in `normal` and never asks: what would ask the user is denied with `Denied without asking: a background subagent cannot ask the user. Leave this out and say in your report what needs approval.` (`SessionOptions.unattended`). The events are `task_started { taskId, agent, label, outputPath, running }` and `task_finished { taskId, agent, label, status, error?, durationMs, outputPath, costUsd?, notified, running, waiting }` (`status` is `finished`, `failed` or `stopped`), said as the job events are; `running` in the job and task events and in `jobs_status` counts jobs and tasks together. They only add to protocol 7.
- ODD (Organic Driven Development) is core state, not prompt prose. A small task takes the small path from gentle-shell: the agent reads only what it changes and its helpers, in one batch, and runs the focused test and the suite in one command. With subagents, a line of the ODD rules ties each task's route (`inline` or one of the session's agents, by name) to the `task` tool's rules on when to delegate. For large work the agent keeps a feature document in `odd/tasks/<name>.md` (`## Specs`, `## Tasks`, `## Log`) through the `feature` tool, the only way to change it: `edit` and `write` refuse that directory. Atelier writes the log's user entries itself, verbatim (L1 is the original request), so the model never paraphrases you. The CLI prints `· <phase>` and `◆ <feature>: n/m done`; the desktop shows the phase in the status bar and the feature's tasks in a side panel.

After reserving the notice, the head gets 1,000 lines and half the remaining bytes (rounded up), the tail 999 lines and the other half. A byte cut may split a line but never a UTF-8 character. The client summary is capped at 500 Unicode characters, including an ellipsis when shortened.

For an oversized single line, use bash byte ranges. Do not repeat a mutation to retrieve its output.]`, with the feature's path substituted. No new action or option is needed: use `grep` with a task ID or `## Specs`/`## Tasks` to locate it, then `read` with `offset` and `limit` to inspect only that range. These reads reflect the current document, not a snapshot of an earlier result.

The line CLI and desktop already show their truncation marker; the TUI still hides successful ODD calls and shows feature progress separately. No protocol or client change is required. - Long-term memory (M6): with Engram 3.4.0 or newer installed, each session gets the project's memory (Engram resolves the project from the working directory). The agent searches and saves through the `memory` tool (a search's call is summed up for the user by how many memories it found, `2 results`, `1 result` or `no results`; the agent still gets each hit); a compact context of recent memory comes with the first message, outside the system prompt. Rules enforced in code: the user's prompts are saved to memory as prompts, never captured along with a memory: each prompt that starts a turn and each steer that enters one, from the main session only (not `/compact`'s instructions, review requests or a subagent's task), with the credentials Atelier recognizes replaced by `[REDACTED]`, best effort (a credential in another form is saved as written): a private key whole, from its `BEGIN` line through its `END` line, or to the end of the prompt without one; the whole value of a header whose name ends in `Authorization` (`Proxy-Authorization`, `X-Authorization`...), whatever its scheme and whether its name is quoted (a quoted value up to its closing quote; a header inside quotes, like curl's `-H '...'`, up to the quote that closes it; any other value, a quoted name's included (`"Authorization": Digest ...`), to the end of the line, quotes inside it included, except a JSON `null`, `true`, `false` or number, which ends where it ends, so `{"Authorization": null, "x": 1}` keeps `, "x": 1}`), and of a bearer token; the value assigned with `=` or `:` to a name containing `PASSWORD`, `PASSWD`, `SECRET`, `TOKEN`, `API_KEY`, `ACCESS_KEY`, `PRIVATE_KEY` or `CREDENTIAL`, in any case (an `AWS_SECRET_ACCESS_KEY=` among them; the name stays; a quoted value whole, across lines too and past a `\"` escaped in double quotes, and one whose quote is left open to the end of its line); the password of a `scheme://user:password@host` URL, up to the authority's last `@` (a password with `@` or `/` in it is masked whole); the password of a curl command's `-u` / `--user` and `-U` / `--proxy-user` `user:password` and of a wget command's `--password` (`--http-password`, `--ftp-password`, `--proxy-password`), however the shell would read it (quoted, `$'...'` included, escaped, `ana\:pw` among them, or attached, as in `-uana:pw`, to the first blank outside quotes, so `;`, `&`, `|` or a line continuation inside it are masked too; the option counts after a `curl` or `wget` with no `;`, `&`, `|`, parenthesis, backtick or newline between them, or after a quote, which may hide one; another command's `-u`, like `docker run -u 1000:1000`, stays); and Anthropic, OpenAI-style, GitHub, Google, AWS access key, Slack, npm (`npm_...`) and Stripe live (`sk_live_...`, `rk_live_...`) keys. The whole prompt is masked first and only then cut to 2,000 characters, never inside a `[REDACTED]`, so a cut cannot leave part of a credential; it is kept out when one of those keys is still found across words; it needs Engram's `mem_save_prompt`, each prompt is one attempt that the turn waits for at most 5 s before it ends (other memory calls get 15 s), and the first failure is the recoverable error `memory_prompt_failed` (`Your prompts are not being saved to memory: <reason>`), once per session. `ATELIER_MEMORY_PROMPTS=off` or `"memory": { "prompts": false }` in `~/.atelier/settings.json` ([settings](cli.md#settings)) keeps them out; anything shaped like a credential is refused when the agent saves a memory, subagents get no memory, and a finished ODD feature is saved under `odd/<name>/tasks` without the user's verbatim messages. A save that Engram keeps but could not check for conflicting memories (`candidate_detection_status: "incomplete"`) is not retried: the tool's answer says `Saved memory #<id>. Warning: ...`, and a feature mirror sends a recoverable `memory_mirror_warning` error. Each compaction that succeeds, on either backend (threshold, overflow or `/compact`), saves its summary as a `session_summary` titled `Session summary: <project>, <YYYY-MM-DD>` under the key `session/<id>/summary`, one per session, so later compactions of the same session update it; the turn waits for the save, and a summary shaped like a credential (`memory_summary_skipped`), a failed save (`memory_summary_failed`) or a save with a warning (`memory_summary_warning`) is a recoverable error, never retried. A save that succeeds sends `memory_summary_saved` with the memory's `id`, a `preview` (the summary's first non-blank line as plain text, its hidden characters shown as markers and its blanks as one space, capped at 200 code points with `…`, never inside a surrogate pair) and the `warning` when there is one; the warning still comes as `memory_summary_warning` too, for clients that do not know the event. The TUI and the line CLI show it as a memory call (`🧠 session summary "## Goal"` / `↳ ✓ saved #5519`), the line cut to 120 columns with `…` (by width, as a card cuts it; a TUI card then to its own width), with the warning inside it instead of the error. The summary is saved there and when the session changes backend, not when a session ends. After saving it, the core fetches the recent memory again (the same 2 KiB context as at start, one attempt) and puts a recovery notice before the next prompt, once, on either backend (Claude Code reports its compactions through its `PostCompact` hook): `<memory-recovery>`, `The conversation was compacted. Recent memory of project <project>:` and that memory, then what to do about the summary: when it was saved, `The compaction summary is already in memory; do not save it again.`; when the save got no answer or Engram failed while handling it (a timeout, a closed Engram, an internal error: it may have landed), to search memory for it first and save it once only if absent; when Engram refused it (an error answer or a protocol error such as invalid params), to save its key points once with the `memory` tool under the session's summary key; when it looked like a credential, not to save it. The notice counts as given only once the backend takes that prompt: if the backend fails before (it throws, or answers only with an error), the notice goes with the next prompt. The core's state that goes with the same prompt leaves the memory out, since the notice brings it, and so does the first turn's `<memory>` when the session compacted before its first prompt; when the recent memory could not be fetched again, neither leaves it out, so the memory from start still goes. If the recent memory does not come, the notice still says what to do, and the turn gets the recoverable error `memory_recovery_failed`. When Engram has `mem_session_start` and `mem_session_end`, each session registers itself at start as `atelier-<id>` in its folder (the same id as its summary key) and every write it makes (memories, summaries, prompts) names it; closing the session ends it in Engram, once, and a failure there is ignored. If the registration fails, the writes go without a session, as before, and the first turn gets the recoverable error `memory_session_failed`. Without Engram, sessions work and say why there is no memory (`memory: <project>` / `no memory: <reason>`); `ATELIER_MEMORY=off` turns it off. Only `atelier-core/src/memory/engram.ts` knows Engram, and a test enforces it.
  - Memory search: `{ action: "search", query, limit?, match_mode? }` requires a nonblank `query`; `limit` is an integer from 1 to 10 (default 10), and `match_mode` is `"all"` (default, every word must match) or `"any"` (any word may match). The tool tells the model: "If a search with all finds no results, retry once with the same query and match_mode: any before concluding there is no memory. Do not retry an empty any search or a failed search." This is a second tool call by the model, not an automatic retry inside the tool or adapter. Each call keeps the existing hit text and result-count summary. Engram 3.6.0 supports both modes; the adapter detects support from the `match_mode` property in the `mem_search` schema returned by `tools/list`, not the version number. When supported, it sends `match_mode` with `query`, `limit` and `response_format: "compact"`. Without that property, omitted mode and explicit `all` leave the field out and preserve the existing search; `any` makes no search request and returns `Memory failed: This Engram does not support match_mode: any; update it to use broader search.` Memory remains available and the minimum Engram version is unchanged.

- Project instructions: at session start the core walks up from the working directory (`--cwd`) through every parent folder, stopping before the user's home folder (or at the disk root if the folder is not under it), and takes `AGENTS.md` from each folder, or `CLAUDE.md` when there is no `AGENTS.md`. Before them comes the user's own `~/.agents/AGENTS.md`, if there is one, as `User instructions from <path>:`. The files are appended to the main session's system prompt from the outermost folder to the closest, each preceded by `Project instructions from <path>:`, so the closest comes last and wins a contradiction. It works the same on `anthropic-api` and `claude-code`, and the files are read once, at start (editing them later does not change the running session, which keeps the prompt prefix cache intact). The total is capped at 32 KiB: over it, the outermost files are dropped first, the user's file before any project file. The first turn reports `instructions: <paths>` and, if the cap left files out, the warning `instructions over 32 KiB, left out: <paths>`; the desktop shows both in the status bar. Subagents do not get them: they keep only their task and role instructions. There is no stop at the git root, so running in `atelier/` also reads `../AGENTS.md`.
- Skills: at session start the core looks for skills, following the [Agent Skills](https://agentskills.io) format, in `.agents/skills/` of the working directory and of each parent folder up to the repository root (the first folder with a `.git`, a folder or a worktree's file; outside a repository, the working directory alone), then in the user's `~/.agents/skills/`. It does not read `~/.claude/skills` or `.claude/skills`. A skill is a folder directly inside one of those (hidden folders are skipped, linked folders are followed) holding a `SKILL.md` whose YAML frontmatter has a `description`; its `name` defaults to the folder's. A `SKILL.md` without a description, with a description that is not a string, or whose frontmatter cannot be parsed or is never closed by `---`, is not loaded; nor is one in a place `read` refuses (a folder linked into `~/.claude`, say). A name that is not lowercase letters, digits and hyphens of at most 64, loads with a warning, and so does a description over 1,024 characters, which the prompt gets cut to 1,024; a name unlike its folder's is accepted silently. Of two skills with the same name the first found wins (the closest project folder first, the user's last) and the other is reported. The main session's system prompt gets, after the project instructions, a short instruction to read a skill's `SKILL.md` with `read` when a task matches it and to resolve its relative paths against the skill's folder, and an `<available_skills>` list with each skill's name, description and the absolute path of its `SKILL.md`; the body is never in the prompt. The block is capped at 24 KiB, its instructions included: the skills found after it fills up are not listed and each gets a warning. If the sandbox configuration is invalid, the places `read` refuses are unknown, so no skill is loaded and, when there were skills to load, a single warning says why. Project skills load without asking for trust, like `AGENTS.md`, and are read once, at start. `read` opens them without approval, since it reads outside the working directory everywhere but the protected locations. The first turn sends `skills_loaded` (`skills`: name and path; `warnings`: path and message) when there are skills or warnings; the CLI prints `skills: <names>` and one `skill <path>: <message>` warning each, the desktop shows them in the status bar. Subagents do not get the list: the agent names the `SKILL.md` in the task's prompt when a subagent needs it.
- The `openai-codex` backend runs Atelier's own loop, like `anthropic-api`, on OpenAI's Responses API with the ChatGPT subscription (`atelier login account openai-codex` or `openai-chatgpt`; see [cli.md](cli.md)). It has two variants. `legacy` signs in with the Codex CLI's OAuth client and sends to ChatGPT's Codex endpoint (`chatgpt.com/backend-api/codex/responses`, with the `chatgpt-account-id` taken from the token and `originator: atelier`). `chatgpt` is Sign in with ChatGPT, the sign-in OpenAI offers other agents, and sends to `api.openai.com/v1/responses`. The session uses `legacy` when it is signed in to it, then `chatgpt`; when the Codex endpoint refuses Atelier (403 or 404) and there is a ChatGPT sign-in, the session moves to it for the rest of its life and says so with a recoverable `variant_changed` error. `ATELIER_CODEX_VARIANT=legacy|chatgpt` forces one, with no move. **Terms of use:** `legacy` uses a client OpenAI issued to its own Codex CLI, on an endpoint meant for it; OpenAI may refuse it at any time, and using it from another program may go against its terms. `chatgpt` is the sanctioned way. Either one counts against the subscription's limits. The history is Atelier's, sent whole with `store: false`; each response's reasoning comes back encrypted and goes back with it, and its summary is shown as thinking. The tools are Atelier's, as functions; the thinking level is sent as `reasoning.effort` (`minimal` as `low`, `off` as `none`, not sent to the models that always reason). The prompt cache is keyed by the session; `cacheRead` counts the cached input and there is no cost, since the subscription pays. Before a request a token less than five minutes from expiring is refreshed, under the lock of `auth.json`, so several Atelier processes refresh it once; a refused token is refreshed once and the request retried (the summary requests of a compaction and of a backend change too); a refused refresh ends the turn with `not_logged_in` and the `/login` command to run. The subscription's limit ends the turn with `usage_limit` (the plan and when it resets); busy servers are retried three times. A request that fails after it showed text or thinking is never sent again, nor compacted and repeated on an overflow: the turn ends with a recoverable error and the history as it was before that request. Server-sent events may end their lines in `\r\n`, `\n` or `\r`. Every token is replaced by `[redacted]` in the messages it shows. Models: `gpt-6-sol` (default), `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`; another name is sent as it is. The Responses client (`atelier-core/src/responses/`) knows nothing of the sign-in, for other providers that speak the same API.
- Context compaction (M8): a long session no longer ends in a context error. On `anthropic-api`, before each model request the core compares the context (the last response's real usage plus an estimate of what was appended since) with `window − 16,384` tokens and compacts when the context passes it, not when it reaches it (as pi does: no cap, so a 1M-token model compacts near 983,616, and every request of a long session can carry that much; a `max_tokens` set above 16,384 can make a request pass the window, an error not yet handled as an overflow), the window coming from the models API (200,000 when it does not answer); `ATELIER_COMPACT_AT=<n>` sets a lower point, never one past the window minus the reserve. Crossing it, the core asks the session's model for a summary in a fixed format (Goal, Constraints & Preferences, Progress, Key Decisions, Next Steps, Critical Context), with the session's own prefix so it reads from the prompt cache, and replaces the older history with one message: the summary, the files read and edited (from the tool calls, not from the model; a file created or replaced with `write` counts as edited), the current turn's request verbatim when it was summarized, and once the core's state (active ODD feature and task, phase, the memory of the first turn). The last ~20,000 tokens stay verbatim and a tool result never loses its call. A summary that is empty, cut short or missing a section is refused and the history stays as it was; a context overflow compacts once and retries the request. `openai-codex` compacts by the same rules, on its history of Responses items (the window is 272,000 tokens, and it compacts when the context passes the window minus 32,000 kept for the answer, since no output cap is sent, and 16,384 more: 223,616 tokens), with the summary request on the session's model and endpoint and the tools present but not callable (`tool_choice: none`); its `session.set_backend` summary is made the same way. Claude Code compacts on its own: Atelier shows its compactions, forwards `/compact`, and gives the core's state with the next prompt. `claude-code` says how full its context is in `turn_finished.context` too, once a turn's result said the model's window: `tokens` is what the last main-thread request carried (the input, cache read and cache write tokens of its usage; the answer's output is left out, since Claude Code's messages carry only part of it, so the size can fall short by that answer), `window` the window a result said the model of that request ran with (never another model's: until a result says it for a model, no context is sent), and `compactAt` where Claude Code says it compacts that model (asked with `getContextUsage` in `summary` mode when a turn starts with no request in flight, until Claude Code answers for the model in use (one unanswered after 10 seconds counts as failed and its answer is dropped), and never waited for; the window until it answers, and when Claude Code does not compact on its own). Right after Claude Code compacts, until an answer measures it again, the size is unknown: `context.unknown` is `true` and `tokens` holds only Claude Code's estimate, or 0. A turn that ends without Claude Code's result (it crashes, ends the session, or does not stop in time after an interrupt) still says what is known of the context in its `turn_finished`. `unknown` is optional; the backends Atelier compacts set it too, from a compaction until an answer measures the new history (a `/compact` turn, or a turn cut right after its compaction), with their estimate in `tokens`. When the main agent's context reaches 90% of where it compacts (`compactAt`, which on `claude-code` can be far below the window), the session says it once with `context_warning` (`tokens`, `window`, `compactAt`), just before that turn's `turn_finished`; it says it again only after the context went below that point, was unknown, compacted (not a subagent's compaction: a subagent's context neither warns, nor rearms it, nor uses it up, and a subagent's own warning is not passed on), or the backend or the model changed (also back to one it was said for, and a new session of the same backend). A turn at whose end a backend or model change was applied carries no `context` in its `turn_finished`: it measured the model before the change, so clients wait for the next turn to measure the new one. Clients show it to the user, not to the model: `⚠ context at 18% of the 1M window (182,000 tokens), near where it compacts (200,000)`. `contextGauge` in `@atelier/core/protocol` is how every client shows the context: the share of the window as eight cells, its percentage and the window's size (`▰▱▱▱▱▱▱▱ 11% · 1M`, `▱▱▱▱▱▱▱▱ ? · 1M` while unknown), and a level measured against `compactAt`: `warning` past 70% of it, `danger` past 90%. Both clients show the compaction (before → after, messages kept, cost), mark the cache miss that follows it as expected, show how full the context is, and accept `/compact [instructions]`. A subagent compacts by the same rules in its own session (the threshold, one compaction on an overflow) and goes on with its task; its compaction events reach the parent tagged with `parentCallId` and `agent` like its other events, both clients show them under the subagent with its own expected cache miss, and its summary is never saved to memory. If a subagent's turn fails after its compaction failed, the task's error names both: `The worker subagent failed (error): <error>; its compaction failed: <reason>`.

- Temporary directories: each session's scratch directory, the verifier's copy, the temporary index of a freeze, the full output of a `bash` command run without a session and the files of an `mcp_call` run without a session (a long result, an image, a binary resource) are `atelier-session-*`, `atelier-verify-*`, `atelier-freeze-*`, `atelier-bash-*` and `atelier-mcp-*` in the system temporary folder. Each holds `.atelier-owner` (the pid and start time of the process that made it) next to `work/`, which is all the agent, the verifier, git or the tool sees. Closing removes them; a process that dies (`kill -9`, a crash, a closed terminal) leaves them behind. The first one a process creates starts a sweep of that folder in the background, once per process, which never delays the start. It deletes the directories whose owner process is gone or whose pid now belongs to a process that started more than 5 s after the owner (`ps` gives the start to the second), and those without an owner file (from Atelier 0.4.0 or older) once neither the directory nor anything right inside it has changed for 7 days. It looks only at those names and only at real directories of the current user, never at the current process's own, and keeps whatever it cannot tell for sure: a process of another user (`EPERM`), a live process whose start time `ps` does not give, an unreadable owner file, and everything on Windows. Before deleting, it moves the directory aside with one rename to an `atelier-trash-*` of its own and checks that what moved is the same real directory (device, inode, user and owner file) it found stale; anything else, such as a symbolic link or a new directory put in its place, goes back. The owner file is deleted last, and a deletion that fails part-way goes back to its name, owner file included, so the next process tries again. `ATELIER_SCRATCH_SWEEP=off` turns the sweep off; the test suite runs with it off (`vitest.config.ts`) and only `scratch.test.ts` turns it on, over a folder of its own. Known limits, accepted as they are:
  - Putting a directory back is a check followed by a rename: an empty directory that another process creates under the original name in between is replaced by it (one that is not empty is kept, and the directory stays as `atelier-trash-*`).
  - Once the moved directory passed its check, another process of the same user that swaps it for a symbolic link makes the deletion walk the link's target. Node has no `openat`/`unlinkat` to close this, and such a process can already delete those files itself.
  - On Windows, a directory without an owner file that is more than 7 days old is still deleted by the age rule, which comes before the Windows guard.
