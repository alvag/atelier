# Review and verification

How the core reviews a turn's changes with receipts (M7) and verifies high-risk turns independently (M9).

## Review with receipts

Review with receipts (M7, Receipt-Driven Development): at the end of a turn that made a change of its own in a git repo (see [Which turns are reviewed](#which-turns-are-reviewed)), the core freezes the candidate: the worktree (tracked and untracked but not ignored) against the tree of the `HEAD` the turn started at, as two git trees built with a temporary index, so your index and worktree are never touched and commits made during the turn are part of the candidate. If `HEAD` no longer descends from the commit the turn started at, the turn's HEAD reflog distinguishes rewritten commits from a move to other history (see [Rewritten commits](#rewritten-commits)); without a commit at the start of the turn (an empty repo) it is the empty tree, so the turn's first commit and everything after it are the candidate; if the turn brought in history it did not write (a `git pull`, a checkout of an existing branch), HEAD's reflog shows it and the base is where HEAD landed after that, or the current `HEAD` without a reflog, so other people's commits are never the candidate (while the repo still has no commit there is no review, and the turn says why once). After an automatic review approved without a correction (with or without follow-ups), as in gentle-shell, where every reviewed boundary becomes the next base, the session's next automatic round is measured from the tree that review's lenses saw, not from the turn's base, so each round sees only what changed since and the diff does not grow over turns without a commit: this holds while the next turn starts on the `HEAD` the approved review ended at and the base is still the turn's start (no reset, rebase or checkout during the turn); commits the agent makes during the turn do not matter, since the trees are compared. A review approved only after a correction does not move the base: its lenses saw the defective tree, so a later revert of the fix would vanish from the diff; the next round sees the whole change again, correction included. An `escalated`, `unavailable` or `declined` review does not move the base either, so what nobody approved is seen again, whole; a change that is empty against the turn's base (a revert of what was reviewed) is not reviewed; a commit, pull or checkout between the turns, a reviewed tree git no longer holds whole (no ref keeps it, so `git prune` or `git gc` can remove it or a blob only it held), and a new or resumed session go back to the turn's base; `/review` neither uses nor moves this base. The review derives its risk from the diff, with no model and no cost: `passive` (documentation only, 0 lenses), `medium` (1 lens, `reliability`) or `high` (4 lenses: `risk`, `resilience`, `readability`, `reliability`). Following gentle-ai's lens selection, the agent can pick the review's lenses itself with the `risk` tool (`lenses`, 1 to 4, with a `lensesReason` naming what it touched and how), and its instructions say when each lens applies; the choice applies to the candidate its turn assessed (a later `/review` of a different tree uses the default lenses); the chosen lenses replace the default at either level, and a high risk Atelier finds by itself (anything but the agent's own items) always keeps `risk`. High risk comes from paths (`auth`, `security`, `permission`, `payment`, `webhook`, `migration`, `secret`, `credential`), dependencies and environment files, and from the content of the added lines, following gentle-ai's method; the size of the change, the number of files and the model never count. Each signal is a named reason with its place: `shell_process: <path>:<line>` for a real process spawn (`spawn`, `exec`, `execFile`, `execSync`, `child_process`, `subprocess`, `popen`, `ProcessBuilder`, `os.system`, `proc_open`, `Process.Start`...; a member call such as `cp.exec(` or `childProcess.spawn(` counts only in a file that imports `child_process`, so `db.exec(` and `/re/.exec(` elsewhere are not spawns, and neither is `process.stdin.setRawMode`; spaces before the parenthesis do not hide a call) and `dangerous_sink: <path>:<line> (<sink>)` for a concrete sink: `eval`, `new Function`, disabled TLS validation, unsafe deserialization, shell commands composed from variables, `rm -rf`, `DROP TABLE`, `DELETE FROM`, world-writable modes, CSRF or JWT bypasses (the catalog is gentle-ai's, gated by language). A line that is only a comment in its file's language (`//`, `/* */`, `#`, `--`) is skipped, and so are the lines inside a block comment that an added line opens (code after its `*/` is scanned); a language Atelier does not know is never skipped. Only source, configuration and `.txt` files are scanned, never test files (`*.test.*`, `*.spec.*`, `__tests__`, `testdata`) or `docs/` and fixture folders, and only the first line of each kind per file is named. The scan fails closed: if the added bytes of scanned files pass 8 MiB the level is high with `process_scan_limit: <path>`. A change is `passive` only when every changed file is documentation proven by its content: an extension only nominates it, and a code fence, an interpreter line (`#!`), a `<script>` tag, MDX with imports, expressions or tags, binary content or text that is not UTF-8 make it not passive. Finally the level must be explained by its reasons (high needs a high reason, passive only `documentation only` over documentation files, medium none); if it is not, the level is high with a `tier_not_explained` reason. The agent's declaration can raise the level, never lower it. Following gentle-shell, the main agent closes every code change by declaring its risk with the `risk` tool: the high-risk items that apply (1 data that cannot be rebuilt or irreversible effects, 2 security, 3 contracts others consume, 4 concurrency, which includes asynchronous events or callbacks that can arrive in another order, turn or request than expected, interrupts and timeouts, races, shared mutable state and locks, 5 delivery or environment, 6 no test would catch a regression), each with a reason, or `none` with a reason (`{ "none": true, "reason": "..." }`), and optionally the lenses (`{ "items": [4], "reason": "...", "lenses": ["resilience"], "lensesReason": "..." }`). A declaration can only raise the level, never lower what the diff shows. If a code change reaches the end of the turn without a declaration, the core asks the agent once, inside the same turn, to declare it; if it still does not, the risk is not lowered (it stays at least `medium`) and the risk line says `no risk declaration`. A declaration covers only the turn it was made in: it is cleared when the next turn starts. If the agent edits, commits or resets while answering the request to declare, the candidate is frozen again (tree, base and base note are compared) and the new one is assessed. The `review_assessed` event carries the declaration (`declaration`: `items`, `none` or `missing`; absent for documentation), the reason for the chosen lenses (`lensesReason`, also on `review_consent_requested`; absent when the agent did not choose) and the base when it is not the current `HEAD` (`since`: the short id of the commit the change is measured from, so the turn's commits are included; `sinceReview`, in its place, when the change is measured from the last approved round: that review's `reviewId`, shown as `since the last review` in the CLI and the TUI and `Changes since the last review` in the desktop; `baseNote`: why a history move retained or changed the base, or that it is the empty tree because the turn started without commits), and both clients show them: the CLI as `◇ review medium · 1 lens (...) · declared none: <reason> · since 1a2b3c4` (with chosen lenses, `◇ review high · 2 lenses: resilience, reliability (...) · lenses chosen: <reason>`), the desktop in the review block; the consent question shows only the question and its answers, since the review line above it already says why. A high-risk candidate is offered for review with a consent question, `Review this high-risk change?`, with three answers (`session.review_consent` with `answer`): `Review this change` (`granted`: only this candidate), `Skip this time` (`declined`: a declined receipt, and the next high-risk candidate asks again) and `Review all this session` (`granted_for_session`: this candidate and every later high-risk candidate of the same session is reviewed without asking; the permission lives in the core's memory, so a new or resumed session asks again, and its later assessments carry `consent: "session"`, which the clients show as `allowed for this session`). No answer turns the review off: that is `--no-review` or `ATELIER_REVIEW=off`. The CLI asks on a terminal, the TUI in a list that starts on `Review this change` (Esc skips), the desktop in a card; `/review` in the CLI and the Review button in the desktop review any risk, without asking, against `HEAD`; `/review <ref>` in the CLI (`Session.review(turnId, base)` in the core, `session.review` with `ref` in the protocol) reviews the worktree against that git ref instead, and refuses an unknown one with `Unknown git ref "<ref>": there is nothing to review against.` (the desktop button takes no ref). A receipt records the candidate tree, so the same worktree state is not offered twice whatever its base (any receipt of that tree counts, however many there are). The lenses are read-only subagents on the session's model that read the frozen tree, never the live worktree. Each lens gets the risk reasons, the list of changed files and the patch, at most 200 KiB with its instruction. A change that fits gets one prompt per lens. A larger one (several commits of a branch, say) is split by file, in path order so a folder stays together, into the fewest parts that each fit (at most 4): each lens runs once per part, every part lists all the changed files and says which part it is, the lens can read the rest with `read` and `grep`, and the findings of all the parts are joined and numbered again (`RL-001`, `RL-002`...), so the refuter, the correction and the validator, which get only the findings, never the patch, work as with one part. A part that fails makes the review `unavailable`, and what the other parts found stays as follow-ups. A file whose patch does not fit 200 KiB alone, or a change that needs more than 4 parts, is refused before any model call (`context_too_large`), never truncated; the refusal says to review smaller candidates. The receipt's `parts` says how many parts there were (absent for one). Each lens, the refuter and the validator may make at most 50 model requests per run, on every backend (on `claude-code` as its `maxTurns`); a lens split into parts shares its 50 equally among them (`⌊50/n⌋` each: 25 for 2 parts, 12 for 4), so the lens stays within 50; a lens's second try, after a reply it could not read, gets only the requests its first try left (a try whose backend reports none counts as one; none left: `request_cap`), so a retry never starts the cap over; and each part's events are tagged `agent: "review:<lens>#<part>"` (`review:reliability#2`) instead of `review:<lens>`, since the parts run at once and their streams must not mix; a role that runs out ends with `turn_limit` (`error_max_turns` on `claude-code`) and counts as `request_cap`. Findings have four levels, `blocker`, `critical`, `warning` and `suggestion`, and only `blocker` or `critical` findings caused by the candidate block. The lenses and the refuter apply gentle-ai's criterion (`reviewerprovider/contract.go`): a severe finding must name its observable harm (violating what was requested, or breaking something that worked before); silently ignoring an explicit option, or changing an existing output nobody asked to change, is also severe; what already happened on the base, what needs out-of-range values and what falls outside the scope without violating anything is at most `warning`. Receipts and lens replies written before the four levels used `major` and `minor`: they are read as `warning` and `suggestion` (a receipt file is never rewritten). The refuter answers `confirmed`, `refuted` or `downgraded` for each severe finding; a downgraded one (the claim holds but names no harm that meets the criterion) becomes a `warning`, stops blocking and stays in the receipt's `followUps`, and `review_progress`'s `refuter_finished` step carries `downgraded` next to `confirmed` and `refuted` (the CLI prints `◇ review: 0 confirmed · 1 refuted · 2 downgraded`, the last part only when there are any). The refuter confirms, downgrades or discards them once, the main agent makes one correction within `min(200, ⌈n/2⌉)` changed lines (at least 2, measured by the core), and a validator checks it. The correction request says not to commit, unless the reviewed work is already committed (the base is an earlier commit, whether the agent committed during the turn or an on-demand `/review <ref>` covers commits): then it asks to commit the correction on the same branch once its checks pass, so corrected work is not left uncommitted; the verifier's correction request does the same. The verdict is `approved`, `escalated` (out of budget or unresolved: the correction stays in the worktree and nothing else is attempted), `declined` or `unavailable`. Every review leaves its own JSON receipt, `<git-dir>/atelier/reviews/<candidate tree>-<id>.json`, never in the worktree, so a second review of the same tree (a `/review`, say) does not replace the first; whatever looks a tree's receipt up takes the most recent by `createdAt`, and receipts stored as `<candidate tree>.json` by older versions are still read, never renamed, and compete by their `createdAt` too. The same candidate is not offered twice. Approving never commits, pushes or opens a PR. An escalated correction can be undone: `/undo-correction` in the CLI (the repository's latest escalated review with a correction, found among the receipts in `<git-dir>/atelier/reviews/` by `createdAt`, so it works in a new session or after Atelier restarted), the Undo correction button in the desktop's review block (that review), `session.undo_correction` (`sessionId`, optional `reviewId` of a review of that session; without it, the repository's latest one as with `/undo-correction`; answered with a `turnId` like `session.send`) or `Session.undoCorrection(reviewId?)` in the core. It is a turn without a model call that puts back, in the worktree only, the files the correction changed, with the bytes and mode they had in the candidate tree (files it created are removed, with the folders that leaves empty, files it deleted come back); other files, the index and the commits are not touched. It fails closed and changes nothing when a file the correction changed is no longer as the correction left it (error `correction_changed`, naming the files), when the correction was committed since the review (`correction_committed`: HEAD moved to the corrected version of one of its files; a file HEAD already held, such as one the correction reverted to HEAD or a new file it deleted, does not count), when it was already undone (`correction_already_undone`), when the review was not escalated (`not_escalated`) or left no correction (`no_correction`), or when its receipt has no `headTree` (receipts written before Atelier kept it: `undo_failed`, saying so); these are recoverable `error` events and the turn ends with `stopReason: "error"`. On success the event `correction_undone` (`reviewId`, `restored`, `removed`) follows, the CLI prints `✓ correction undone · restored a.ts, src/auth.ts · removed src/extra.ts`, the desktop shows it in the review block, and the receipt of the review that was undone (that very file, never a newer receipt of the same tree) gets `undoneAt`. Each receipt keeps `headTree`, the tree of `HEAD` when the review ended, which is how a later commit of the correction is told. Its `base` is the tree the change was measured from; when that is the last approved round's tree, `previousReview` holds that round's receipt id. If writing fails midway (a disk error, a folder that refuses the change), the files it reached are put back as the correction left them (the bytes and mode of the corrected tree, which the worktree was checked to hold before it began) and the error `undo_failed` says so; only if putting them back fails too does the message name the files that may be in neither state. Review is on by default; `--no-review` or `ATELIER_REVIEW=off` turns it off, and without git (or without a commit) it says why there is no review; `/review` in a repo without commits is refused with the same reason.

### Which turns are reviewed

A turn made a change of its own when it ran at least one tool outside this list: `read`, `grep`, `web_fetch`, `web_search`, `ask_user`, `memory`, `phase`, `risk`, `job_list` and `mcp_search`. So `write`, `edit`, `bash`, `bash_background`, `mcp_call` (even a call of a server's tool that only reads) and any other tool count, and so do `feature`, which writes the feature document in `odd/tasks/`, and `job_stop`: a stopped job sends no notice and may leave files half written. A `task` counts when its subagent works in the session's folder with a tool outside the list: a `worker` without `background`, which writes in the session's own working directory, or another agent defined with such a tool; an `explorer` does not, and neither does a `worker` in the background, which writes only in a worktree of its own (applying its patch is a call of the agent's own). A call counts once it runs, even if it fails, since a command that exits with an error may have written first; a call that never runs does not count: one the guard or a protected path refuses, one the user or the classifier denies, one of an interrupted turn. A turn that hears that a `bash_background` job of the session ended (its notice comes with the prompt or with a tool result) made a change of its own too, since what the job wrote is the session's. The rule does not look at the worktree: the files are not compared at the start and the end of the turn.

A turn without a change of its own is not assessed: no `review_assessed`, no request to declare its risk, no verification, no consent question and no receipt, and the base of the last approved review stays where it was. It still takes the pending `<review-followups>` block, and the note that there is no git or no commit waits for the first turn with a change of its own. A turn with a change of its own is reviewed as before, whole: the changes others made in the same worktree are part of its candidate. What others change in the worktree (another session, the user, a `!command`, another program) is reviewed with the session's next turn that makes a change of its own, as long as it is still uncommitted, or with `/review`; until then, and if no such turn comes, no review sees it. A `bash_background` job still running when the session closes is not reviewed automatically. `/review` and the desktop's Review button do not depend on the turn: they review the worktree as it is.

### Rewritten commits

Before the agent's tools run, the session captures the starting commit, all ref tips with `git for-each-ref` (local branches, remote-tracking refs, tags and stash), and a boundary in that worktree's HEAD reflog, located with `git rev-parse --git-path logs/HEAD` (not the common gitdir in a linked worktree). When the starting commit is no longer an ancestor of HEAD:
- Commits and amends made during the turn retain the starting commit's tree as the base. A reset to an ancestor followed by a new commit also retains that tree: the turn's replacement, including deletions, is reviewed rather than disappearing against HEAD.
- A reset alone uses the final HEAD as the base, so removed history is not a candidate. Edits left uncommitted after the reset are still included.
- A branch switch onto pre-existing history moves the base to where HEAD landed after the switch. Later commits and uncommitted edits are included, not that branch's existing history. Creating or switching to a branch at a commit made during this turn instead restores that commit's attributed base and ownership, even after visiting another branch; earlier turn changes must not disappear from a later amend. The same rule retains the mapped boundary of a turn-owned rebase replay. A switch alone produces no review of unrelated history.
- A complete linear rebase matches the original commits to their replays in order, by unique, nonempty patches (only the index blob ids are ignored; paths, modes, hunks and bytes must match). Commits created during the turn must form a suffix of that sequence. The base is the rewritten boundary before the first own replay, excluding upstream and pre-turn commits. A pure rebase without own commits uses its landing HEAD only after the same replay checks; operation messages alone cannot make newly written changes pre-turn replays. Dropped, empty, reordered, squashed, merged or conflict-resolved replays, and changed hunk offsets, cannot be attributed by this rule and report unavailable rather than guessing.
- Unrecognized or unverifiable rewrites report `review_status` with `available: false` and a reason instead of silently treating the turn as unchanged. This also covers a missing or expired HEAD reflog, `core.logAllRefUpdates=false` (even when an old log remains), and a message-less `git update-ref`. A failure while re-freezing after the risk declaration reports the same status; no stale snapshot is assessed. The explicit `/review <ref>` remains available.

Reflog messages are written by the operation and can be forged, so a `checkout:` or `rebase (start):` message alone never proves that a destination is unrelated pre-turn history. A checkout without a saved own-commit base, or a rebase's starting landing/upstream, must be reachable from one of the initial ref tips. The check uses the captured tips, not the refs at review time; annotated tags and ancestors of tips count. If that proof fails, automatic review reports `review_status` with `available: false` and `Cannot safely attribute the turn's rewritten commits: a HEAD move goes to history that did not exist when the turn started.`

Consequently, on this rewritten-history path, a fetch or pull followed by checkout or rebase onto history first obtained during the turn reports unavailable rather than excluding that history silently. This conservative cost is intentional; `/review <ref>` remains available for an explicit comparison. A repository without commits at turn start keeps its existing empty-start rule.

The existing rule for a start that **is** still an ancestor is unchanged: it uses the turn-start tree, even if upstream history arrived during the turn. That separate upstream-attribution limitation is not fixed here. The temporary-index snapshot, staged/unstaged handling, first-commit rules and receipt format are unchanged. A history-move note also prevents reuse of the previous approved round's base.

The exact base notes are (ids are short commit ids):
- `HEAD no longer descends from <start>, where the turn started: the base remains the turn-start tree because the turn rewrote its commits`
- `HEAD no longer descends from <start>, where the turn started: the base moved to <base>, where HEAD landed after the branch switch, to exclude that branch's history`
- `HEAD no longer descends from <start>, where the turn started: the base is the current HEAD`
- `HEAD no longer descends from <start>, where the turn started: the base moved to <base>, before the turn's replayed commits, to exclude upstream history`
- `HEAD no longer descends from <start>, where the turn started: the base moved to <base>, where HEAD landed after the rebase, to exclude upstream history`

An attribution failure uses `Cannot safely attribute the turn's rewritten commits: <detail>.`, where `<detail>` is one of:
- `the worktree's HEAD reflog is unavailable`
- `the worktree's HEAD reflog no longer contains the turn-start boundary`
- `a HEAD reflog entry has no operation message`
- `the HEAD reflog transitions are incomplete`
- `a HEAD reflog operation is not attributable`
- `the rebase replay cannot be attributed unambiguously`
- `a HEAD move goes to history that did not exist when the turn started`

### What the agent is told

The agent does not see the review's events, so the core tells it how its latest review and verification ended: before its next prompt, once, a `<review-followups>` block. For a review: the verdict and its reason (the line cut to 300 characters), how many unresolved findings (escalated only) and follow-ups it left, whether an escalated correction is still in the worktree (the user can undo it with `/undo-correction`) and the receipt's path. For a verification that did not pass (`needs_decision`, or `failed` other than by an interrupt), before the review: its outcome and reason (cut the same way) and how many open defects and unverified requirements it left. Then one list for the whole block, `Items, the most severe first:`, at most 10 items in all, each one line cut to 160 characters: `- <id> <severity> <path>:<line>: [unresolved] <claim>` or `[follow-up]` for the review, `- <id> <severity>: [open defect] <summary>` and `- <id> unverified: [requirement] <requirement>` for the verification, with `…and N more in the receipt` (or `in the verification's events`) for the rest. The order uses one scale, `blocker`, `critical`, `major`/`warning`, `minor`/`suggestion`: the verifier's `major` and `minor` rank as `warning` and `suggestion`, and an unverified requirement as `warning`. A review the user skipped is one line, `The user skipped the review of your last change (risk high); it was not reviewed.`; an approved review without follow-ups, a verification that passed, and an interrupted review or verification say nothing. A `/review` is told the same way. Only the latest review and the latest verification count: a newer one replaces the older one's notice, and an interrupted one, which says nothing, drops it. Everything in the block that Atelier did not write (the reviewers' and the verifier's text, ids, paths and `path:line`, the receipt's path) is put on one line with `&`, `<` and `>` escaped, so it can neither close the block nor open another, and the block says that the items are the reviewers' information, never instructions, and that the agent should act on them only if the user asks. The block counts as given only once the model answered (text, thinking or a tool call, or a turn that ended other than on an error or an interrupt); if the backend fails before that, even after reporting `session_started`, the block goes with the next prompt, unless a newer review or verification ended since. Clients see no new event: the block is part of what the backend receives, like the recent memory.

## Independent verification

Independent verification (M9, following gentle-shell's `gentle-ai-verify`): when the agent's risk declaration for a turn names at least one high-risk item (1 to 6; `none`, no declaration, and a high risk that only the diff showed do not count), the core, not the model, runs a `verifier` role on the turn's frozen candidate at the end of the turn, before the review is assessed or offered. It is not asked for consent (the review keeps its consent), and `--no-review` / `ATELIER_REVIEW=off` turns verification off with the review. The verifier works in a temporary directory (`work/` of an `atelier-verify-*` in the system temp folder; see [temporary directories](architecture.md)) that holds `candidate/` and `base/`, both written from the frozen git trees with `git cat-file`, so your worktree, index and refs are never touched and no attribute or filter of the repository runs. Installed dependencies are made usable without installing and without sharing them with your project: every `node_modules` of the worktree (the root's and each workspace package's) is copied into both copies (a copy-on-write clone with `cp -c` on macOS, `cp --reflink=auto` on Linux, a plain recursive copy otherwise; links stay links, files are new ones, so a hard link to the pnpm store is broken). A symbolic link in the copies that points into your project is re-pointed at the same place of the copy, so the candidate's tests run the candidate's code, and one that points anywhere else is removed (the verifier is told how many). More than 4 GiB of dependencies, more than 120 seconds of copying, or a failed copy leaves the copies with no dependencies, and the verifier is told and marks those requirements unverified; so does a project without any. What the verifier's `bash` writes in `node_modules` stays in the copy. Its `bash` is confined by the sandbox (see [Sandbox (macOS)](sandbox.md)): it writes only this directory and has no network; without a sandbox it gets no `bash`. The copy is removed when the verification ends, also on error or interrupt. The verifier has `read`, `grep` and `bash` with that directory as working directory; its `bash` runs without asking (only there) with the same filtered environment as the agent's `bash`, plus variables that make package managers refuse to install or fetch (`npm_config_offline`, `pnpm_config_offline`, an unreachable `npm_config_registry`, `npm_config_manage_package_manager_versions=false`, `NO_UPDATE_NOTIFIER`, `COREPACK_ENABLE_NETWORK=0`, `YARN_ENABLE_NETWORK=0`, `PIP_NO_INDEX`, `CARGO_NET_OFFLINE`, `GOPROXY=off`); its mandate also forbids installing and using the network, and caps it at 80 model requests per run. It receives the user's request for the turn verbatim, a copy of the active ODD feature document (`feature/<name>.md`), the agent's declaration, a summary of base vs candidate and, since the copies have no `.git`, what the repository shows: the current branch (`none (detached HEAD)` without one), the short id and subject of each commit from the base to `HEAD` (oldest first, at most 50 listed), and whether the worktree holds uncommitted changes (so it can check requirements such as working on a branch and committing; if git cannot answer, this part is left out), and must derive the requirements, run probes (including hostile input aimed at what the declared item protects), reproduce every defect on `candidate/` and on `base/` (a defect that also happens on the base is advisory), and answer one JSON report: a verdict per requirement (`met`, `unmet`, `unverified`, with evidence) and the defects (`blocker`, `major` or `minor`, with reproduction, behavior on the candidate and on the base, `onBase`). A reply that is not a complete report (including one with no requirements) is a failed verifier, never a pass. A requirement judged `unmet` counts as a blocker even without a defect. Blocker or major defects that are not on the base, and unmet requirements (as `R1 [blocker] Requirement not met: ...`, with the verifier's evidence), go to the main agent once, inside the same turn, as a correction request; the candidate is frozen again and the verifier runs a second time. There are at most two rounds. It passes only when every requirement is `met` and no blocking defect is left; a requirement still `unverified` ends it with "needs your decision" and the list of them, never as a pass. If blocking defects remain after round 2, or the verifier failed, the turn ends with a visible "needs your decision" and the open defects; it does not loop. The review then continues on the final candidate as usual. Events: `verification_started` (`verifyId`, `items`, `declaration`), `verification_round` (`round`, `ok`/`error`, `cause`, `observed`, `requirements`, `defects`, `blocking`, `correcting`, `usage`, `costUsd`) and `verification_finished` (`outcome`: `passed`, `corrected`, `needs_decision` or `failed`; `reason`, `cause`, `observed`, `rounds`, `openDefects`, `usage`, `costUsd`); the verifier's own events are tagged `agent: "verify:verifier"` under `verifyId`, and its cost (and the correction's) is added to the turn's `turn_finished`. The CLI prints `◇ verifying · item 2`, `◇ verify · round 1 · 2 defects (blocker, major) · asking the agent to fix them`, `✓ verify passed`, `✓ verify passed after a correction · 2 rounds`, `✗ verify: needs your decision · 1 open defect` (followed by each defect and its reproduction), `✗ verify: needs your decision · 1 unverified requirement: R1 ...` and `✗ verify failed: <reason> · needs your decision`; when the event has a cause they show it with the value observed in place of the reason, as in `◇ verify · round 1 · failed: invalid_report (looks fine to me)`, `✗ verify failed: request_cap (80 requests) · needs your decision` and `✗ verify: needs your decision · open_defects (D2)` (for `needs_decision` the reason follows, since it lists the unverified requirements); the desktop shows a verification block with the declared items, each round's verdicts and defects, and the outcome. Every verifier or review that ends without a pass names why, from a closed set, never only with a message: the optional fields `cause` and `observed` (the value seen, when there is one) on `verification_round` (with `ok: false`), `verification_finished` (`needs_decision` or `failed`) and `review_finished` (`escalated` or `unavailable`), and in the review receipt. The causes: `interrupted`; `role_failed` (the verifier or a review role could not start or failed; `observed`: its error); `request_cap` (it ran out of model requests; `observed`: `80 requests` for the verifier, `50 requests` for a review role); `invalid_report` (the verifier's reply is not a complete report) and `missing_requirements` (it lists none; `observed`: `0 requirements`); `invalid_reply` (a lens, the refuter or the validator answered something unreadable); `context_too_large` (`observed`: `<bytes> bytes, limit 204800`; the review's reason says the change is too large and to review smaller candidates); `patch_unreadable`; `copy_failed` (the verifier's copy could not be made); `sandbox_unavailable` (the verifier had no bash and left requirements unverified; `observed`: the sandbox's reason); `correction_failed`; `freeze_failed`; `measure_failed`; `over_budget` (`observed`: `<used> lines, budget <budget>`); `unverified_requirements`, `open_defects` and `unresolved_findings` (`observed`: their ids). A reply or an error given as `observed` is its start on one line, cut at 200 characters. The existing `reason` and `error` stay as they were. Clients show `<cause> (<observed>)`, followed by the next action for a cause that has one, as gentle-ai's review stop reasons do: `context_too_large (900000 bytes, limit 204800) · review smaller candidates: commit in steps, or /review <ref> from a nearer commit`.
