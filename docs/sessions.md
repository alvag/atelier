# Saved sessions

Where sessions are saved, what the files hold, and how to resume them.

The core saves every session the CLI or `atelier-core serve` starts (when it has a home directory; the echo test backend saves nothing) under `~/.atelier/sessions/<folder key>/<session id>.jsonl`. The folder key encodes the session's `--cwd` the way pi does: the path without its leading `/`, with `/`, `\` and `:` as `-`, between `--` (`/Users/me/app` is `--Users-me-app--`; one too long for a file name, over 200 bytes of UTF-8, ends in a hash and stays within the 255-byte file name limit). Two folders can share a key (`/a-b` and `/a/b`): every file names its own `cwd`, and listing, resuming, renaming and deleting skip the other folder's. That holds for any file whose header can be read, whatever its format version (a file from a newer format is never deleted from another folder); a file whose header cannot be read is not known to belong to any folder, so it is not listed and `session.delete` refuses it (`not_found`). Sessions are per folder, so a worktree never sees the sessions of another.

**What the file holds.** One JSON object per line. The first is the header `{ "kind": "atelier.session", "version": 1, "id", "cwd", "createdAt", "name"? }`, written with the first entry (a session that never ran a turn leaves no file). Then, in order: `config` (backend, model, thinking level, permission mode and profile _name_, at the start and each time `session_configured` says it changed), `prompt` (each turn's prompt, a queued message's when it started the turn), `text` (the main agent's text of a segment, one entry for all its deltas, tagged with `agent` and `parentCallId` for a subagent), `event` (every other event as clients got it, `turn_finished` last in its turn; thinking deltas are not kept, nor `queue_update`: a queued message is saved only once it enters the conversation, a steer as its `queued_message` event), `state` (what the backend needs to resume, written before the turn's `turn_finished`) and `name` (a rename). Each is a single appended write, so a crash costs at most the last line, which readers ignore; the next writer of that file removes it before appending. A line that is not JSON anywhere else, a header that is not ours or an entry missing what it needs makes the file `corrupt`; a header with another `version` is `unsupported_version`. Both are still listed, with `resumable: false` and the reason in `problem`, and neither is touched. Nothing rewrites a session's file: a rename appends a `name` entry.

**The file holds what the agent saw.** Tool outputs are part of the saved state, not only their summaries: the `anthropic-api` history in the file carries every tool result in full, and Claude Code keeps its own session (with the same outputs) under `~/.claude/projects/`, which is why `claude-code` sessions now run with `persistSession: true` when they are saved (subagents, review roles and the classifier never are). Paths, file contents and command output can include secrets. Because of that, the files are private: `~/.atelier/sessions` and each folder are created `0700` and the files `0600`, and a folder or file that is looser when Atelier opens it is tightened. Delete a session (`session.delete`) to remove its file; Atelier does not expire old ones.

**One writer per file.** A running session holds `<id>.jsonl.lock`, created exclusively with the process id in it. A second process (or, in the server, a second session) that wants the same file is refused: the CLI prints `error: Session <id> is already in use by another Atelier process (pid <n>).` and exits 1, the server answers `session_in_use`. The lock is released when the session closes (even if closing fails) and when the process exits; the lock of a process that is no longer running is taken over. A `.lock` file is not a session and is never listed. A rename only appends one line and does not take the lock.

**The backend state.** `claude-code` saves Claude Code's session id and resumes with `resume: <id>`; it first checks with the SDK that Claude Code still has that session for the folder and fails to start otherwise. `anthropic-api` saves its message history as an append-only log: after each turn the messages the file does not hold yet follow as one `state` entry (`replace: false`), and when the history no longer starts with what is saved (a compaction replaced its beginning, an interrupted turn merged into a message) the whole history is written once (`replace: true`). A snapshot per turn would write the whole conversation every time, so a long session's file would grow with the square of its length; this grows with its length. The state belongs to the backend that wrote it, so a session resumes with the last configuration of that backend: a backend change whose turn never finished is not resumed.

**Resuming.** `--continue` resumes the newest session of the folder that can be resumed (by the file's last write), `--resume <id>` a given one. Both print `resumed session <id>: <n> turns`, then each prompt after `> ` (and after it, the same way, what was steered during its turn) with the final text the main agent wrote in that turn (control characters shown as markers), and then go on: interactive, or with the prompt given on the command line. The saved backend, model, thinking level and mode are restored; the profile is frozen again by name from the files as they are now, the way a session freezes it at start. `--model`, `--mode`/`--yes` and `--profile` replace the saved ones; `--backend` must be the saved one (`error: Session <id> was saved on claude-code; --backend anthropic-api cannot resume it.`, exit 2). A restored model counts as chosen by the user: later profile changes do not replace it. A session that was never answered (no `state` yet) starts empty with its saved configuration. A resume that fails (`error: No saved session "<id>" for <cwd>.`, the file corrupt or from a newer format, or the backend cannot resume, as when Claude Code no longer has the session: `error: Could not resume session <id>: ...`) exits 1, starts nothing and leaves the file as it was. A resumed session writes to the same file. `--no-session` turns recording off for the run, and `session.start` takes `noSession: true` for the same.

**Protocol.** `session.start` answers `savedId` (the file's id) besides `sessionId` when it saves the session, and always `configuration`, what the first turn runs with, as `session.set_model` answers it.
- `sessions.list` (`cwd`) answers `{ sessions }`, newest first by the file's last write: `id`, `name`, `createdAt`, `updatedAt`, `turns` (prompts), `lastPrompt` (one line, at most 80 characters), `backend`, `model` (absent while the default ran), `resumable` and, when it is not, `problem`.
- `session.resume` (`sessionId` is the saved id, plus `cwd`) starts a live session from the file and answers `sessionId` (the live one), `savedId`, `name`, `createdAt`, `configuration` (as `session.set_model` answers it) and `entries`: the saved transcript in order (`config`, `prompt`, `text`, `event`, `name`; never `state`), so a client can show it again. One command answers with the transcript, rather than a separate `session.history`, so there is no window in which the session is live and its history is not yet known, and a client that does not want it ignores the field. Codes: `not_found`, `unsupported_version`, `corrupt`, `session_in_use` (this server, or another process, already runs that file: one writer per file), `session_resume_failed` (`Could not resume session <id>: <why>`), `sessions_unavailable` (no home directory, or saving is off).
- `session.rename` (`sessionId`, `cwd`, `name`: 1 to 200 characters, trimmed) appends the name and answers `{}`; `session.delete` (`sessionId`, `cwd`) removes the file and answers `{}`, refused with `session_in_use` while this server runs the session. A saved id is letters, digits, `-` and `_` (at most 128, not starting with a symbol); anything else is `invalid_command`.
